CI/CD 从 0 系统学习路线

本档为==自包含学习文档==，新会话可直接拿来用，不依赖任何前置对话上下文。
选型已定：==GitLab CI + Argo CD==，三亮点子模块：Trivy 镜像安全扫描 / Argo Rollouts 金丝雀发布 / Prometheus+AlertManager 监控告警闭环。
终点目标：能独立搭建 GitLab CI + Argo CD 流水线 + 三亮点，且能扛面试深挖。
时间线：8 月中完成最小闭环（约 2—3 周），对齐秋招正式批投递。

一、前置基础检查

开始前确认这些基础已具备（你已有）：

基础 要求 你的情况
K8s 会部署 Deployment/Service，理解 Pod/CRD 概念 已有（沃趣实习）
Docker 会写 Dockerfile，构建/推送镜像 已有
Git 会 commit/push/分支管理 已有
Linux 命令行 熟练 已有
一个 K8s 集群 能跑实验（本地 k3s/kind 或云上） 需准备

==准备一个实验集群==：本地用 k3s（轻量）或 kind（K8s in Docker），云上用 ACK/TKE/CCE 托管版。整个学习过程都要在这个集群上实操。

二、关键概念速查（先理解再动手）

什么是 CI/CD

  • CI（Continuous Integration 持续集成）：开发者 push 代码后自动编译、测试、打包。类比==自动质检流水线==
  • CD（Continuous Delivery/Deployment 持续交付/部署）：自动把应用部署到运行环境。类比==自动配送卡车==
  • 没有 CI/CD 时：手动编译、手动传包、手动部署，易错且慢
  • 有了 CI/CD 后：==git push 一键触发全流程==

CI/CD 的典型流程（你要做出来的项目骨架）

三工具各自是什么

GitLab CI：GitLab 自带的 CI 引擎，代码仓库和 CI 一体化。用 .gitlab-ci.yml 定义流水线，通过 Runner（执行器）跑任务。负责 CI 部分（编译、测试、构建镜像）。

Argo CD：==CNCF 毕业项目==，专门做 K8s 的 CD。核心理念是 ==GitOps==：把 K8s 部署清单（YAML）存在 Git 仓库，Argo CD 监听 Git，发现变更就自动同步到 K8s。你声明”集群应该长这样”，Argo CD 保证集群和声明一致。

Jenkins（对比用，不学）：老牌 CI/CD 工具，Java 写的，插件生态丰富。既做 CI 也做 CD，和 K8s 集成要靠 Kubernetes Plugin。==你选 Argo CD 而非 Jenkins 的理由==：K8s 原生集成 + GitOps 理念 + 声明式 + 可回滚。

GitOps 三句话（必须张口就来）

  1. ==Git 是唯一真源==（Single Source of Truth）：集群状态由 Git 仓库的声明决定
  2. ==声明式==（Declarative）：你声明”应该是什么样”，系统保证达到
  3. ==可回滚==（Reversible）：git revert 即回滚到历史版本

GitLab CI + Argo CD vs Jenkins 核心区别

维度 GitLab CI + Argo CD Jenkins
架构 CI/CD 分离，各司其职 一体化
K8s 集成 Argo CD 原生 K8s 需 Kubernetes Plugin
配置语言 YAML（声明式） Groovy DSL（脚本式）
部署理念 GitOps（声明式） 脚本驱动（命令式）
回滚 git revert 即回滚 重新跑流水线

三、学习路线（分阶段，每阶段有验收）

阶段 0：理解 CI/CD 概念（0.5 天）

学习内容：

  • 通读本文档”关键概念速查”部分
  • 看官方文档理解 CI/CD 的定义和价值

动手任务：

  • 用自己的话写一段”CI/CD 是什么、解决什么问题、典型流程”

==验收标准==：能对面试官讲清楚——“CI 是持续集成，push 代码后自动编译测试打包；CD 是持续部署，自动把应用部署到运行环境；典型流程是 push→CI 构建镜像→推仓库→CD 部署到 K8s”。

面试深挖预演：

  • Q: CI 和 CD 的区别？A: CI 关注代码集成质量（编译测试），CD 关注交付到环境
  • Q: 为什么需要 CI/CD？A: 替代手工编译传包部署，减少人为错误，加快交付频率

阶段 1：GitLab CI 上手（1—2 天）

学习内容：

  • GitLab CI 架构：.gitlab-ci.yml（流水线定义）+ Runner（执行器）
  • 注册 Runner 到你的 GitLab 项目
  • .gitlab-ci.yml 语法：stages / jobs / script / artifacts / cache / only/except / rules
  • 变量管理：CI/CD Variables（项目级 vs Job 级）

动手任务：

  1. 在 GitLab 建一个项目（或用现有的）
  2. 注册一个 Runner（本地 docker runner 最方便）
  3. 写一个 .gitlab-ci.yml，包含两个 stage：build（构建 Docker 镜像）+ push（推到 Harbor）
  4. push 代码后看流水线自动跑起来

==验收标准==：

  • push 代码后 GitLab CI 自动触发，构建镜像并推 Harbor
  • 能讲清楚 stages 的执行顺序、artifacts 怎么传、Runner 是什么

面试深挖预演：

  • Q: Runner 是什么？有几种类型？A: 执行任务的组件，分 shared/specific/group，executor 有 shell/docker/docker-machine
  • Q: artifacts 和 cache 区别？A: artifacts 是 job 产物传给下游，cache 是加速重复依赖
  • Q: 怎么控制哪个分支触发？A: only/except/rules，新版推荐 rules

阶段 2：Argo CD 上手（2—3 天）

学习内容：

  • Argo CD 架构：controller / API server / repo server / application controller
  • ==GitOps 理念==（必背三句话，见上文）
  • 安装 Argo CD 到 K8s 集群
  • Argo CD Application 概念（source + destination + syncPolicy）
  • 同步机制：手动 sync vs 自动 auto-sync
  • Argo CD CLI 和 UI 操作
  • 多环境管理（dev/staging/prod 用不同目录或分支）

动手任务：

  1. 在实验集群安装 Argo CD（官方 Helm chart 或 manifest）
  2. 在 Git 仓库建一个 manifests/ 目录，放一个 Deployment + Service 的 YAML
  3. 创建 Argo CD Application，指向这个 Git 仓库
  4. 手动 sync，看应用部署到集群
  5. 修改 Git 里的镜像 tag，Argo CD 检测到 OutOfSync，自动 sync（开启 auto-sync）

==验收标准==：

  • 改 Git 里的部署清单，Argo CD 自动同步到集群
  • 能讲清楚 Argo CD 怎么发现变更、sync 的过程、auto-sync 和 selfHeal 的作用

面试深挖预演：

  • Q: Argo CD 怎么发现 Git 变更？A: repo server 周期拉取（默认 3 分钟）或 webhook 即时触发
  • Q: auto-sync 和 selfHeal 区别？A: auto-sync 是 OutOfSync 自动同步，selfHeal 是有人手动改集群也强行拉回 Git 声明状态
  • Q: 怎么回滚？A: git revert 提交，Argo CD 自动同步回旧版本；或 Argo CD UI 点 rollback 选历史版本
  • Q: GitOps 比传统 CI/CD 部署好在哪？A: 可审计（Git 历史即部署历史）、可回滚（git revert）、可观测（看 Git 知道集群状态）、声明式（不用写部署脚本）

阶段 3：最小闭环打通（1—2 天）

学习内容：

  • 把阶段 1（GitLab CI）和阶段 2（Argo CD）串起来
  • GitLab CI 构建镜像后，怎么更新 Git 仓库里的部署清单镜像 tag

动手任务：

  1. 在 .gitlab-ci.yml 加一个 update-manifest stage
  2. 这个 job 用 sed 或 yq 修改 manifests 里的镜像 tag，commit 回 Git 仓库
  3. Argo CD 检测到 manifests 变更，自动 sync 新镜像

==验收标准==（==最重要的一关==）：

  • push 业务代码 → GitLab CI 构建镜像推 Harbor → 自动更新 manifests → Argo CD 自动 sync → K8s 滚动更新
  • ==能完整讲清楚”push 代码后每一秒发生了什么、每个组件作用、数据流向”==
  • 这关过了，简历主项目骨架就成型了

面试深挖预演：

  • Q: GitLab CI 怎么更新 Argo CD 的 manifests？A: CI job 用 sed/yq 改镜像 tag，commit 回 Git，Argo CD 检测到自动 sync
  • Q: 为什么不让 Argo CD 直接拉镜像？A: GitOps 原则——Git 是唯一真源，Argo CD 只认 Git 声明，不主动拉镜像仓库
  • Q: 整个流程有哪些组件？数据怎么流？A: 开发者→GitLab→Runner→Harbor→Git manifests→Argo CD→K8s

阶段 4：亮点子模块（每个 1—2 天，三亮点全做）

4.1 Trivy 镜像安全扫描（1—2 天）

契合点：==契合软件工程（安全与管理方向）专业，差异化武器（安全+运维稀缺组合）==

学习内容：

  • Trivy 是什么：Aqua Security 开源的镜像漏洞扫描工具
  • 扫描 CVE 漏洞库
  • 在 GitLab CI 集成 Trivy
  • 扫描结果处理（有高危 CVE 阻断流水线）

动手任务：

  1. 在 .gitlab-ci.yml 加一个 scan stage（在 push 之后）
  2. 用 Trivy 官方 Docker 镜像扫描刚构建的镜像
  3. 配置阈值（有 CRITICAL 级别 CVE 则 job 失败，阻断流水线）
  4. 生成扫描报告（artifacts）

==验收标准==：

  • 故意构建一个有漏洞的镜像（用旧的基础镜像），Trivy 扫出 CRITICAL 并阻断流水线
  • 能讲镜像安全扫描的价值和实现

面试深挖预演：

  • Q: Trivy 扫什么？A: 镜像里的系统包漏洞（CVE）、应用依赖漏洞、配置错误
  • Q: 怎么决定阻断？A: 按 severity 阈值，CRITICAL 阻断，HIGH 告警
  • Q: 镜像安全为什么重要？A: 镜像是部署的源头，带漏洞部署 = 把漏洞带进生产

4.2 Argo Rollouts 金丝雀发布（1—2 天）

契合点：==关联 K8s 控制器学习==。Argo Rollouts 是 K8s 的自定义控制器（CRD + Controller），扩展了原生 Deployment 不支持的金丝雀/蓝绿发布。

学习内容：

  • 原生 Deployment 的局限：只支持滚动更新（RollingUpdate），不支持精细金丝雀
  • Argo Rollouts 是什么：K8s CRD，用 Rollout 资源替代 Deployment，支持金丝雀/蓝绿
  • 金丝雀发布原理：先切 10% 流量→观察→再 30%→再 100%
  • Rollout 资源定义（spec.strategy.canary）
  • 流量切分机制（需要 Ingress/Nginx 或 Service Mesh 配合）

动手任务：

  1. 安装 Argo Rollouts controller 到集群
  2. 把之前的 Deployment 改成 Rollout 资源
  3. 配置金丝雀策略：先 10%→暂停→手动/自动推进→30%→100%
  4. 触发一次发布，观察流量切分

==验收标准==：

  • 能用 Rollout 做一次金丝雀发布，流量从 10%→30%→100%
  • 能讲清楚原生 Deployment 为什么不行、Rollouts 怎么扩展的

面试深挖预演：

  • Q: 原生 Deployment 为什么不能金丝雀？A: RollingUpdate 只支持按比例替换 Pod，不控制流量比例
  • Q: Argo Rollouts 是什么？A: K8s CRD + 自定义控制器，替代 Deployment，支持金丝雀/蓝绿
  • Q: 金丝雀和蓝绿区别？A: 金丝雀是渐进切流量，蓝绿是两套环境一次性切换
  • Q: 流量怎么切？A: 用 Nginx Ingress 的 canary 注解或 Service Mesh（Istio）权重

4.3 Prometheus + AlertManager 监控告警闭环（1—2 天）

契合点：==沃趣 QFusion 集成过 Prometheus，有使用者经验，现在转搭建者==

学习内容：

  • Prometheus 架构：==Pull 模型==（服务器主动拉指标，不是 push）
  • ServiceMonitor（Prometheus Operator 的 CRD，定义拉取目标）
  • 告警规则（PromQL 写条件）
  • AlertManager：告警路由、分组、抑制（inhibit）、静默（silence）
  • 监控告警闭环：指标采集→告警规则触发→AlertManager 路由→通知（钉钉/邮件）

动手任务：

  1. 安装 Prometheus Operator（kube-prometheus-stack）
  2. 给你的应用加一个 metrics 接口（或用示例 exporter）
  3. 写 ServiceMonitor 让 Prometheus 拉指标
  4. 写告警规则：Pod 重启次数 > 3 或 镜像部署失败 告警
  5. 配 AlertManager 路由到钉钉 webhook

==验收标准==：

  • 故意触发一次故障（删 Pod 让它重启），Prometheus 采集到指标，告警触发，钉钉收到通知
  • 能讲 Pull 模型、ServiceMonitor、告警闭环

面试深挖预演：

  • Q: Prometheus 为什么用 Pull 不用 Push？A: Pull 主动可控、易调试、服务发现、不丢数据
  • Q: ServiceMonitor 是什么？A: Prometheus Operator 的 CRD，声明式定义拉取目标，不用手改 prometheus.yml
  • Q: AlertManager 的抑制（inhibit）和静默（silence）区别？A: 抑制是 A 告警来了自动抑制 B（比如机房断电抑制单机告警），静默是手动临时关告警

六、面试话术集（CI/CD 部分）

选型话术

“选型时对比过 Jenkins 和 GitLab CI + Argo CD。考虑到 K8s 原生集成和 GitOps 理念选了 Argo CD——Git 是唯一真源，声明式部署可审计可回滚。Jenkins 的基本概念和 Pipeline 也了解。”

架构话术

“我的项目用 GitLab CI 做 CI（编译、测试、构建镜像、推 Harbor），Argo CD 做 CD（监听 Git 仓库的 K8s 部署清单，自动同步到集群）。两者通过 Git 仓库的 manifests 目录衔接——GitLab CI 构建完镜像后更新 manifests 里的镜像 tag，Argo CD 检测到变更自动 sync。”

GitOps 话术

“我用的是 GitOps 理念，核心是三句话：Git 是唯一真源，集群状态由 Git 仓库的声明决定；声明式，我声明’应该是什么样’Argo CD 保证达到；可回滚，git revert 即回滚到历史版本。比传统脚本式部署好在可审计、可回滚、可观测。”

亮点话术

“项目还集成了三个亮点：Trivy 在 CI 阶段扫镜像 CVE 漏洞，有 CRITICAL 阻断流水线，契合我安全专业方向；Argo Rollouts 做金丝雀发布，10%→30%→100% 渐进切流量，原生 Deployment 不支持；Prometheus+AlertManager 做监控告警闭环，部署失败能告警到钉钉。”

七、风险提醒

  1. ==Argo CD 概念新==，GitOps 三句话必须张口就来，不然面试一深挖就露
  2. ==不要只搭 demo 不懂原理==。每个组件的作用、数据流向、为什么这么设计，都要能讲
  3. ==最小闭环（阶段 3）是核心==，三亮点是锦上添花。时间紧先保证最小闭环
  4. Trivy 契合安全专业是差异化武器，==优先做==
  5. 不要做完就忘。能讲清楚”push 代码后每一秒发生了什么”才算掌握
  6. 面试官会问”你遇到什么问题”——记录学习过程中踩的坑（Runner 注册失败、Argo CD sync 失败、Rollout 流量切不动），这些是真经历

八、学习资源建议

  • ==官方文档优先==：GitLab CI Docs、Argo CD Docs、Argo Rollouts Docs、Prometheus Docs
  • 动手实验 > 看视频 > 读博客
  • 遇到问题先看官方文档的 Troubleshooting，再搜 Stack Overflow
  • 每个阶段做完后，用自己的话复述一遍（能复述 = 掌握）

九、验收总清单（全部打勾才算出师）

  • 能讲 CI/CD 是什么、解决什么问题
  • 能写 .gitlab-ci.yml，push 后自动构建镜像推 Harbor
  • 能装 Argo CD，改 Git manifests 后自动 sync 到集群
  • 能讲 GitOps 三句话
  • 能打通最小闭环（push→CI→manifests→Argo CD→K8s）
  • 能讲”push 代码后每一秒发生了什么”
  • Trivy 扫镜像有 CVE 阻断流水线
  • Argo Rollouts 做金丝雀 10%→30%→100%
  • Prometheus+AlertManager 监控告警闭环
  • 能讲选型理由（为什么 GitLab CI+Argo CD 而非 Jenkins）
  • 简历 bullet 能扛”你用它做过什么/遇到什么问题”这一问
