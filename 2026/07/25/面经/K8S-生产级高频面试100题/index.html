1-20 K8s 核心基础

1. 什么是 Kubernetes？它解决了什么问题？

#k8s
🔗 CICD 监控 操作系统 中间件 自动化

📝 标准答案
Kubernetes（简称 K8s）是一个开源的容器编排平台，用于自动化管理容器化应用。
它可以实现应用的自动部署、扩缩容、服务发现、负载均衡、故障恢复以及滚动更新等能力。
简单来说，Docker 解决的是“如何运行容器”，而 Kubernetes 解决的是“如何大规模管理容器”。

2. Pod 是什么？为什么 Kubernetes 不直接运行容器？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
Pod 是 Kubernetes 中最小的调度单位，也是 Kubernetes 实际管理和运行应用的基本单位。
一个 Pod 中可以包含：一个容器或多个紧密协作的容器Pod 内的容器会共享：网络命名空间（同一个 IP）存储卷localhost 通信Kubernetes 不直接管理容器，而是通过 Pod 来管理容器，主要有以下几个原道因：容器需要更高层级的抽象某些业务场景需要多个容器协同工作Kubernetes 需要统一管理容器生命周期Pod 更适合作为调度与编排单位例如：一个 nginx 容器负责业务，另一个 sidecar 容器负责日志采集，它们可以放到同一个 Pod 中，通过 localhost 通信。
生产环境中，Pod 通常不会单独创建，而是由：DeploymentStatefulSetDaemonSet等控制器进行管理。

是否理解 Pod 是 K8s 的最小调度单位是否理解 Pod 与容器的关系是否理解“共享网络”和“sidecar”概念是否知道 Kubernetes 调度的是 Pod 而不是容器是否具备一定生产环境经验，而不是只会使用 Docker

3. Pod 的生命周期有哪些阶段？

#k8s
🔗 CICD 监控 操作系统 中间件 自动化

📝 标准答案
Pod 生命周期常见阶段包括：Pending、Running、Succeeded、Failed、Unknown。
Pending：Pod 已创建，但还未成功运行，常见原因有调度失败、资源不足、镜像拉取中、PVC 未绑定等。
Running：Pod 已成功运行，但不一定代表业务正常，还需要结合 Probe 和日志判断。
Succeeded：Pod 正常执行完成，通常出现在 Job 或 CronJob 场景。
Failed：Pod 执行失败，例如程序异常退出。
Unknown：无法获取 Pod 状态，通常是节点或 kubelet 异常导致。

💡 面试官考察点
是否理解 Pod 生命周期是否知道 Running 不一定代表服务正常是否具备基础排障能力是否真正使用过 Kubernetes 而不是只会背概念

Pending：Pod 已创建，但还未成功运行。
Running：Pod 已运行，但不一定业务正常。

7. Deployment 的作用是什么？

#k8s

Deployment 是 Kubernetes 中用于管理无状态应用的控制器，主要负责 Pod 的部署、扩缩容、滚动更新、自愈和回滚。

15. Liveness Probe 与 Readiness Probe 的区别是什么？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
Liveness Probe 用于判断容器是否存活，Readiness Probe 用于判断服务是否已经可以接收流量。
区别如下：Liveness Probe 失败：Kubernetes 会重启容器。
Readiness Probe 失败：Pod 会从 Service 的后端列表中移除，但不会重启容器。
简单理解：Liveness：程序还活着吗？
Readiness：程序现在能对外提供服务吗？
例如：Java 应用启动较慢时，可能容器已经运行，但服务还没完全启动，此时 Readiness 可能失败。
如果 Liveness 配置不合理，可能会导致 Pod 被不断重启，出现 CrashLoopBackOff。

💡 面试官考察点
是否理解 Probe 的核心作用是否知道两种 Probe 的区别是否真正处理过 Probe 导致的问题是否理解“Running 不等于服务可用”

18. resource request 与 limit 的区别是什么？

#k8s
🔗 CICD 监控 操作系统 中间件 数据库

📝 标准答案
request 和 limit 都用于限制 Pod 的资源使用，但作用不同。
request：Pod 调度时所需的最小资源，Scheduler 会根据 request 进行节点调度。

19. 什么是污点（Taint）与容忍（Toleration）？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
Taint（污点）用于让节点拒绝 Pod 调度，Toleration（容忍）用于让 Pod 可以忽略这些污点并继续调度。
简单理解：Taint：节点说“普通 Pod 不要过来”Toleration：Pod 说“我可以容忍这个限制”常见场景：Kubernetes 的 Master 节点默认会带有污点，因此普通业务 Pod 不会调度到 Master 节点。
例如：node-role.kubernetes.io/control-plane:NoSchedule如果某个 Pod 想调度到该节点，就需要配置对应的 Toleration。
Taint 常见效果包括：NoSchedule：不允许调度
PreferNoSchedule：尽量不调度
NoExecute：驱逐已有 Pod

💡 面试官考察点
是否理解 Kubernetes 调度机制是否知道 Master 默认为什么不跑业务 Pod是否理解 Taint 与 Toleration 的配合关系是否真正做过节点隔离或专用节点调度

20. 什么是亲和性（Affinity）与反亲和性（Anti-Affinity）？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
Affinity（亲和性）用于让 Pod 倾向调度到某些节点，Anti-Affinity（反亲和性）用于避免 Pod 调度到某些节点。
它们本质上都是 Kubernetes 的高级调度策略。
常见场景：Affinity：让业务 Pod 调度到 SSD、高性能节点
Anti-Affinity：让多个副本分散到不同节点，提高高可用例如：3 个 nginx Pod 分散到 3 台节点这样即使某个节点故障，也不会导致所有 Pod 同时不可用。
Affinity 常见类型包括：nodeAffinity：节点亲和性
podAffinity：Pod 亲和性
podAntiAffinity：Pod 反亲和性

💡 面试官考察点
是否理解 Kubernetes 调度策略是否真正做过高可用部署是否知道反亲和性在生产环境的重要性是否理解节点级与 Pod 级亲和性的区别

21. Pod 一直 CrashLoopBackOff 如何排查？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
Pod 一直 CrashLoopBackOff，说明容器启动后反复异常退出，Kubernetes 不断重启它，并进入退避重试。
排查思路一般是：先看 Pod 事件，确认退出原因：kubectl describe pod «pod-name» -n «namespace»
重点看 Events、Exit Code、Reason、Probe 失败信息。

61. PV 与 PVC 的关系是什么？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
PV（PersistentVolume）和 PVC（PersistentVolumeClaim）是 Kubernetes 中用于实现持久化存储的核心资源。
PV 可以理解为集群中的实际存储资源，例如 NFS、Ceph、云盘等；
PVC 则是应用对存储资源的申请。
简单来说，PVC 提需求，PV 提供资源。
当 Pod 创建时，并不是直接使用 PV，而是先绑定 PVC，再由 PVC 绑定到合适的 PV。
这样可以实现存储与业务解耦，开发人员不需要关心底层具体是什么存储。
例如，一个 Pod 申请 “10G、支持 ReadWriteOnce 的存储”，Kubernetes 会道自动寻找符合条件的 PV 进行绑定。
如果配置了 StorageClass，还可以自动动态创建 PV，而不需要提前手工准备。
生产环境中，Deployment 通常用于无状态服务，而 StatefulSet、数据库、中间件等有状态应用则大量依赖 PVC 实现数据持久化。

62. StorageClass 的作用是什么？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案

StorageClass 本质上定义的是“如何创建存储”，其中会指定具体的存储插件、参数、回收策略等。
例如可以基于NFS、Ceph、云厂商云盘等不同后端动态创建存储。
整个流程通常是：PVC -> StorageClass -> 动态创建 PV -> Pod 挂载使用生产环境中，大多数 Kubernetes 集群都会配置默认 StorageClass，这样业务只需要创建 PVC，就能自动获得存储资源，大幅提升运维效率。

66. Ceph 与 NFS 的区别是什么？

68. ConfigMap 挂载更新机制是什么？

📝 标准答案

简单来说，Jenkins 动态 Agent 就是“有任务时在 K8s 里临时拉起构建 Pod，任务完成后自动销毁”。

87. Kubernetes 为什么需要多 Master？

#k8s
🔗 CICD 监控 操作系统 中间件 自动化

📝 标准答案
Kubernetes 需要多 Master，核心原因是避免控制面出现单点故障。
因为 Master 节点上运行着 kube-apiserver、controller-manager、scheduler、etcd 等核心组件，一旦单 Master 宕机，整个集群虽然已有业务 Pod可能还能继续运行，但集群将无法进行新的调度、扩缩容、发布和状态管理。
多 Master 部署后，即使某个 Master 节点故障，其他 Master 仍然可以继续提供 API 服务和集群控制能力，从而保证 Kubernetes 控制面的高可用。
生产环境中，通常会使用：3 Master或 5 Master架构，并在前面通过负载均衡提供统一的 kube-apiserver 访问入口。
另外，etcd 本身也是分布式组件，多 Master 通常也意味着 etcd 多节点部署，这样才能保证 Kubernetes 核心数据不会因为单节点故障而丢失。
简单来说：单 Master 适合学习测试环境，而真正生产环境基本都会做多 Master 高可用。

92. 什么是 SRE？它与传统运维有什么区别？

#k8s
🔗 CICD 自动化 监控

📝 标准答案
SRE（Site Reliability Engineer，站点可靠性工程）本质上是一种以软件工程方式解决运维问题的理念，它的核心目标是提升系统稳定性、可用性和可扩展性。
传统运维更多偏向人工操作，例如：手工部署手工排障手工巡检人工变更而 SRE 更强调：自动化平台化工程化稳定性治理例如传统运维可能是“出了问题去修”，而 SRE 更关注“如何通过监控、自动化、容量规划、告警治理、可观测性等方式，提前降低故障发生概率”。
SRE 通常会重点建设：CI/CD自动化运维平台监控告警体系可观测性体系容量与稳定性分析故障应急与复盘机制另外，SRE 非常强调 SLI、SLO、SLA 等稳定性指标，希望通过数据衡量系统可靠性，而不是仅靠经验判断。
简单来说：传统运维更偏“人肉维护”，SRE 更偏“工程化稳定性体系建设”。

💡 面试官考察点
主要考察你是否理解 SRE 不只是“高级运维”，而是一种工程化理念，是否具备自动化、平台化、稳定性治理思维，以及是否理解传原统运维向云原生、DevOps、SRE 转型的发展方向。

93. 如何理解稳定性治理？

#k8s
🔗 监控 CICD 自动化

📝 标准答案
稳定性治理，本质上是通过技术、流程和体系化手段，持续降低故障发生概率，并提升系统在异常情况下的恢复能力。
它并不只是“系统别挂”，而是从架构、监控、发布、容量、告警、应急、复盘等多个层面，长期建设系统稳定性。
例如一个成熟的稳定性治理体系，通常会包含：高可用架构多副本与容灾监控告警可观测性灰度发布限流熔断自动化运维故障复盘容量规划真正的稳定性治理，更强调“提前预防”，而不是故障发生后再救火。
例如：通过监控发现异常趋势通过 SLO 衡量服务质量通过灰度发布降低变更风险通过演练验证容灾能力通过复盘避免同类事故再次发生在 Kubernetes 和云原生场景下，稳定性治理通常还会结合：HPA 自动扩缩容Pod 反亲和性多 AZ 部署服务熔断降级Trace + Metrics + Logs 联动分析简单来说：稳定性治理不是某一个工具，而是一整套“保证系统长期稳定运行”的工程体系。

💡 面试官考察点
主要考察你是否具备整体稳定性思维，是否理解高可用、监控、发布、容灾、复盘之间的关系，以及是否能够从“运维执行”上升到“稳定性建设与治理”的层面。

94. 如何设计灰度发布与回滚方案？

#k8s
🔗 CICD 监控 操作系统 中间件 自动化

📝 标准答案
设计灰度发布与回滚方案，核心目标是降低发布维风险，让新版本先影响少量用户或少量流量，确认稳定后再逐步扩大范围。
如果发布过程中出现异常，可以快速切回旧版本，避免故障扩大。
在 Kubernetes 中，最基础的方式是使用 Deployment 的滚动更新能力，通过控制 maxSurge、maxUnavailable来逐步替换 Pod，并结合 Readiness Probe 确保新 Pod 真正可用后再接入流量。
但这种方式只能做到副本级滚动，灰度能力相对有限。
如果要做更精细的灰度，通常会结合 Ingress、Service Mesh 或网关能力实现流量比例控制。
例如先让 5% 流量进入新版本，观察错误率、延云迟、日志和业务指标，如果没有问题，再逐步提升到 20%、50%、100%。
在这个过程中，Prometheus、日志平台和 Trace 系统都要参与验证。
回滚方案也必须提前设计好。
简单场景可以使用 kubectl rollout undo deployment/«name»
回滚到上一个版本；
更规范的做法是镜像 tag、配置文件、数据库变更都要可追溯，确保能快速恢复到稳定版本。
需要特别注意，数据库变更要尽量保持向前兼容，否则应用回滚了，数据库回不去，仍然可能导致事故。
生产环境中，灰度发布不是只看 Pod 是否 Running，而是要看接口成功率、响应时间、错误日志、核心业务指标是否正常。
真正成熟的发布体系应该做到：小流量验证、自动健康检查、异常自动中止、人工确认放量、失败快速回滚。

💡 面试官考察点
主要考察你是否具备生产发布风险控制意识，是否理解 Kubernetes 滚动更新、Readiness Probe、Ingress/网关灰度、监控验证和回滚机制，也会关注你是否知道数据库变更、配置变更和镜像版本管理对回滚的影响。

95. 如何避免 Kubernetes 集群发生雪崩？

#k8s
🔗 CICD 监控 操作系统 中间件 自动化 数据库

📝 标准答案
避免 Kubernetes 集群发生雪崩，核心是不要让单点故障、资源耗尽、错误发布或流量突增扩散成全局故障。
它不是靠某一个配置解决，而是要从资源隔离、弹性扩缩容、发布控制、限流降级、监控告警和故障隔离几个方面共同设计。
在资源层面，要合理配置 Pod 的 request 和 limit，避免某个应用占满节点资源，导致其他 Pod 被驱逐或 OOM。
不同业务、不同环境可以通过 namespace、ResourceQuota、LimitRange 做资源隔离，关键业务还可以使用独立节点池，避免被普通业务影响。
在应用层面，服务要多副本部署，并配置合理的 Readiness Probe 和 Liveness Probe。
尤其要避免 Probe 配置过于激进，否则高峰期应用响应变慢时，可能会导致大量 Pod 被同时摘除或重启，反而加剧故障。
在流量层面，要有超时、重试、限流、熔断和降级机制。
特别是重试一定不能无限重试，否则下游服务异常时，上游持续放大请求量，很容易造成连锁故障。
在发布层面，要使用滚动更新、灰度发布和快速回滚，避免一次性把有问题的版本推到所有实例。
发布后不能只看Pod 是否 Running，还要结合错误率、延迟、日志和核心业务指标判断是否健康。
在平台层面，要做好 Prometheus 监控、日志采集、Trace 链路追踪和告警分级，提前发现资源耗尽、错误率升高、Pod 大量重启、节点 NotReady、CoreDNS 异常等风险。
简单来说，避免雪崩的关键是：资源隔离、防止故障扩散、控制流量放大、降低发布风险，并通过可观测性及时发现和止损。

💡 面试官考察点
主要考察你是否具备生产稳定性思维，是否理解 Kubernetes 资源隔离、探针配置、灰度发布、限流熔断、监控告警之间的关系，以及是否能从单点排障上升到系统性防雪崩设计。

96. 如何从零设计一原套企业级 Kubernetes 平台？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
从零设计一套企业级 Kubernetes 平台，不能只理解为“搭一个 K8s 集群”，而是要围绕企业应用交付、资源管理、稳定性、安全、可观测性和运维效率来整体设计。
首先是集群架构层面，生产环境通常会采用多 Master 高可用架构，kube-apiserver 前面接负载均衡，etcd 使用 3节点或 5 节点集群并定期备份。
Worker 节点可以按业务类型、环境或资源规格划分节点池，例如普通业务节点、数据库节点、GPU 节点、CI 构建节点等。
其次是网络与入口层面，需要选择合适的 CNI 插件，例如 Calico、Cilium，并规划 Pod 网段、Service 网段、网络策略和跨节点通信方式。
服务入口通常使用 Ingress Controller、Gateway API 或云厂商 LB，实现域名路由、HTTPS、灰度发布和统一流量治理。
再往上是应用交付体系，企业级平台一定要配套 CI/CD，例如 Jenkins、GitLab CI 或 ArgoCD。
镜像统一推送到Harbor，部署配置通过 Helm、Kustomize 或 GitOps 管理，实现开发、测试、预发、生产多环境隔离和标准化发布。
然后是存储、监控和日志体系。
存储层要根据业务选择云盘、Ceph、NFS 或 Local PV；
监控层使用 Prometheus、Grafana、Alertmanager；
日志层使用 EFK、OpenSearch 或 Loki；

97. 如何设计生产级 CI/CD 平台？

#k8s
🔗 CICD 自动化

📝 标准答案
设计生产级 CI/CD 平台，核心目标不是“能自动发布”就行，而是要让代码从提交、构建、测试、制品管理、部署、验证、审批、回滚形成一套稳定、可追溯、可管控的交付体系。
在 CI 阶段，通常会从 Git 仓库触发流水线，完成代码拉取、依赖安装、单元测试、代码扫描、编译打包和镜像构建。
构建完成后，镜像会推送到 Harbor 这类私有镜像仓库，并使用明确的镜像 tag，例如 commit id、构建时间或版本号，保证每一次发布都可以追踪来源。
在 CD 阶段，需要根据不同环境进行部署，例如 dev、test、uat、prod。
不同环境应该使用独立的 namespace、配置文件、密钥、资源配额和发布权限。
部署方式可以使用 Kubernetes YAML、Helm、Kustomize 或 GitOps。
生产环境发布通常还要增加审批、灰度发布、健康检查和回滚机制，不能简单地 kubectl apply
完就结束。
生产级 CI/CD 平台还必须关注安全和稳定性，例如控制 kubeconfig 权限、限制生产发布权限、保护 Secret、做镜像漏洞扫描、保留发布记录、记录操作审计，并在发布后自动检查 Pod Ready 状态、接口健康、错误率、响应时间等指标。
如果验证失败，需要能快速回滚到上一个稳定版本。
真正成熟的 CI/CD 平台，应该做到流程标准化、环境隔离、制品可追溯、发布可审计、失败可回滚，并能和监控、告警、日志系统联动，确保发布不仅“发得出去”，还要“发得稳、出问题能快速止损”。

💡 面试官考察点
主要考察你是否真正做过生产发布平台，是否理解 CI 和 CD 的职责边界，是否具备多环境管理、镜像仓库、Kubernetes 发布、健康检查、灰度回滚、权限控制和发布审计等生产级交付经验。

98. 如何设计 Kubernetes 多租户体系？

#k8s
🔗 CICD 监控 操作系统 中间件

📝 标准答案
设计 Kubernetes 多租户体系，核心是让多个团队、项目或业务线可以共享同一套集群资源，但彼此之间在权限、资源、网络、数据和运维边界上相互隔离，避免一个租户影响另一个租户。
最基础的隔离方式是 namespace。
通常会为不同项目、不同环境、不同团队划分独立 namespace，并结合 RBAC控制用户只能访问自己的资源，避免误删、误改其他团队的应用。
资源层面，需要通过 ResourceQuota 和 LimitRange 限制每个租户可使用的 CPU、内存、Pod 数量、PVC 数量等资源，防止某个租户无限创建资源，把整个集群打满。
网络层面，可以通过 NetworkPolicy 控制 namespace 之间、Pod 之间的访问关系，默认不允许随意互通，只开放必要端口和服务，避免东西向流量失控。
安全层面，还需要控制 Secret 访问、镜像仓库权限、ServiceAccount 权限、Pod 安全策略、准入控制和审计日志，防止租户通过高权限 Pod 影响宿主机或其他业务。
生产环境中，如果租户之间安全要求非常高，单纯 namespace 隔离是不够的，可能需要独立集群、独立节点池，或者使用虚拟集群方案。
简单来说，多租户体系要根据隔离强度分层设计：普通项目可以 namespace 隔离，核心业务可以独立节点池，强安全场景最好独立集群。

💡 面试官考察点
主要考察你是否理解 Kubernetes 多租户不是简单分 namespace，而是要同时考虑权限隔离、资源隔离、网络隔离、安全隔离和审计能力，也会关注你是否具备企业级平台治理和资源管理经验。

99. 如何设计云原生可观测性平台？

#k8s
🔗 CICD 监控 操作系统 中间件 自动化

📝 标准答案
设计云原生可观测性平台，核心目标是统一采集、存储、分析 Metrics、Logs、Traces 三类数据，让运维和研发能够快速发现问题、定位问题、复盘问题，而不是只做几个监控大盘。
在 Kubernetes 环境中，Metrics 通常使用 Prometheus 采集，Grafana 展示，Alertmanager 负责告警；
Logs 可以使用 Loki、EFK、OpenSearch 等方案统一采集和检索；
Traces 则可以通过 OpenTelemetry 接入应用，再发送到Jaeger 或 Tempo。

平台设计时还要考虑多集群、多环境、多租户场景。
不同业务、namespace、集群的数据要能够区分，权限要能隔离，告警要能按团队分发，日志和指标也要有合理的保留周期，避免存储成本失控。
真正生产级的可观测性平台，不只是把数据采进来，更要做到告警降噪、链路关联、故障定位、容量分析和稳定性趋势分析。
它最终服务的不是“看图”，而是帮助团队更快恢复故障、更少发生故障，并持续提升系统稳定性。

💡 面试官考察点
