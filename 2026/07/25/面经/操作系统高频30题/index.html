1-8 Linux基础原理

1. Linux 中用户态与内核态的区别是什么？

#os
🔗 数据库 中间件 K8S

[!quote]- 标准答案
Linux 为了保证系统安全，将运行环境分为用户态和内核态。
用户程序通常运行在用户态，例如 Java、Nginx、MySQL 等应用。
用户态权限较低，不能直接访问硬件资源。
内核态则拥有最高权限，可以直接操作 CPU、内存、磁盘和网络设备。
当应用需要读取文件、访问网络或申请内存时，会通过系统调用进入内核态执行，完成后再返回用户态。
简单来说，用户态负责业务逻辑，内核态负责系统资源管理。

[!tip]- 面试官考察点
考察是否理解操作系统权限隔离机制，以及系统调用的本质。

2. 什么是进程？什么是线程？

#os
🔗 数据库 K8S

[!quote]- 标准答案
进程是操作系统进行资源分配的基本单位，每个进程拥有独立的内存空间。
线程是进程内部的执行单元，一个进程可以包含多个线程，多个线程共享进程的内存和资源。
例如一个 Java 应用启动后是一个进程，而其中的业务线程、GC线程、定时任务线程都属于该进程内部的线程。
简单来说：进程负责资源管理，线程负责执行任务。

[!tip]- 面试官考察点
考察是否理解进程和线程的基本概念。

3. 进程与线程的区别是什么？

#os
🔗 数据库 K8S

[!quote]- 标准答案
进程拥有独立的地址空间和系统资源，而线程共享所属进程的资源。
进程之间相互隔离，一个进程崩溃通常不会直接影响其他进程；
线程之间共享内存，一个线程出现问题可能导致整个进程异常。
创建进程的开销通常大于创建线程，因为进程需要分配独立资源。
因此现代应用通常采用多线程模型提高并发处理能力。

[!tip]- 面试官考察点
考察是否理解资源隔离、内存共享以及并发模型。

4. 什么是僵尸进程？如何处理？

#os
🔗 数据库 K8S

[!quote]- 标准答案
僵尸进程是已经执行结束，但父进程还没有回收其退出状态的进程。
此时进程本身已经不再运行，但仍然保留部分进程信息，因此会占用进程表资源。
少量僵尸进程问题不大，但大量僵尸进程可能导致系统无法创建新进程。
处理方式通常是让父进程回收子进程，或者重启父进程。
如果父进程异常，也可以直接结束父进程，让系统的 init 进程接管并完成回收。

[!tip]- 面试官考察点
考察是否理解 Linux 进程生命周期和资源回收机制。

5. 什么是孤儿进程？

#os
🔗 数据库 K8S

[!quote]- 标准答案
孤儿进程是指父进程已经退出，但子进程仍然在运行的进程。
当父进程结束后，Linux 会自动让 PID 为 1 的 init（或 systemd）进程接管这些子进程。
孤儿进程本身并不是异常现象，也不会像僵尸进程一样占用系统资源。
很多后台服务实际上都会经历成为孤儿进程再被 systemd 接管的过程。

[!tip]- 面试官考察点
考察是否理解孤儿进程与僵尸进程的区别。

6. 什么是上下文切换？

#os
🔗 数据库 K8S

[!quote]- 标准答案
上下文切换是指 CPU 从当前任务切换到另一个任务时，保存当前运行状态并恢复新任务运行状态的过程。
由于 CPU 同一时刻只能执行一个任务，因此多个进程或线程需要轮流使用 CPU。
每次切换都会产生额外开销，包括寄存器保存、内存映射切换等操作。
如果系统线程过多或频繁抢占 CPU，就会导致上下文切换次数过高，从而影响系统性能。

[!tip]- 面试官考察点
考察是否理解多任务调度机制以及性能损耗来源。

7. 什么是系统调用（System Call）？

#os
🔗 数据库 K8S 中间件

[!quote]- 标准答案
系统调用是应用程序请求操作系统内核提供服务的一种机制。
由于用户态程序不能直接访问硬件资源，因此当程序需要读取文件、创建进程、访问网络或申请内存时，都必须通过系统调用进入内核态执行。
常见系统调用包括：openreadwriteforksocket系统调用本质上就是用户态与内核态之间的桥梁。

[!tip]- 面试官考察点
考察是否理解应用程序与操作系统之间的交互机制。

8. Linux 中 CPU Load 与 CPU Usage 的区别是什么？

#os
🔗 数据库 K8S

[!quote]- 标准答案
CPU Usage 表示 CPU 实际使用率，即 CPU 当前有多少时间在执行任务。
CPU Load（负载）表示系统中正在运行和等待 CPU 运行的任务数量。
两者并不完全等价。
例如 CPU 使用率只有 30%，但大量进程因为磁盘 IO 阻塞而处于等待状态，此时 Load 仍然可能很高。
生产环境中很多故障表现为：CPU Usage 不高，但 Load Average 持续升高。
因此排查性能问题时，不能只看 CPU 使用率，还需要结合 Load、IO、内存等指标综合分析。

[!tip]- 面试官考察点
考察是否真正理解 Linux 性能指标，以及是否具备基础性能分析能力。

9-15 CPU与内存

9. CPU 使用率过高如何排查？

#os
🔗 数据库 K8S

[!quote]- 标准答案
当 CPU 使用率过高时，首先要确认是哪个进程占用了大量 CPU 资源。
通常会先通过 top 或 htop 查看高 CPU 进程，再结合 ps 查看具体进程信息。
如果是 Java 程序，还需要结合jstack 分析线程状态。
生产环境中常见原因包括死循环、线程异常、频繁 GC、高并发请求以及程序 Bug。
排查思路通常是：先找进程，再找线程，最后定位具体代码。

[!tip]- 面试官考察点
考察是否具备 Linux 性能问题定位能力，以及 Java 应用排障经验。

10. Load Average 过高如何排查？

#os
🔗 数据库 K8S 中间件

[!quote]- 标准答案
Load Average 表示系统中正在运行和等待运行的任务数量。
当 Load 持续升高时，并不一定是 CPU 出现问题，还可能是磁盘 IO、网络 IO 或锁竞争导致大量进程阻塞。
排查时通常会结合 CPU、内存、磁盘和进程状态一起分析。
如果 CPU 很低但 Load 很高，往往说明大量进程处于等待状态，而不是正在执行。
因此 Load 高不等于 CPU 高，需要综合判断系统资运源情况。

[!tip]- 面试官考察点
考察是否真正理解 Load生 的含义，而不是简单认为 Load 就是 CPU 使用率。

11. Linux 内存是如何管理的？

#os
🔗 数据库 K8S

[!quote]- 标准答案
Linux 会尽可能利用空闲内存提高系统性能。
除了应用程序占用的内存外，系统还会将部分内存用于 Buffer 和 Cache，用于加速磁盘读写。
因此在 Linux 中看到内存使用率很高并不一定是异常现象，因为很多内存实际上可以被系统随时回收。
真正需要关注的是 Available 内存是否持续下降，以及是否出现频繁 Swap 或 OOM。
生产环境中判断内存是否紧张，通常不会只看 Used，而会重点关注 Available。

[!tip]- 面试官考察点
考察是否理解 Linux 内存管理机制，以及为什么 Linux 看起来总是“内存快满了”。

12. 什么是 Buffer 与 Cache？

#os
🔗 数据库 K8S

[!quote]- 标准答案
Buffer 和 Cache 都是 Linux 为了提升 IO 性能而使用的内存区域。
Buffer 主要用于缓存磁盘块数据，例如文件系统元数据；
Cache 主要用于缓存文件内容。
当应用读取文件时，如果数据已经存在于 Cache 中，就不需要再次访问磁盘，从而提高读取速度。
因此很多服务器运行一段时间后，Cache 会越来越大，这通常属于正常现象。
当应用需要内存时，Linux 会自动释放部分 Buffer 和 Cache。

[!tip]- 面试官考察点
考察是否理解 Linux 内存使用情况，以及 Buffer、Cache 的作用。

13. 什么是 Swap？生产环境为什么经常关闭？

#os
🔗 K8S CICD 监控 中间件 数据库

[!quote]- 标准答案
Swap 是 Linux 的交换分区或交换文件，当物理内存不足时，系统会将部分内存数据暂时写入磁盘。
这样虽然能够缓解内存压力，但磁盘速度远低于内存，因此会导致系统性能明显下降。
对于数据库、Java 应用和 Kubernetes 节点来说，频繁使用 Swap 往往意味着性能问题。
因此很多生产环境会关闭 Swap，让内存不足时直接触发 OOM，而不是让系统长期处于严重性能下降状态。
例如 Kubernetes 默认就要求关闭 Swap。

[!tip]- 面试官考察点
考察是否理解 Swap 的工作机制，以及生产环境为什么普遍关闭 Swap。

14. OOM Killer 的工作原理是什么？

#os
🔗 数据库 中间件 K8S

[!quote]- 标准答案
OOM（Out Of Memory）表示系统内存耗尽。
当 Linux 无法继续分配内存时，会触发 OOM Killer 机制，自动选择部分进程进行终止，从而释放内存资源。
选择哪个进程被杀死，并不是随机的，而是根据进程占用资源情况计算 OOM Score。
通常占用内存较大、优先级较低的进程更容易被终止。
因此线上有时会看到 Java、MySQL 等进程生突然消失，实际上可能就是被 OOM Killer 杀掉了。

[!tip]- 面试官考察点
考察是否理解 Linux 内存保护机制，以及 OOM 的处理逻辑。

15. Linux 服务器发生 OOM 如何排查？

#os
🔗 监控 K8S 数据库

[!quote]- 标准答案
发生 OOM 后，首先要确认是否真的触发了 OOM Killer。
通常会查看系统日志：dmesg -T或者：journalctl -k确认是否存在 Out of memory 或 Kill process 等记录。
然后分析被杀死的是哪个进程、占用了多少内存，以及是否存在内存泄漏、参数配置不合理或者业务流量突增等问题。
如果是 Java 应用，还需要结合 Heap Dump、GC 日志和 JVM 参数进一步分析。
生产环境中，OOM 往往只是结果，真正需要找到的是内存持续增长的根本原因。

[!tip]- 面试官考察点
考察是否真正处理过 OOM 故障，以及是否具备 Linux 与应用联合排障能力。

16-20 磁盘与文件系统

16. Linux 磁盘满了如何排查？

#os
🔗 监控 K8S CICD 自动化 数据库

[!quote]- 标准答案
当磁盘空间不足时，首先通过 df -h 查看哪个挂载点使用率过高，然后使用 du -sh 或 du -h –max-depth=1 逐层定位占用空间最大的目录。
生产环境中常见原因包括日志文件过大、备份文件堆积、临时文件未清理、Docker 镜像和容器日志增长等。
如果发现磁盘已满但找不到大文件，还需要检查是否存在“文件已删除但进程仍占用”的情况。
排查思路通常是：先找分区，再找目录，最后找文件。

[!tip]- 面试官考察点
考察是否具备 Linux 磁盘空间故障处理经验。

17. df 与 du 的区别是什么？ 道

#os
🔗 数据库 K8S

[!quote]- 标准答案
df 用于查看文件系统整体空间使用情况，而 du 用于查之看目录或文件实际占用空间。
例如：df -h查看的是整个分区还剩多少空间。
而：du -sh /data查看的是指定目录占用了多少空间。
生产环境中经常出现：df 显示磁盘已满，但 du 统计不到对应空间。
这种情况通常说明存在已删除但仍被进程占用的文件。
因此排查磁盘问题时，df 和 du 经常需要结合使用。

[!tip]- 面试官考察点
考察是否理解文件系统空间统计原理。

18. inode 耗尽会导致什么问题？

#os
🔗 监控 K8S 数据库

[!quote]- 标准答案
inode 用于保存文件的元数据信息，例如文件权限、大小、时间戳等。
Linux 中创建一个文件就会消耗一个 inode。
当 inode 耗尽时，即使磁盘空间还有很多剩余，也无法继续创建新文件。
常见现象包括：无法创建文件服务启动失败日志无法写入数据库异常生产环境中，大量小文件最容易导致 inode 耗尽，例如缓存目录、邮件系统、日志目录等。
排查时通常使用：df -i查看 inode 使用情况。

[!tip]- 面试官考察点
考察是否理解 inode 机制以及相关故障现象。

19. 文件被删除但空间没有释放如何排查？

#os
🔗 数据库 K8S

[!quote]- 标准答案
这种情况通常是因为文件虽然已经删除，但仍然被某个进程占用。
Linux 删除文件时，只是删除目录项。
如果进程仍然持有文件句柄，系统不会立即释放磁盘空间。
因此会出现：df -h显示磁盘已满，但：du -sh统计不到对应文件。
排查时通常使用：lsof | grep deleted查看被删除但仍被占用的文件。
处理方式一般是重启相关进程，或者释放对应文件句柄。
这是 Linux 运维中非常经典的磁盘故障场景。

[!tip]- 面试官考察点
考察是否真正处理过线上磁盘空间异常问题。

20. 如何分析磁盘 IO 性能问题？

#os
🔗 监控 K8S 中间件 数据库

[!quote]- 标准答案
分析磁盘 IO 问题时，通常需要关注磁盘利用率、IO 等待时间和读写性能。

排查时不仅要看磁盘指标，还要结合具体进程分析是谁产生了大量 IO 请求。

21-25 网络

21. TCP 三次握手与四次挥手是什么？

#os
🔗 数据库 K8S

[!quote]- 标准答案
TCP 是面向连接的协议，通信前需要先建立连接，这个过程称为三次握手。
客户端先发送 SYN 请求，服务端返回 SYN+ACK，客户端再回复 ACK，连接建立完成。
通信结束后，需要通过四次挥手释放连接。
因为 TCP 是全双维工通信，双方都需要分别关闭自己的发送通道，所以通常需要四次交互才能完全断开连接。
三次握手解决的是连接建立问题，四次挥手解决的是连接释放问题。

[!tip]- 面试官考察点
考察是否理解 TCP 连接建立与释放机制，以及网络通信基础知识。

22. TIME_WAIT 为什么会产生？

#os
🔗 中间件 K8S 数据库

[!quote]- 标准答案
TIME_WAIT 是 TCP 主动关闭连接的一方在连接结束后进入的一种状态。
它的主要作用有两个：一是确保最后一个 ACK 能够成功到达对端；
二是避免旧连接中的延迟数据影响新的连接。
TIME_WAIT 会持续一段时间后自动消失。
生产环境中，如果短时间建立和关闭大量连接，例如高并发 Web 服务、Nginx 或数据库连接频繁创建销毁，就可能产生大量 TIME_WAIT。
大量 TIME_WAIT 本身并不一定是故障，但过多时可能导致端口资源耗尽。

[!tip]- 面试官考察点
考察是否理解 TCP 状态机，以及 TIME_WAIT 的设计目的。

23. 服务器连接数过高如何排查？

#os
🔗 监控 K8S 数据库

[!quote]- 标准答案
当服务器连接数过高时，首先要确认是什么类型的连接增长。
通常会通过：ss -ant或者：netstat -ant查看连接状态分布。
如果大量连接处于 ESTABLISHED，说明业务访问量较大；
如果大量处于 TIME_WAIT，可能是连接创建过于频繁；
如果大量处于 CLOSE_WAIT，则可能是应用程序没有正确关闭连接。
然后需要结合进程、应用日志和业务流量进一步分析。
生产环境中常见原因包括流量突增、程序连接泄漏、数据库连接池配置不合理以及恶意访问。

[!tip]- 面试官考察点
考察是否具备网络连接分析能力，以及线上故障排查经验。

24. Linux 网络故障如何排查？

#os
🔗 中间件 K8S 数据库

[!quote]- 标准答案
排查 Linux 网络故障时，一般遵循从下到上的思路。
首先检查网卡是否正常、IP 是否正确、路由是否存在，然后检查目标地址是否可达，再检查端口监听和防火墙策略。
常见排查命令包括：ip addrip routepingtelnetcurlss -lntp如果网络层正常，再进一步分析 DNS、应用服务和负载均衡配置。
生产环境中很多所谓的网络故障，最终其实是服务未启动、防火墙拦截或配置错误导致的。

[!tip]- 面试官考察点
考察是否具备系统化网络排障思维。

25. DNS 解析异常如何排查？

#os
🔗 数据库 K8S 中间件

[!quote]- 标准答案
当出现域名无法访问时，首先需要确认问题是否发生在 DNS 解析阶段。
可以使用：nslookup或者：dig测试域名解析结果。
如果解析失败，需要检查 DNS 服务器配置、网络连通性以及域名记录是否正确。
如果能够解析出 IP，但业务仍然无法访问，则问题可能出现在网络层或应用层。
生产环境中常见原因包括 DNS 服务异常、配置错误、缓存未刷新以及域名解析记录错误。
排查 DNS 问题时，要先确认“解析是否正常”，再确认“解析后的地址是否可达”。

[!tip]- 面试官考察点
考察是否理解 DNS 工作原理，以及网络故障定位能力。

26-30 生产级故障排查

26. Linux 服务器响应缓慢如何排查？

#os
🔗 监控 K8S 数据库 中间件

[!quote]- 标准答案
服务器响应缓慢时，不能直接判断是 CPU、内存还是网络问题，而是要从整体资源使用情况入手分析。
通常先通过 top、htop 查看 CPU、Load、内存使用情况，再结合 iostat 查看磁盘 IO，使用 ss 或 netstat 查看网络连接状态。
如果资源都正常，还需要检查应用日志、数据库慢查询以及外部依赖服务是否异常。
生产环境中，CPU 打满、内存不足、磁盘 IO 阻塞、数据库慢查询和网络异常都是常见原因。
排查思路一般遵循：先看系统资源，再看应用状态，最后定位具体业务问题。

[!tip]- 面试官考察点
考察是否具备系统化性能问题排查思维。

27. 服务器频繁重启可能有哪些原因？

#os
🔗 监控 K8S 数据库

[!quote]- 标准答案
服务器频繁重启可能来自硬件、操作系统、应用程序或者人为操作等多个方面。
常见原因包括内核崩溃、硬件故障、电源异常、OOM 导致关键进程退出、系统自动升级重启以及人为误操作。
排查时通常需要查看系统日志：last -xjournalctl以及内核日志：dmesg确认重启发生的具体时间和原因。
生产环境中，如果没有明确证据，不要轻易认为是应用问题，很多时候可能是硬件或系统层面的故障。

[!tip]- 面试官考察点
考察是否具备故障分析能力，以及对 Linux 日志体系的理解。

28. 如何分析 Java 进程异常占用资源？

#os
🔗 监控 K8S 数据库

[!quote]- 标准答案
当 Java 进程 CPU 或内存异常升高时，首先要确认问题类型。
如果 CPU 过高，通常会先找到高 CPU 线程，再通过 jstack 查看线程堆栈定位代码问题。
如果内存持续增长，则需要查看 JVM 堆使用情况、GC 日志以及 Heap Dump 文件，分析是否存在内存泄漏。
生产环境中常见原因包括死循环、频繁 Full GC、大对象堆积、线程泄漏和缓存设计不合理等问题。
对于 Java 故障，Linux 只能帮助定位现象，真正的问题往往还需要结合 JVM 分析。

[!tip]- 面试官考察点
考察是否具备 Java 应用与 Linux 联合排障能力。

29. 如何进行 Linux 性能分析？

#os
🔗 数据库 K8S 中间件

[!quote]- 标准答案
Linux 性能分析通常围绕 CPU、内存、磁盘和网络四个维度展开。
首先通过 top 查看整体资源情况，再通过 vmstat、iostat、sar 等工具分析具体指标。
如果 CPU 高，需要关注进程和线程；
如果 Load 高，需要分析是否存在 IO 等待；
如果内存异常，需要关注 Swap 和OOM；
如果网络异常，则需要查看连接数和网络流量。
性能分析的关键不是记住命令，而是建立完整的分析思路。
生产环境中，大多数性能问题最终都可以归结为 CPU、内存、磁盘或网络中的某一个环节出现瓶颈。

[!tip]- 面试官考察点
考察是否具备性能分析体系化思维，而不仅仅会执行命令。

30. 遇到线上故障时你的排查思路是什么？

#os
🔗 监控 K8S 自动化

[!quote]- 标准答案
遇到线上故障时，首先要确认故障影响范围，是单个服务异常还是整个系统异常。
然后根据现象快速收集信息，例如错误日志、监控指标、告警记录和最近变更情况。
接下来优先恢复业务，再分析根因。
因为生产环境中最重要的是降低业务影响，而不是第一时间追究原因。
通常会按照：现象确认 → 范围评估 → 日志分析 → 资源检查 → 根因定位 → 故障恢复 → 事后复盘的思路进行处理。
真正成熟的运维工程师，不是不会遇到故障，而是能够快速定位故障并恢复业务。

[!tip]- 面试官考察点
考察是否具备生产故障处理经验、应急响应能力以及稳定性治理思维。
