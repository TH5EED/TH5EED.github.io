1-6 CI/CD基础

1. 什么是 CI/CD？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
CI/CD 是一种软件交付模式，用于实现代码从开发到上线的自动化流程。
其中 CI（Continuous Integration）表示持续集成，开发人员提交代码后自动进行编译、测试和检查；
CD（Continuous Delivery/Deployment）表示持续交付或持续部署，代码通过验证后自动发布到测试环境或生产环境。
CI/CD 的核心目标是提高交付效率、降低人为错误、缩短发布周期。

💡 面试官考察点
考察是否理解 CI/CD 的基本概念，以及是否参与过自动化发布流程。

2. CI 与 CD 的区别是什么？

#cicd
🔗 K8S 自动化

📝 标准答案
CI 主要解决“代码能不能顺利集成”的问题，关注代码提交后的自动编译、测试和构建。
CD 主要解决“代码能不能快速交付”的问题，关注构建完成后的自动部署和发布。
简单来说，CI 负责构建软件，CD原 负责交付软件。

💡 面试官考察点
考察是云否理解持续集成与持续交付的职责边界。

3. DevOps 与 CI/CD 的关系是什么？

#cicd
🔗 K8S 自动化

📝 标准答案
DevOps 是一种文化和工作模式，强调开发与运维协同合作，提高软件交付效率。
CI/CD 则是 DevOps 落地的重要技术手段之一。
简单理解：DevOps 是理念，CI/CD 是工具和实践。
没有 CI/CD，DevOps 很难真正落地；
而只有 CI/CD，没有团队协作和流程改进，也不能算真正的 DevOps。

💡 面试官考察点
考察是否理解 DevOps 与 CI/CD 的关系，而不是把两者当成同一个概念。

4. 为什么企业需要 CI/CD？

#cicd
🔗 K8S 自动化

📝 标准答案
随着系统规模增大和发布频率提高，依靠人工部署容易出现效率低、错误多、难回滚等问题。
CI/CD 可以实现代码自动构建、自动测试、自动发布，大幅减少人工操作，提高发布效率和交付质量。
对于企业来说，CI/CD 不仅提升研发效率，也能够降低发布风险，保证业务快速迭代。

💡 面试官考察点
考察是否理解 CI/CD 给企业带来的实际价值，而不仅仅是会使用工具。

5. 一套完整的 CI/CD 流程包含哪些阶段？

#cicd

一套完整的 CI/CD 流程通常包括代码提交、代码拉取、编译构建、自动测试、镜像构建、制品存储、自动部署、健康检查和发布验证等阶段。

7-12 Jenkins核心

7. Jenkins 的核心架构是什么？

#cicd
🔗 K8S 自动化

📝 标准答案
Jenkins 采用 Master-Agent 架构（新版本通常称为 Controller-Agent）。
Controller 负责管理任务、调度流水线、保存配置和展示 Web 界面；
Agent 负责真正执行构建任务，例如代码编译、镜像构建、自动测试和发布部署。
这种架构可以将管理与执行分离，提高构建效率和扩展能力。

💡 面试官考察点
考察是否理解 Jenkins 的整体工作原理，以及是否接触过分布式构建。

8. Jenkins Master 与 Agent 的区别是什么？

#cicd
🔗 K8S 自动化

📝 标准答案
Master（Controller）主要负责任务管理和调度，不直接参与大量构建工作；
Agent 负责执行具体任务。
例如用户点击构建后，请求先到 Jenkins Controller，然后 Controller 将任务分发给对应 Agent 执行。
这样可以避免 Jenkins 主节点压力过大，也方便根据不同项目分配不同构建环境。

💡 面试官考察点
考察是否理解 Jenkins 的角色分工，以及分布式构建思想。

9. Jenkins 为什么需要 Agent？

#cicd
🔗 K8S 自动化

📝 标准答案
如果所有构建任务都在 Jenkins Controller 上执行，当项目数量增加后，很容易出现资源不足、任务排队和构建效率下降的问题。
通过 Agent，可以将构建任务分散到多台机器执行，不同 Agent 还可以安装不同环境，例如 Java、Node.js、Python、Docker 等，从而满足不同项目需求。
因此 Agent 的核心价值是提高扩展性、隔离构建环境和提升并发能力。

💡 面试官考察点
考察是否理解 Jenkins 扩展机制，以及企业为什么普遍采用 Agent 架构。

10. Jenkins 如何实现分布式构建？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
Jenkins 通过 Controller-Agent 架构实现分布式构建。
管理员先将多台服务器注册为 Agent，然后在流水线中指定任务运行在哪类 Agent 上。
当构建任务触发后，Controller 会自动选择符合条件的 Agent 执行任务运。
这样多个项目可以同时在不同 Agent 上构生建，从而提高整体构建效率。
在 Kubernetes 环境中，还可以通过 Kubernetes Plugin 动态创建 Agent Pod，实现弹性构建。

💡 面试官考察点
考察是否真正使用过 Jenkins Agent，以及是否理解分布式构建原理。

11. Jenkins Pipeline 与 Freestyle 的区别是什么？

#cicd
🔗 K8S 自动化

📝 标准答案
Freestyle 是 Jenkins 早期的任务模式，主要通过 Web 页面进行配置，简单易用，但复杂流程维护困难。
Pipeline 则采用代码方式定义流水线，将整个构建流程写入 Jenkinsfile 中，可以进行版本管理、代码审查和复用。
因此生产环境中，大多数企业都会选择 Pipeline，而不是 Freestyle。
简单来说：Freestyle 偏配置化，Pipeline 偏代码化。

💡 面试官考察点
考察是否真正使用过 Jenkins Pipeline，以及是否理解 Pipeline 的优势。

12. Jenkinsfile 的作用是什么？

#cicd
🔗 K8S 自动化

📝 标准答案
Jenkinsfile 用于定义整个 CI/CD 流程，可以理解为流水线脚本。
开发人员将 Jenkinsfile 与代码一起存放在 Git 仓库中，Jenkins 拉取代码后按照 Jenkinsfile 中定义的步骤执行构建、测试、镜像制作和部署等操作。
这样做的好处是发布流程代码化、版本化和可追溯，团队成员看到 Jenkinsfile 就能了解完整交付流程。
在企业中，Jenkinsfile 通常被视为 Infrastructure as Code（IaC）思想的一部分。

💡 面试官考察点
考察是否理解 Jenkinsfile 的作用，以及是否具备流水线代码化管理思维。

13-18 流水线设计

13. 如何设计企业级 CI/CD 流水线？

#cicd
🔗 K8S 自动化 监控 操作系统

📝 标准答案
企业级 CI/CD 流水线的核心目标是实现标准化、自动化和可追溯的软件交付流程。
一般会包含代码拉取、编译构建、自动测试、镜像构建、制品存储、自动部署、健康检查和结果通知等阶段。
生产环境中还会增加权限控制、发布审批、灰度发布和回滚机制。

14. 为什么要将构建、测试、部署分阶段执行？ 道

#cicd
🔗 K8S 自动化

📝 标准答案
分阶段执行可以让问题尽早暴露，并降低发布风险。
例如代码编译失败时，就不需要继续执行镜像构建；
自动测试失败时，也不应该继续部署到生产环境。
同时分阶段设计还能让流水线结构更加清晰，方便排查问题和后期维护。
因此生产环境中的流水线通常都会将构建、测试、发布拆分成独立阶段。

💡 面试官考察点
考察是否理解流水线设计思想，以及质量控制流程。

15. 如何实现流水云线参数化？

#cicd
🔗 K8S 自动化

📝 标准答案
流水线参数化是指在执行任务时动态传入参数，而不是将配置写死在脚本中。
例如可以让用户选择：发布环境Git 分支应用名称镜像版本这样同一套流水线就能适用于多个项目和多个环境，提高复用性和维护效率。

16. 如何设计多环境发布流程？

#cicd
🔗 K8S 自动化

📝 标准答案
多环境发布通常会划分为开发、测试、预发和生产等环境。
每个环境应使用独立的配置文件、命名空间、数据库和权限体系，避免相互影响。
正常发布流程一般是：开发环境验证 → 测试环境验证 → 预发环境验证 → 生产环境发布。
这样能够提前发现问题，降低直接发布生产环境带来的风险。

💡 面试官考察点
考察是否具备多环境管理经验，以及生产变更风险控制意识。

17. 如何实现流水线失败自动终止？

#cicd
🔗 K8S 自动化 监控

📝 标准答案
流水线失败自动终止是 CI/CD 中最基本的保护机制。
当某个阶段执行失败后，例如编译失败、单元测试失败、镜像构建失败或健康检查失败，流水线应立即停止后续步骤，避免错误版本继续发布。
这样可以保证只有通过验证的代码才能进入下一阶段。
生产环境中，失败即停止几乎是所有流水线的默认策略。

💡 面试官考察点
考察是否理解流水线质量门禁机制，以及自动化发布中的风险控制思维。

18. 如何实现流水线失败自动回滚？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
自动回滚是指发布完成后，如果发现新版本异常维，系统能够快速恢复到上一个稳定版本。
在 Kubernetes 环境中，通常会结合 Deployment 的版本历史实现回滚。
如果发布后出现 Pod 启动失败、健康检查异常、错误率升高等情况，可以自动触发回滚流程。
实现自动回滚的前提是：镜像版本可追溯配置变更可追溯发布记录完整这样才能准确恢复到指定版本。
生产环境中，自动回滚能够大幅缩短故障恢复时间，减少业务影响。

💡 面试官考察点
考察是否理解发布失败后的处理机制，以及是否具备生产环境故障恢复经验。

19-22 镜像与制品管理

19. Harbor 私有镜像仓库的作用是什么？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
Harbor 是企业常用的私有镜像仓库，用于统一存储和管理 Docker 镜像。
相比 Docker Hub，Harbor 可以部署在企业内部网络中，避免镜像上传到公网，同时还能提供用户权限管理、镜像复制、安全扫描、审计日志等功能。
在 CI/CD 流程中，通常会先将镜像构建完成，然后推送到 Harbor，最后再由 Kubernetes 从 Harbor 拉取镜像进行部署。
因此 Harbor 可以理解为企业内部的镜像管理中心。

💡 面试官考察点
考察是否真正搭建或使用过 Harbor，以及是否理解镜像仓库在 CI/CD 中的作用。

20. 为什么生产环境不建议使用 latest 标签？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
因为 latest 并不代表最新版本，而只是一个普通标签。
如果多个版本都使用 latest，后续很难确认当前运行的是哪一个版本，也无法准确回滚到指定版本。
例如今天发布了一次 latest，明天又发布了一次 latest，那么出现问题时，很难知道当前 Pod 实际拉取的是哪个镜像。
生产环境通常会使用：版本号Git Commit ID构建编号发布时间作为镜像标签。
这样可以保证镜像可追溯、可审计、可回滚。

💡 面试官考察点
考察是否具备生产环境发布经验，以及是否理解镜像版本管理的重要性。

镜像版本管理的核心目标是保证每次发运布都可追溯、可回滚。

22. 如何保证镜像可追溯性？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
镜像可追溯性是指能够通过镜像快速找到对应的代码版本、构建记录和发布记录。

镜像可追溯性是生产级 CI/CD 平台非常重要的能力，也是快速定位发布问题和执行回滚的基础。

23-26 Kubernetes发布

23. Kubernetes 中如何实现自动发布？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
Kubernetes 中的自动发布通常结合 Jenkins、GitLab CI、ArgoCD 等工具实现。

整个过程无需人工登录服务器操作，从代码提交到应用上线都可以自动完成。

24. 滚动更新（Rolling Update）的原理是什么？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
滚动更新是 Kubernetes Deployment 默认的发布策略，它不会一次性删除所有旧 Pod，而是逐步创建新 Pod、逐步删除旧 Pod。
在更新过程中，Kubernetes 会保证始终有一定数量的 Pod 对外提供服务，从而避免业务中断。
例如一个 10 副本应用升级时，可能先启动 1 个新 Pod，确认正常后再删除 1 个旧 Pod，然后重复这个过程，直到全部升级完成。
这种方式既保证了服务连续性，又降低了发布风险，因此是生产环境最常用的发布方式。

💡 面试官考察点
考察是否理解 Deployment 更新机制，以及为什么 Kubernetes 发布时业务通常不会中断。

25. 如何设计灰度发布方案？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
灰度发布的核心思想是让少量流量先进入新版本，验证稳定后再逐步扩大流量范围，而不是一次性全量发布。
例如先让 5% 用户访问新版本，观察错误率、响应时间和业务指标，如果没有问题，再逐步提升到 20%、50%、100%。
在 Kubernetes 中，灰度发布通常通过 Ingress、Service Mesh 或网关实现流量控制。
这样即使新版本存在问题，也只会影响少量用户，能够有效降低发布风险。

💡 面试官考察点
考察是否理解灰度发布的价值，以及是否具备生产环境风险控制意识。

26. 如何设计回滚方案？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
回滚方案的核心目标是在新版本出现问题时，能够快速恢复到上一个稳定版本。
要实现可靠回滚，首先需要保证镜像版本可追溯、配置变更可追溯、发布记录完整。
这样发生故障时，才能准确知道要恢复到哪个版本。
在 Kubernetes 中，可以利用 Deployment 的历史版本记录快速回滚，也可以通过重新指定旧镜像版本进行恢复。
需要特别注意的是，应用可以回滚，但数据库变更往往无法简单回滚，因此生产环境的数据库升级通常要求向前兼容。
一个成熟的回滚方案，应该做到快速恢复、影响最小、过程可审计。

💡 面试官考察点
考察是否真正经历过生产故障回滚，以及是否理解镜像、配置、数据库变更对回滚的影响。

27-30 企业级实践

27. Jenkins 在 Kubernetes 中如何动态创建 Agent？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
Jenkins 在 Kubernetes 中通常通过 Kubernetes Plugin之 动态创建 Agent。
当流水线开始执行时，Jenkins 会根据预先定义好的 Pod Template，在 Kubernetes 集群中临时创建一个 AgentPod。
构建任务在该 Pod 中执行，任务完成后 Pod 自动销毁。
这种方式不需要提前准备大量构建服务器，可以根据任务量动态申请和释放资源，提高资源利用率。
对于大型企业来说，动态 Agent 能够很好生地解决构建环境管理和资源扩展问题。

💡 面试官考察点
考察是否真正使原用过 Jenkins 与 Kubernetes 集成，以及是否理解动态构建和弹性资源管理。

28. GitOps 的核心思想是什么？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
GitOps 的核心思想是将 Git 作为系统配置和集群状态的唯一事实来源。
开发人员不直接修改 Kubernetes 集群，而是修改 Git 仓库中的配置文件。
GitOps 工具会自动检测 Git 变化，并将集群状态同步到 Git 中定义的目标状态。
这样所有变更都有记录、有审计、有回滚依据。
简单来说：GitOps 认为 Git 才是真正的配置中心，集群只是负责执行 Git 中定义的内容。

💡 面试官考察点
考察是否理解 GitOps 理念，以及是否具备声明式运维和平台化管理思维。

29. ArgoCD 与 Jenkins 的区别是什么？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
Jenkins 主要解决 CI 问题，负责代码构建、测试、镜像制作等工作；
ArgoCD 主要解决 CD 问题，负责Kubernetes 应用部署和状态同步。

30. 如何设计生产级 CI/CD 平台？

#cicd
🔗 K8S 监控 操作系统 中间件 自动化

📝 标准答案
生产级 CI/CD 平台的核心目标是实现标准化、自动化、安全化的软件交付。
平台通常包含代码仓库、流水线引擎、镜像仓库、Kubernetes 集群和监控告警体系。
开发提交代码后，系统自动完成构建、测试、镜像制作、部署发布和健康检查。
除了自动化之外，还需要考虑权限控制、发布审批、灰度发布、快速回滚、审计日志、多环境管理等能力。
一个成熟的 CI/CD 平台应该做到：代码可追溯、镜像可追溯、发布可审计、故障可回滚，并尽量减少人工干预。
本质上，生产级 CI/CD 平台不是一个发布工具，而是一套企业软件交付体系。

💡 面试官考察点
考察是否具备整体交付平台设计能力，是否理解发布、监控、安全、审计和回滚之间的关系，以及是否具备企业级 DevOps 思维。
