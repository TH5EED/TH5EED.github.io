1-6 监控基础

1. 为什么需要监控系统？

#monitor
🔗 操作系统 数据库 K8S 自动化 CICD 中间件

📝 标准答案
监控系统的核心作用是及时发现问题、定位问题和预防问题。
随着系统规模越来越大，服务器、容器、数据库、中间件和业务服务数量不断增加，仅靠人工巡检已经无法保证系统稳定运行。
通过监控系统，可以实时采集各类指标，例如 CPU、内存、磁盘、网络、接口响应时间和错误率等。
当指标异常时，系统能够自动告警，帮助运维人员第一时间发现故障。
对于企业来说，监控系统不仅是故障发现工具，更是保障业务稳定运行的重要基础设施。

💡 面试官考察点
考察是否理解监控系统的价值，以及监控与稳定性之间的关系。

2. 什么是监控？监控的核心目标是运什么？

#monitor
🔗 K8S CICD 自动化

📝 标准答案
监控是指持续采集系统运行状态，并通过可视化和告警机制帮助运维人员掌握系统健康状况。
很多人认为监控就是画图表，但原实际上监控的核心目标并不是展示数据，而是及时发现异常并辅助故障定位。
一个成熟的监控体系应该云能够回答三个问题：系统现在是否正常运行？
系统出现了什么问题？
问题发生后如何快速定位原因？
因此监控本质上是稳定性保障体系的重要组成部分。

💡 面试官考察点
考察是否理解监控的真正目的，而不仅仅停留在数据展示层面。

3. 什么是白盒监控与黑盒监控？

#monitor
🔗 中间件 数据库 K8S 操作系统

📝 标准答案
白盒监控关注系统内部状态，通过采集应用和系统内部指标了解运行情况。
例如：CPU 使用率JVM 堆内存数据库连接数Redis 命中率这些都属于白盒监控。
黑盒监控则从用户视角出发，不关心系统内部实现，而是直接验证服务是否可用。
例如：网站是否能打开API 是否返回 200页面响应时间是否正常这些都属于黑盒监控。
生产环境中通常会同时使用白盒监控和黑盒监控，两者互为补充。

💡 面试官考察点
考察是否理解不同监控方式的区别，以及实际应用场景。

4. Golden Signals 是什么？

#monitor
🔗 K8S 自动化 CICD

📝 标准答案
Golden Signals（黄金指标）是 Google SRE 提出的监控模型，用于快速评估服务运行状态。
它包含四个核心指标：Latency（延迟）Traffic（流量）Errors（错误）Saturation（饱和度）延迟反映响应速度，流量反映请求规模，错误反映服务质量，饱和度反映资源压力。
通过监控这四类指标，通常可以快速判断一个服务是否存在性能或稳定性问题。
因此 Golden Signals 也是很多企业设计监控体系的重要参考模型。

💡 面试官考察点
考察是否了解 SRE 监控理念，以及服务健康度评估方法。

5. RED 与 USE 监控模型是什么？

#monitor
🔗 K8S 自动化 操作系统 数据库 中间件

📝 标准答案
RED 和 USE 是两种常见监控模型。
RED 模型主要用于应用服务监控，关注：Rate（请求量）Errors（错误率）Duration（响应时间）适合 Web 服务、API 服务等业务系统。
USE 模型主要用于基础设施监控，关注：Utilization（利用率）Saturation（饱和度）Errors（错误数）适合 CPU、磁盘、网络等系统资源监控。
简单来说：RED 看业务服务是否健康。
USE 看基础设施是否健康。
生产环境中通常会同时使用这两种模型。

💡 面试官考察点
考察是否理解监控体系设计思路，以及不同监控模型的适用场景。

6. 企业监控体系通常包含哪些层级？

#monitor
🔗 K8S CICD 操作系统 中间件

📝 标准答案
企业监控体系通常会从多个层级进行建设，而不是只监控服务器资源。
最底层是基础设施监控，包括服务器、网络、存储等资源指标；
然后是平台层监控，例如 Kubernetes、数据库、中间件和消息队列；
再往上是应用层监控，例如接口响应时间、错误率和 JVM 指标；
最顶层则是业务监控，例如订单量、支付成功率和任务完成率。
一个成熟的监控体系应该能够从业务异常逐步下钻到应用、平台和基础设施层面，从而快速定位问题根因。
因此监控体系本质上是一个从业务到基础设施的完整观测链路。

💡 面试官考察点
考察是否具备整体监控架构思维，以及是否理解不同层级监控之间的关系。

7-12 Prometheus

7. Prometheus 的工作原理是什么？

#monitor
🔗 K8S 自动化 操作系统

📝 标准答案
Prometheus 是一套开源监控系统，其核心工作方式是定时从目标服务拉取监控指标，然后存储到本地时序数据库中。
被监控对象通常会暴露一个 HTTP 指标接口，例如 /metrics。

8. Prometheus 为什么采用 Pull 模式？

#monitor
🔗 K8S 自动化

📝 标准答案
Prometheus 默认采用 Pull（拉取）模式，即由 Prometheus 主动向目标服务获取监控数据。
相比 Push 模式，Pull 模式能够更方便地发现目标状态。
如果某个服务宕机，Prometheus 拉取失败本身就是一种监控信息。
同时 Pull 模式统一了采集频率和数据格式，便于服务发现和大规模管理。
当然，对于一些无法被主动访问的场景，例如批处理任务，也可以通过 Pushgateway 实现数据推送。
因此 Prometheus 虽然以 Pull 为主，但并非完全不支持 Push。

💡 面试官考察点
考察是否理解 Pull 与 Push 模式的区别，以及 Prometheus 的设计思想。

9. Exporter 的作用是什么？

#monitor
🔗 K8S 自动化 数据库 中间件 操作系统

📝 标准答案
Exporter 的作用是将各种系统或应用的运行状态转换为 Prometheus 能够识别的指标格式。
因为很多软件本身并不直接支持 Prometheus，所以需要通过 Exporter 采集数据并暴露 /metrics 接口。
例如：node-exporter 采集 Linux 指标mysqld-exporter 采集 MySQL 指标redis-exporter 采集 Redis 指标Prometheus 再通过 Pull 模式采集这些指标。
因此 Exporter 可以理解为 Prometheus 与各种系统之间的数据适配器。

💡 面试官考察点
考察是否理解 Exporter 在 Prometheus 体系中的定位。

10. node-exporter 常监控哪些指标？

#monitor
🔗 K8S 自动化 操作系统 数据库 中间件

📝 标准答案
node-exporter 主要用于采集 Linux 服务器运行状态。
常见监控指标包括：CPU 使用率、Load Average、内存使用情况、Swap 使用情况、磁盘空间使用率、磁盘 IO、网络流量、文件系统状态以及系统运行时间等。
这些指标基本覆盖了 Linux 运维日常关注的核心资源。
生产环境中，node-exporter 通常是 Prometheus 监控体系最基础的组件之一。

💡 面试官考察点
考察是否真正使用过 Prometheus 监控服务器，以及是否了解常见系统指标。

11. 什么是 Service Discovery？

#monitor
🔗 K8S CICD 操作系统 中间件 自动化

📝 标准答案
Service Discovery（服务发现）是指 Prometheus 自动发现监控目标的能力。
在云原生环境中，Pod、容器和服务经常动态变化，如果依靠手工配置监控目标，维护成本会非常高。

12. Prometheus 如何实现高可用？

#monitor
🔗 K8S 自动化 CICD 操作系统

📝 标准答案
Prometheus 本身是单机架构，并没有内置完整的高可用能力，因此生产环境通常会部署多个Prometheus 实例采集相同指标。
这样即使其中一个 Prometheus 故障，另一个实例仍然能够继续采集数据和触发告警。
对于长期存储和多副本需求，企业通常会结合 Thanos、VictoriaMetrics 或 Cortex 等方案，实现数据副本、统一查询和跨集群监控。
因此生产级 Prometheus 高可用通常不是依靠单个组件，而是通过多实例加长时存储方案共同实现。

💡 面试官考察点
考察是否了解 Prometheus 的架构特点，以及企业级监控平台的高可用设计思路。

13-18 告警体系

13. Alertmanager 的作用是什么？

#monitor
🔗 K8S 自动化

📝 标准答案
Alertmanager 是 Prometheus 生态中的告警管理组件，负责接收 Prometheus 产生的告警信息，并进行统一处理和发送。
当 Prometheus 检测到某项指标满足告警规则时，会将告警发送给 Alertmanager。
Alertmanager 可以根据配置对告警进行分组、去重、抑制和路由，然后通过邮件、企业微信、飞书、钉钉等方式通知相关人员。
因此 Alertmanager 并不负责发现问题，而是负责管理和分发告警。

💡 面试官考察点
考察是否理解 Prometheus 与 Alertmanager 的职责划分，以及告警通知流程。

14. 如何设计企业级告警体系？

#monitor
🔗 自动化

📝 标准答案
企业级告警体系的核心目标不是产生更多告警，而是让真正重要的问题能够被及时发现和处理。
首先需要覆盖基础设施、平台、中间件、应用和业务等多个层级。
其次需要为不同告警设置合理阈值，避免因为阈值过于敏感而产生大量误报。
同时还需要建立告警分级机制，例如 P1、P2、P3 等级，不维同级别采用不同通知方式和响应要求。
一个成熟的告警体系应该做到：有问题及时发现，没问题尽量少打扰。
否则告警数量越多，实际效果反而越差。

💡 面试官考察点
考察是否具备告警体系设计思维，以及稳定性治理经验。

15. 什么是告警风暴？

#monitor
🔗 自动化

📝 标准答案
告警风暴是指某个故障发生后，大量关联告警在短时间内同时产生，导致运维人员收到海量告警通知。
例如某个数据库故障后，可能同时触发应用异常、接口超时、连接池耗尽、业务失败等几十甚至上百条告警。
此时真正的问题只有一个，但却产生了大量重复或关联告警。
告警风暴不仅增加处理难度，还可能掩盖真正的故障根因。
因此生产环境通常会通过告警聚合、告警抑制和根因分析等方式减少告警风暴。

💡 面试官考察点
考察是否理解告警治理的重要性，以及真实生产环境中的告警问题。

16. 如何减少无效告警？

#monitor
🔗 K8S CICD 自动化

📝 标准答案
减少无效告警的核心原则是提高告警质量，而不是单纯减少告警数量。
首先要避免监控所有指标，而是重点关注影响业务稳定性的关键指标。
其次要合理设置告警阈值和持续时间，避免因为瞬时波动触发告警。
对于重复性问题，可以通过告警聚合和去重机制减少通知次数；
对于已知故障，可以通过静默机制暂时屏蔽告警。
生产环境中经常出现的问题不是告警太少，而是告警太多导致真正重要的告警被忽略。
因此高质量告警体系追求的是“少而准”，而不是“多而全”。

💡 面试官考察点
考察是否具备告警治理思维，以及对告警有效性的理解。

17. 什么是告警抑制（Inhibition）？

#monitor
🔗 自动化

📝 标准答案
告警抑制是指当某个根因告警发生时，自动屏蔽由其引发的关联告警，从而减少无意义通知。
例如某台服务器宕机后，可能会同时触发：服务器不可达、应用不可用、接口超时、数据库连接失败等多个告警。
实际上根因只有“服务器宕机”这一项。
如果所有告警都发送出来，就容易形成告警风暴。
此时可以配置告警抑制规则，当“服务器宕机”告警触发后，自动抑制其下游关联告警，只保留最关键的根因告警。
在 Alertmanager 中，Inhibition 是非常重要的告警治理能力。

💡 面试官考察点
考察是否理解告警抑制机制，以及如何通过根因告警减少告警风暴。

18. 如何设计告警分级体系？ 维

#monitor
🔗 自动化

📝 标准答案
告警分级体系的核心目的是区分故障严重程度，避免所有告警都采用同样的处理方式。
通常会根据业务影响范围和紧急程度划分生等级。
P1 通常表示业务中断、核心服务不可用等重大故障，需要立即响应；
P2 表示重要功能异常，但业务仍可部分运行；
P3 一般为性能下降或潜在风险；
P4 则更多是提示类和观察类告警。
不同等级对应不同的通知方式和响应要求。
例如 P1 可能通过电话、短信和企业微信同时通知，而 P4 可能仅记录到告警平台。
一个成熟的告警体系应该做到：重大故障绝不漏报，普通问题不过度打扰。
这样才能保证运维团队真正关注最重要的风险。

💡 面试官考察点
考察是否具备企业级告警治理思维，以及是否理解告警优先级管理的重要性。

19-22 日志平台

19. 为什么需要集中式日志平台？

#monitor
🔗 K8S 操作系统

📝 标准答案
随着系统规模不断扩大，日志会分散在不同服务器、容器和应用中。
如果仅依靠登录服务器查看日志，不仅效率低，而且很难快速定位跨服务问题。
集中式日志平台可以统一采集、存储和检索所有日志数据，让运维和开发人员通过一个平台查看整个系统的运行情况。
当系统出现故障时，可以快速搜索关键日志、分析错误原因、定位异常时间点，大幅提高问题处理效率。
因此集中式日志平台不仅是日志存储工具，更是故障排查和稳定性治理的重要基础设施。

💡 面试官考察点
考察是否理解日志平台建设的价值，以及为什么企业需要统一日志管理。

20. Kubernetes 如何实现日志采集？

#monitor
🔗 K8S CICD 操作系统 中间件 自动化

📝 标准答案
Kubernetes 中实现日志采集，通常会采用“DaemonSet + 日志采集 Agent + 日志平台”的方案。
最常见的做法是使用 Filebeat、Fluentd、Fluent Bit 等 Agent，以 DaemonSet 方式部署到每个节点，然后统一采集节点上的容器日志。
因为 Kubernetes 容器日志通常会写入 /var/log/containers/ 目录，所以日志 Agent 会挂载宿主机日志目录，持续采集各 Pod 日志，再发送到 Elasticsearch、Loki、Kafka、OpenSearch 等日志平台。
由于 Kubernetes 中 Pod 会频繁创建和销毁，因此运日志系统通常会结合 namespace、label 和 annotation 自动识别日志来源。

💡 面试官考察点
考察是否真正搭建过 Kubernetes 日志系统，以及是否理解 DaemonSet 为什么适合日志采集场景。

21. EFK 与 Loki 的区别是什么？

#monitor
🔗 K8S CICD 自动化 数据库 中间件 操作系统

📝 标准答案
EFK 和 Loki 都是常见的日志解决方案，但设计思路有所不同。
EFK 通常由 Elasticsearch、Fluentd（或 Filebeat）和 Kibana 组成。
它能够对日志内容建立全文索引，因此查询能力非常强，但资源消耗和存储成本相对较高。
Loki 则采用“只索引元数据，不索引日志内容”的设计方式，因此资源占用更低，部署和运维成本也更小。
Loki 通常与Grafana 配合使用，在云原生环境中非常流行。
简单来说：EFK 查询能力更强；
Loki 资源消耗更低。
对于 Kubernetes 场景，很多企业已经开始从 EFK 转向 Loki。

💡 面试官考察点
考察是否了解主流日志平台，以及不同方案之间的优缺点。

22. 如何设计企业级日志平台？

#monitor
🔗 K8S 自动化 操作系统

📝 标准答案
企业级日志平台的核心目标是实现日志统一采集、统一存储、统一检索和统一分析。
平台通常需要覆盖操作系统、容器平台、中间件、数据库和业务应用等多个层级，并支持海量日志的存储和快速检索。
除了日志采集之外，还需要考虑日志分级、日志保留周期、权限管理、审计追踪和成本控制等问题。
同时，日志平台还应与监控告警、链路追踪体系联动。
例如发现某个接口异常时，可以直接关联查看对应日志和调用链，从而加快故障定位速度。
一个成熟的日志平台最终服务的目标不是保存日志，而是帮助团队快速发现问题、定位问题和解决问题。

💡 面试官考察点
考察是否具备日志平台整体设计思维，以及对日志、监控和故障排查体系的理解。

28-30 稳定性治理

28. 什么是 SLI、SLO、SLA？

#monitor
🔗 K8S CICD 操作系统 中间件

📝 标准答案
SLI、SLO 和 SLA 是稳定性管理中的三个核心概念。
SLI（Service Level Indicator）是服务等级指标，用于衡量系统运行状态，例如可用率、响应时间、错误率等。
SLO（Service Level Objective）是服务等级目标，例如规定服务可用率达到 99.9%。
SLA（Service Level Agreement）是服务等级协议，通常是企业对客户作出的道正式承诺，例如承诺全年可用率达到99.95%。
简单来说：SLI 是监控指标，SLO 是内部目标，SLA 是对外承诺。

💡 面试官考察点
考察是否理解现代 SRE 稳定性管理体系，以及指标、目标和协议之间的关系。

29. 如何构建完整的可观测性体系？

#monitor
🔗 K8S 自动化 CICD

📝 标准答案
完整的可观云测性体系通常由 Metrics、Logs 和 Traces 三部分组成。
Metrics 负责发现问题，Logs 负责分析问题，Traces 负责定位问题。
在云原生环境中，通常会使用 Prometheus + Grafana 构建指标监控，使用 Loki 或 EFK 构建日志平台，使用OpenTelemetry + Jaeger 或 Tempo 构建链路追踪系统。
同时还需要建立统一告警平台、统一身份认证以及统一查询入口，实现监控、日志和链路数据的关联分析。
真正成熟的可观测性体系，不仅能够发现故障，更能够帮助团队快速定位故障和恢复业务。

💡 面试官考察点
考察是否具备整体可观测性架构思维，以及对 Metrics、Logs、Traces 协同工作的理解。

30. 如何设计企业级监控告警平台？

#monitor
🔗 K8S CICD 操作系统 中间件 自动化

📝 标准答案
企业级监控告警平台的核心目标是实现全链路监控、精准告警和快速故障定位。
平台通常需要覆盖基础设施、Kubernetes、数据库、中间件、应用服务以及业务指标等多个层级，并统一接入监控、日志和链路追踪数据。
