1-12 Redis

1. Redis 为什么这么快？

#middleware
🔗 数据库 K8S 操作系统

📝 标准答案
Redis 之所以快，主要是因为它基于内存存储，数据读写不需要经过磁盘 IO。
同时 Redis 使用单线程事件模型，避免了线程切换和锁竞争带来的开销。
此外 Redis 底层数据结构经过高度优化，并采用 IO 多路复用机制处理大量网络连接，因此能够实现极高的读写性能。

💡 面试官考察点
考察是否理解 Redis 高性能的核心原因，以及内存、单线程和 IO 多路复用之间的关系。

2. Redis 的数据类型有哪些？

#middleware
🔗 数据库 K8S 操作系统

📝 标准答案
Redis 常见数据类型包括 String、Hash、List、Set 和 ZSet（有序集合）。
其中 String 最常用，适合缓存对象和计数器；
Hash 适合存储结构化数据；
List 适合消息队列场景；
Set 适合去重和标签系统；
ZSet 适合排行榜和排序场景。
生产环境中，大部分业务主要使用 String 和 Hash。

💡 面试官考察点
考察是否了解 Redis 常用数据结构以及适用场景。

3. String 与 Hash 如何选择？

#middleware
🔗 数据库 K8S 操作系统

📝 标准答案
如果存储的是一个简单值，例如 Token、验证码、计数器等，通常使用 String。
如果存储的是一个对象，例如用户信息、商品信息等，则更适合使用 Hash。
Hash 可以单独修改某个字段，不需要整体读取和写入对象，因此在对象字段较多时更加灵活。
简单来说，简单数据用 String，结构化数据用 Hash。

💡 面试官考察点
考察是否具备 Redis 数据模型设计能力。

4. Redis 持久化机制有哪些？

#middleware
🔗 数据库 K8S

📝 标准答案
Redis 主要有两种持久化机制：RDB 和 AOF。
RDB 是在指定时间点生成数据快照；
AOF 是记录每一次写操作命令。
RDB 恢复速度快，占用空间小；
AOF 数据更完整，但文件通常更大。
生产环境中很多企业会同时开启 RDB 和 AOF，以兼顾性能和数据安全。

💡 面试官考察点
考察是否理解 Redis 数据持久化原理。

5. RDB 与 AOF 的区别是什么？

#middleware
🔗 数据库 K8S

📝 标准答案
RDB 保存的是某个时间点的数据快照，而 AOF 保存的是所有写操作记录。
RDB 文件体积较小，恢复速度快，但可能丢失最近一次快照之后的数据；
AOF 数据完整性更高，通常只会丢失极少量数据，但恢复速度相对较慢。
因此 RDB 更偏性能，AOF 更偏数据安全。

💡 面试官考察点
考察是否理解两种持久化方式的优缺点以及生产环境选型思路。

6. Redis 主从复制原理是什么？

#middleware
🔗 数据库 操作系统 K8S 监控 CICD

📝 标准答案
Redis 主从复制是指从节点自动同步主节点数据，实现数据冗余和读写分离。
首次同步时，主节点会生成 RDB 快照发送给从节点，从节点加载完成后，再同步后续写命令。
之后主节点每收到新的写请求，都会同步给从节点，保证数据基本一致。
主从架构能够提升读取性能，同时也是 Sentinel 和 Cluster 实现高可用的基础。

💡 面试官考察点
考察是否理解 Redis 高可用架构，以及主从复制的基本工作机制。

7. Redis Sentinel 的作用是什么？ 道

#middleware
🔗 CICD K8S 自动化 数据库 操作系统 监控

📝 标准答案
Redis Sentinel（哨兵）主要用于实现 Redis 的高可用。
之它会持续监控 Redis 主从节点状态，当主节点发生故障时，维Sentinel 会自动选举新的主节点，并通知客户端更新连接地址，从而实现故障自动切换。
Sentinel 本身不存储业务数据，它更像 Redis 集群的“监控与管理组件”。
生产环境中，Sentinel 通常至少部署 3 个节点，避免因为单个 Sentinel 故障导致误判。

💡 面试官考察点
考察是否理解 Redis 高可用方案，以及主从切换机制。

8. Redis Cluster 的工作原理是什么？

#middleware
🔗 数据库 K8S 监控 CICD 操作系统

📝 标准答案
Redis Cluster 是 Redis 官方提供的分布式集群方案，主要用于解决单机容量和性能瓶颈问题。
Cluster 将数据划分为 16384 个哈希槽，每个节点负责其中一部分槽位。
客户端访问数据时，会根据 Key 计算哈希槽，然后直接访问对应节点。
这样数据可以分散存储在多个节点上，实现水平扩展。
相比 Sentinel，Cluster 不仅具备高可用能力，还具备分布式存储能力，因此更适合大规模生产环境。

💡 面试官考察点
考察是否理解 Redis 分布式架构，以及 Cluster 与 Sentinel 的区别。

9. Redis 为什么会发生缓存穿透？

#middleware
🔗 数据库 K8S

📝 标准答案
缓存穿透是指查询一个既不存在于 Redis，也不存在于数据库中的数据。
由于缓存中没有数据，每次请求都会直接访问数据库。
如果大量恶意请求持续查询不存在的数据，就可能导致数据库压力过大。
常见解决方案包括缓存空值、布隆过滤器和参数校验。
生产环境中，布隆过滤器是比较常见的防穿透方案。

💡 面试官考察点
考察是否真正处理过高并发缓存问题，以及对缓存架构的理解。

10. Redis 为什么会发生缓存击穿？

#middleware
🔗 数据库 K8S

📝 标准答案
缓存击穿是指某个热点数据在缓存中过期的瞬间，大量请求同时访问该数据，导致请求全部落到数据库。
与缓存穿透不同，缓存击穿的数据原本是存在的，而且通常还是热点数据。
常见解决方案包括互斥锁、逻辑过期和热点数据永不过期。
生产环境中，对于热点 Key，通常会采用互斥锁或者提前续期的方式避免数据库被瞬间打垮。

💡 面试官考察点
考察是否理解热点数据场景，以及高并发下的缓存保护机制。

11. Redis 为什么会发生缓存雪崩？

#middleware
🔗 数据库 K8S 监控 CICD

📝 标准答案
缓存雪崩是指大量缓存数据在同一时间失效，导致请求同时落到数据库，从而引发数据库压力骤增甚至宕机。
例如系统中大量 Key 都设置了相同过期时间，当这个时间点到来时，大量缓存同时失效，就可能发生雪崩。
常见解决方案包括给过期时间增加随机值、多级缓存、热点数据永不过期以及限流降级。
缓存雪崩通常影响范围比缓存击穿更大，因此生产环境需要重点防范。

💡 面试官考察点
考察是否理解缓存雪崩、缓存击穿和缓存穿透三者的区别。

12. 如何设计高可用 Redis 架构？

#middleware
🔗 数据库 操作系统 K8S 监控 CICD 自动化

📝 标准答案
高可用 Redis 架构的设计，需要根据业务规模选择不同方案。
对于中小型系统，通常采用 Redis 主从复制加 Sentinel，实现数据冗余和自动故障切换。
对于大型系统，则更倾向于使用 Redis Cluster，通过数据分片实现容量扩展和高可用。
同时还需要考虑持久化、监控告警、数据备份、客户端连接池以及缓存异常时的降级策略。
一个成熟的 Redis 架构不仅要保证 Redis 不宕机，还要保证 Redis 异常时业务依然能够继续运行。

💡 面试官考察点
考察是否具备 Redis 架构设计能力，以及对高可用、扩展性和稳定性的整体理解。

13-22 消息队列 MQ

14. 消息队列有哪些应用场景？

#middleware
🔗 K8S

📝 标准答案
消息队列最常见的应用场景包括系统解耦、异步处理和流量削峰。
例如用户注册后发送短信、邮件通知，可以通过 MQ 异步完成；
秒杀场景下，大量请求可以先进入消息队列，再由消费者慢慢处理，避免数据库被瞬间打垮。
此外，订单、支付、物流等系统之间的数据同步，也经常通过消息队列完成。
简单来说，只要涉及高并发、异步执行或系统间通信，通常都可以考虑使用 MQ。

💡 面试官考察点
考察是否真正理解消息队列在生产环境中的使用场景。

15. RabbitMQ 与 Kafka 的区别是什么？

#middleware
🔗 监控 K8S

📝 标准答案
RabbitMQ 更偏向企业业务系统，特点是功能丰富、可靠性高、支持复杂路由；
Kafka 更偏向大数据和日志场景，特点是吞吐量高、扩展能力强。
RabbitMQ 通常用于订单、支付、通知等生业务消息；

16. Kafka 为什么吞吐量高？

#middleware
🔗 监控 K8S 操作系统 数据库

📝 标准答案
Kafka 吞吐量高，主要因为它采用顺序写磁盘、批量发送、批量消费和零拷贝等优化机制。
虽然 Kafka 数据最终会落盘，但顺序写磁盘的效率非常高，再加上操作系统页缓存的加速，实际性能接近内存读写。
此外，Kafka 的 Partition 机制允许多个消费者并行消费数据，从而进一步提升处理能力。
因此 Kafka 特别适合海量日志、实时计算和大数据场景。

💡 面试官考察点
考察是否理解 Kafka 高性能的核心原理。

17. Kafka 中 Topic 与 Partition 的作用是什么？

#middleware
🔗 K8S 操作系统

📝 标准答案
Topic 可以理解为消息分类，不同业务的数据通常存储在不同 Topic 中。
Partition 则是 Topic 的数据分片，用于实现数据分布和并行处理。
一个 Topic 可以包含多个 Partition，消息会分散存储到不同 Partition 中。
Partition 数量越多，理论上支持的并发消费能力越强。
因此 Topic 负责逻辑分类，Partition 负责性能扩展。

💡 面试官考察点
考察是否理解 Kafka 的核心数据模型和扩展机制。

18. 消息为什么会重复消费？

#middleware
🔗 数据库 操作系统 K8S

📝 标准答案
消息重复消费通常发生在消费者处理成功后，还没来得及提交消费位点（Offset）就发生故障。
当消费者恢复后，会重新读取之前的消息，从而导致同一条消息被消费多次。
网络抖动、服务重启、消费超时等情况都可能导致重复消费。
因此生产环境中通常会设计幂等机制，例如订单号去重、数据库唯一索引等方式，保证即使消息被重复消费，也不会对业务产生影响。

💡 面试官考察点
考察是否理解 MQ 的可靠性机制，以及是否具备处理重复消费问题的经验。

19. 如何保证消息不丢失？

#middleware
🔗 K8S

📝 标准答案
消息不丢失需要同时保证生产者、MQ 和消费者三个环节的可靠性。
生产者发送消息后要确认消息已经成功到达 MQ；

20. 如何保证消息顺序性？

#middleware
🔗 K8S

📝 标准答案
消息顺序性是指消息的消费顺序与生产顺序保持一致。
如果多个消费者同时消费同一批消息，就可能导致顺序被打乱。
因此生产环境中通常会让同一业务的数据进入同一个队列或同一个 Partition。
例如订单状态变更：创建订单 → 支付成功 → 发货成功如果顺序被打乱，业务逻辑就会出现问题。
Kafka 通常通过同一个 Key 路由到同一个 Partition 保证局部有序；

21. 什么是消息积压？如何处理？

#middleware
🔗 K8S

📝 标准答案
消息积压是指生产消息的速度超过消费消息的速度，导致大量消息堆积在 MQ 中无法及时处理。
常见现象包括消息数量持续增长、消费延迟升高、业务处理变慢等。
出现积压后，首先要确认是消费者故障、消费能力不足还是业务处理过慢导致的。
常见解决方案包括增加消费者数量、优化消费逻辑、提升服务器资源以及临时扩容 MQ 集群。
生产环境中，消息积压本身不是最危险的，最危险的是积压持续增长最终导致消息过期、磁盘写满或者业务大量超时。

💡 面试官考察点
考察是否真正处理过 MQ 生产故障，以及面对高并发场景的排障能力。

22. 如何设计高可用 MQ 集群？

#middleware
🔗 CICD K8S 自动化 操作系统 数据库 监控

📝 标准答案
高可用 MQ 集群的核心目标是保证单节点故障不会导致消息服务中断或数据丢失。
通常会采用多节点部署、数据副本机制和自动故障切换。
例如 RabbitMQ 会通过镜像队列或 Quorum Queue 实现数据冗余；
Kafka 则通过 Partition Replica 实现副本同步。
除了集群本身高可用，还需要关注监控告警、磁盘容量、网络状态和数据备份等方面。
因为很多 MQ 故障并不是节点宕机，而是磁盘写满、消息积压或者网络异常导致的。
一个成熟的 MQ 架构不仅要保证服务可用，更要保证消息可靠、故障可恢复、容量可扩展。

💡 面试官考察点
考察是否具备 MQ 架构设计能力，以及是否理解高之可用、可靠性和扩展性之间的关系。

23-27 Nginx

23. Nginx 的工作原理是什么？

#middleware
🔗 K8S 操作系统 数据库

📝 标准答案
Nginx 本质上是一个高性能 Web 服务器和反向代理服务器。
它采用 Master-Worker 架构运行，Master进程负责管理配置和 Worker 进程原，真正处理客户端请求的是 Worker 进程。
当用户请求到达 Nginx 云后，Nginx 会根据配置规则决定是直接返回静态资源，还是转发给后端应用服务器，例如Tomcat、Spring Boot、Node.js 等。

24. Nginx 为什么性能这么高？

#middleware
🔗 K8S 操作系统 数据库

📝 标准答案
Nginx 性能高的核心原因在于采用了异步非阻塞和 IO 多路复用模型。
传统服务器通常一个连接对应一个线程，当连接数很多时，线程切换开销会非常大。
而 Nginx 使用少量 Worker 进程就可以同时管理大量连接，因此资源消耗更低。
同时 Nginx 对静态资源处理效率非常高，再加上内存缓存、文件缓存等优化机制，使其能够轻松支撑数万甚至数十万并发连接。
因此 Nginx 经常作为互联网系统的流量入口。

💡 面试官考察点
考察是否理解异步非阻塞、IO 多路复用以及 Nginx 高性能原理。

25. 正向代理与反向代理的区别是什么？

#middleware
🔗 K8S CICD 监控 操作系统

📝 标准答案
正向代理代理的是客户端，反向代理代理的是服务器。
正向代理场景下，客户端主动访问代理服务器，再由代理服务器访问目标网站。
例如科学上网、企业统一出口上网都属于正向代理。
反向代理场景下，客户端并不知道后端真实服务器是谁，只知道访问代理服务器。
代理服务器再将请求转发给后端应用。
例如 Nginx、Ingress、WAF 都属于反向代理。
简单来说：正向代理隐藏客户端，反向代理隐藏服务器。

💡 面试官考察点
考察是否理解代理模式，以及实际应用场景。

26. Nginx 如何实现负载均衡？

#middleware
🔗 K8S

📝 标准答案
Nginx 可以将请求分发到多个后端服务器，从而实现负载均衡。
当客户端访问 Nginx 时，Nginx 会根据配置的负载均衡策略选择一个后端节点进行转发。
常见策略包括轮询、权重、IP Hash 和最少连接数等。
例如轮询会依次将请求分发到各个节点；
权重模式可以让性能更强的服务器处理更多请求；
IP Hash 可以让同一个用户始终访问同一台服务器。
通过负载均衡，可以提高系统吞吐量和高可用能力运。

💡 面试官考察点
考察是否理解负载均衡原生理，以及不同策略的适用场景。

27. Nginx 出现 502 与 504 如何排查？

#middleware
🔗 监控 K8S 操作系统

📝 标准答案
502 和 504 都属于 Nginx 与后端服务通信异常导致的问题，但原因不同。
502 通常表示 Nginx 无法正常连接后端服务，例如后端程序未启动、端口错误、服务崩溃或者网络不通。
504 通常表示 Nginx 已经连接到后端，但后端响应时间过长，超过了配置的超时时间。
排查时一般先确认后端服务是否正常运行，然后检查端口监听、网络连通性、Nginx 日志和应用日志。
生产环境中比较常见的原因包括应用线程池耗尽、数据库慢查询、服务假死、Pod 重启以及超时时间配置不合理等。

💡 面试官考察点
考察是否真正处理过线上故障，以及对 Nginx、应用服务和网络链路的排障能力。

28-30 Zookeeper

28. Zookeeper 的作用是什么？

#middleware

📝 标准答案
Zookeeper 是一个分布式协调组件，主要用于解决分布式系统中的协调与管理问题。
它本身并不负责业务处理，而是提供统一的配置管理、服务注册发现、分布式锁、集群选举等能力。
例如在早期微服务架构中，Dubbo 经常使用 Zookeeper 作为注册中心；

29. Zookeeper 为什么能实现分布式协调？

#middleware
🔗 数据库 操作系统

📝 标准答案
Zookeeper 能实现分布式协调，核心原因在于它能够保证数据一致性。
集群中的数据会通过 ZAB 协议同步到多个节点，并通过 Leader 负责事务处理，从而保证所有节点最终看到的数据一致。
同时，Zookeeper 提供了临时节点、顺序节点和 Watch 机制，可以方便地实现服务发现、主节点选举和分布式锁等功能。
例如服务宕机后，其对应的临时节点会自动删除，其他节点就能够立即感知状态变化。
正是因为具备这些能力，所以 Zookeeper 经常被用于各种分布式协调场景。

💡 面试官考察点
考察是否理解 Zookeeper 的一致性机制，以及为什么它能够实现分布式协调。

30. Zookeeper 与 Etcd 的区别是什么？

#middleware

📝 标准答案
Zookeeper 和 Etcd 都属于分布式协调组件，都能够实现配置管理、服务发现和集群协调，但实现方式和应用场景有所不同。
