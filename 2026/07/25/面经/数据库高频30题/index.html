1-8 MySQL基础原理

1. MySQL 的存储引擎有哪些？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
MySQL 支持多种存储引擎，常见的有 InnoDB、MyISAM、Memory 和 Archive 等。
其中 InnoDB 是 MySQL 目前默认的存储引擎，支持事务、行锁和崩溃恢复，适用于绝大多数业务场景；
MyISAM 不支持事务，查询性能较高，但数据安全性较弱；
Memory 引擎将数据存储在内存中，速度快但重启后数据会丢失。
生产环境中，绝大多数业务系统都使用 InnoDB。

[!tip]- 面试官考察点
考察是否了解 MySQL 存储引擎体系，以及 InnoDB 的主流地位。

2. InnoDB 与 MyISAM 的区别是什么？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
InnoDB 和 MyISAM 最大的区别在于事务和锁机制。
InnoDB 支持事务、行级锁、外键以及崩溃恢复能力，能够保证数据一致性；
MyISAM 不支持事务和外键，采用表级锁，并发性能相对较差。
另外，InnoDB 支持 MVCC 和 Buffer Pool，适合高并发业务系统；
MyISAM 更适合读多写少的场景。
目前生产环境中，除特殊场景外，基本都会选择 InnoDB。

[!tip]- 面试官考察点
考察是否理解两种存储引擎的核心差异，以及生产环境为什么选择 InnoDB。

3. 什么是聚簇索引？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
聚簇索引是指索引和数据存储在一起的索引结构。
在 InnoDB 中，主键索引就是聚簇索引。
数据记录会按照主键顺序存储在 B+Tree 的叶子节点中，因此通过主键查询时，可以直接获取完整数据，而不需要再次查找。
由于一张表的数据只能按照一种顺序存储，所以一个表只能有一个聚簇索引。
聚簇索引能够提高主键查询效率，但主键设计不合理也可能影响性能。

[!tip]- 面试官考察点
考察是否理解 InnoDB 的数据存储结构，以及主键索引的特殊性。

4. 什么是回表查询？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
回表查询是指通过普通索引找到对应主键后，再根据主键去聚簇索引中获取完整数据的过程。
例如查询条件命中了二级索引，但查询字段并不全部包含在索引中，此时 MySQL 会先查二级索引，再根据主键回到聚簇索引获取剩余字段。
由于需要进行两次查找，因此回表会增加查询开销。
生产环境中，经常会通过覆盖索引来减少或避免回表查询，从而提升 SQL 性能。

[!tip]- 面试官考察点
考察是否理解索引查询过程，以及 SQL 优化中的回表问题。

5. 什么是覆盖索引？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
覆盖索引是指查询所需要的字段全部包含在索引中，MySQL 可以直接从索引获取数据，而不需要再回表查询。
例如索引包含 name 和 age 字段，而查询语句只查询这两个字段，那么 MySQL 直接从索引中就能返回结果。
由于避免了回表操作，因此覆盖索引通常能够显著提升查询性能。
在 SQL 优化中，覆盖索引是非常常见的一种优化手段。

[!tip]- 面试官考察点
考察是否理解覆盖索引与回表查询之间的关系，以及索引优化思路。

6. B+Tree 为什么适合数据库索引？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
MySQL 的 InnoDB 索引底层采用 B+Tree 结构，因为它非常适合磁盘存储和范围查询。
B+Tree 的非叶子节点只保存索引信息，不保存具体数据，因此一个节点可以存储更多索引项，从而降低树的高度，减少磁盘 IO 次数。
同时，B+Tree 的叶子节点之间通过链表连接，非常适合范围查询和排序操作。
相比二叉树或红黑树，B云+Tree 在大数据量场景下查询效率更稳定，因此成为数据库索引的主流实现方式。

[!tip]- 面试官考察点
考察是否理解数据库索引底层原理，以及 B+Tree 的优势。

7. 什么情况下索引会失效？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
索引并不是创建后一定会生效，如果 SQL 写法不合理，MySQL 可能放弃使用索引而进行全表扫描。
常见情况包括使用模糊查询且以 % 开头、对索引列进行函数运算或类型转换、违反最左前缀原则，以及数据量过小导致优化器认为全表扫描成本更低。
例如：where name like ‘%tom’这种写法通常无法使用普通索引。
因此生产环境中，除了建立索引，更重要的是编写能够正确利用索引的 SQL。

[!tip]- 面试官考察点
考察是否理解索引失效场景，以及 SQL 编写规范。

8. 如何查看 SQL 是否走索引？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
通常使用 EXPLAIN 查看 SQL 的执行计划。
通过执行：EXPLAIN SQL语句可以看到 MySQL 的访问方式、使用的索引以及扫描行数等信息。
其中重点关注：typekeyrowsExtra如果 key 字段为空，通常表示没有使用索引；
如果 type 为 ALL，则说明发生了全表扫描。
生产环境中，排查慢 SQL 时，EXPLAIN 往往是第一步分析工具。

9-15 SQL与性能优化

9. 什么是慢 SQL？

#db
🔗 监控 K8S 中间件 操作系统

[!quote]- 标准答案
慢 SQL 是指执行时间较长、影响数据库性能的 SQL 语句。
具体多长时间算慢 SQL，并没有统一标准，通常会通过 MySQL 的 long_query_time 参数进行定义，例如超过 1 秒或 2 秒的 SQL 就会被记录到慢查原询日志中。
慢 SQL 并不一定是 SQL云 写错了，也可能是索引缺失、数据量过大、锁等待或者服务器资源不足导致的。
生产环境中，慢 SQL 是数据库性能问题最常见的原因之一。

[!tip]- 面试官考察点
考察是否理解慢 SQL 的概念，以及数据库性能问题的来源。

10. 如何排查慢 SQL？

#db
🔗 监控 K8S 中间件 操作系统

[!quote]- 标准答案
排查慢 SQL 时，通常先查看慢查询日志，找到执行时间较长的 SQL 语句。
然后通过 EXPLAIN 分析执行计划，确认是否使用索引、是否存在全表扫描以及扫描行数是否过多。
如果 SQL 已经走索引，还需要进一步分析数据量、表结构、锁等待和业务逻辑。
生产环境中，排查慢 SQL 的核心思路是：先找到慢 SQL，再分析执行计划，最后定位性能瓶颈。

[!tip]- 面试官考察点
考察是否具备数据库性能分析能力，以及慢 SQL 处理经验。

11. EXPLAIN 的作用是什么？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
EXPLAIN 用于查看 MySQL 的执行计划，帮助分析 SQL 的执行过程。
通过 EXPLAIN 可以看到：是否使用索引使用了哪个索引扫描了多少行数据是否发生全表扫描是否存在临时表或文件排序因此 EXPLAIN 是 SQL 优化过程中最常用的分析工具。
生产环境中，几乎所有慢 SQL 排查都会先使用 EXPLAIN 查看执行计划。

[!tip]- 面试官考察点
考察是否真正做过 SQL 优化，以及是否会使用 EXPLAIN 分析问题。

12. 如何优化 SQL 性能？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
SQL 优化的核心目标是减少扫描数据量、减少磁盘 IO 和减少不必要的计算。
常见优化方式包括建立合适索引、避免全表扫描、使用覆盖索引、减少回表查询、避免复杂子查询以及控制返回数据量。
同时还应避免频繁使用 select *，尽量只查询需要的字段。
生产环境中，大部分 SQL 性能问题最终都可以归结为索引设计不合理或者查询条件编写不规范。
因此优化 SQL 的本质，其实就是让数据库用更少的资源完成同样的工作。

[!tip]- 面试官考察点
考察是否具备 SQL 优化思维，以及对索引和执行计划的理解。

13. count(*)、count(1)、count(字段) 有什么区别？

#db

[!quote]- 标准答案
这三种写法都用于统计数据数量，但含义有所不同。
count() 统计的是所有记录行数，不会忽略 NULL 值；
count(1) 本质上也是统计记录行数，与 count() 基本等价；
count(字段) 只统计该字段不为 NULL 的记录。
例如某张表有 100 条数据，其中 10 条记录的 age 字段为 NULL，那么：count() 返回 100count(1) 返回 100count(age) 返回 90在 InnoDB 中，count() 通常是官方推荐写法，可读性最好。

[!tip]- 面试官考察点
考察是否理解不同 count 写法的含义，以及 NULL 值对统计结果的影响。

14. 为什么不建议 select *？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
select * 虽然编写方便，但生产环境通常不建议使用。
因为它会查询表中的所有字段，增加网络传输和数据库读取开销。
如果表字段较多，而业务实际只需要其中几个字段，就会造成资源浪费。
此外，select * 还可能导致覆盖索引失效，从而产生回表查询，影响 SQL 性能。
生产环境中，推荐只查询真正需要的字段，这样既能提高查询效率，也能降低系统资源消耗。

[!tip]- 面试官考察点
考察是否具备 SQL 编写规范意识，以及是否理解覆盖索引优化思路。

15. 如何分析数据库性能瓶颈？

#db
🔗 监控 K8S 中间件 操作系统

[!quote]- 标准答案
分析数据库性能瓶颈时，首先要判断问题出现在 CPU、内存、磁盘 IO、锁竞争还是 SQL 本身。
通常会先查看数据库监控指标，例如 CPU 使用率、连接数、QPS、TPS、慢 SQL 数量以及磁盘 IO 情况。
然后结合慢查询日志和 EXPLAIN 分析具体 SQL 是否存在性能问题。
如果数据库资源正常，还需要进一步检查应用程序是否存在连接池配置不合理、频繁创建连接或者业务逻辑异常等问题。
生产环境中，大多数数据库性能问题最终都集中在以下几个方面：慢 SQL、索引缺失、锁等待、连接数过高以及磁盘IO 瓶颈。

[!tip]- 面试官考察点
考察是否具备数据库性能分析思维，以及从系统层面定位问题的能力。

16-20 事务与锁

16. 什么是事务？

#db
🔗 CICD K8S 自动化 中间件 操作系统

[!quote]- 标准答案
事务（Transaction）是一组逻生辑上相关的数据库操作，这些操作要么全部成功执行，要么全部失败回滚，不会只执行一部分。
例如银行转账业务：A账户扣款 → B账户加款这两个操作必须同时成功或同时失败。
如果只扣款成功而加款失败，就会导致数据不一致。
事务的出现就是为了保证数据的完整性和一致性。
生产环境中的订单、支付、库存等核心业务，通常都会使用事务保证数据正确。

[!tip]- 面试官考察点
考察是否理解事务的作用，以及事务为什么存在。

17. ACID 分别代表什么？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
ACID 是事务的四大特性。
A（Atomicity）表示原子性，事务中的操作要么全部成功，要么全部失败。
C（Consistency）表示一致性，事务执行前后数据必须保持正确状态。
I（Isolation）表示隔离性，多个事务之间互不干扰。
D（Durability）表示持久性，事务提交后数据永久保存，即使数据库重启也不会丢失。
ACID 是关系型数据库保证数据可靠性的基础。

[!tip]- 面试官考察点
考察是否理解事务四大特性，以及它们分别解决什么问题。

18. 什么是脏读、不可重复读和幻读？

#db
🔗 CICD K8S 自动化 中间件 操作系统

[!quote]- 标准答案
脏读是指一个事务读取到了另一个事务尚未提交的数据。
如果后续事务回滚，那么读取到的数据实际上是无效数据。
不可重复读是指同一个事务中，两次查询同一条记录得到不同结果。
通常是因为其他事务修改并提交了数据。
幻读是指同一个事务中，两次查询满足条件的数据集时，发现记录数量发生变化。
通常是因为其他事务新增或删除了数据。
简单理解：脏读关注“读到了未提交数据”，不可重复读关注“同一条数据被修改”，幻读关注“数据数量发生变化”。

[!tip]- 面试官考察点
考察是否理解事务并发问题，以及不同读异常之间的区别。

19. MySQL 的隔离级别有哪些？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
MySQL 提供四种事务隔离级别。
Read Uncommitted（读未提交）允许读取未提交数据，可能发生脏读。
Read Committed（读已提交）只能读取已提交数据，解决脏读问题。
Repeatable Read（可重复读）保证同一个事务中多次读取结果一致，也是 MySQL 默认隔离级别。
Serializable（串行化）隔离级别最高，通过强制串行执行事务保证数据绝对一致，但性能开销最大。
生产环境中最常见的是 Repeatable Read 和 Read Committed。

[!tip]- 面试官考察点
考察是否了解事务隔离级别，以及 MySQL 默认隔离级别。

20. 什么是死锁？如何排查死锁？

#db
🔗 CICD K8S 自动化 中间件 操作系统

[!quote]- 标准答案
死锁是指两个或多个事务互相等待对方释放资源，从而导致所有事务都无法继续执行。
例如事务A锁住记录1等待记录2，事务B锁住记录2等待记录1，此时双方都无法继续执行，就形成了死锁。
MySQL 检测到死锁后，会自动选择一个事务回滚，从而解除死锁。
排查死锁时，通常通过：show engine innodb status\G查看最近一次死锁信息，分析涉及的 SQL 和锁资源。
生产环境中，死锁通常与事务过大、更新顺序不一致以及高并发更新同一数据有关。

[!tip]- 面试官考察点
考察是否理解死锁产生原理，以及是否具备数据库故障排查经验。

21-25 高可用与主从复制

21. MySQL 主从复制原理是什么？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
MySQL 主从复制是一种数据同步机制，通过将主库的数据变更同步到从库，实现数据冗余和读写分离。
当主库执行写操作后，会将变更记录到 Binlog。
从库通过 IO Thread 拉取主库 Binlog，并写入本地 Relay Log，然后由 SQL Thread 读取 Relay Log 并重放 SQL，从而完成数据同步。
整个过程可以简单理解为：主库写 Binlog → 从库拉取 Binlog → 从库执行 Binlog → 数据保持一致。
主从复制是 MySQL 高可用架构的重要基础。

[!tip]- 面试官考察点
考察是否理解 MySQL 数据同步机制，以及 Binlog、Relay Log 的作用。

22. 主从延迟如何排查？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
主从延迟是指从库同步数据的速度落后于主库，导致两边数据不一致。
排查时通常先查看：show slave status\G重点关注：Seconds_Behind_Master如果数值持续增长，说明存在同步延迟。
生常见原因包括大事务执行时间过原长、慢 SQL、从库硬件性能不足、磁盘 IO 瓶颈以及网络延迟等问题。
生产环境中，如果业务对实时性要求较高，还需要避免将大批量更新操作直接执行在主库上。

[!tip]- 面试官考察点
考察是否真正维护过 MySQL 主从架构，以及主从同步故障排查能力。

23. 什么是读写分离？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
读写分离是指写请求发送到主库，读请求发送到从库，从而分担数据库压力。
由于大多数业务场景中读操作远多于写操作，因此通过增加从库数量，可以显著提升系统整体吞吐能力。
例如：新增、修改、删除数据走主库；
查询数据走从库。
这样主库专注处理写请求，从库负责查询请求。
读写分离通常需要配合主从复制一起使用。

[!tip]- 面试官考察点
考察是否理解数据库扩展方案，以及主从复制与读写分离之间的关系。

24. 如何设计 MySQL 高可用架构？

#db
🔗 中间件 操作系统 K8S 监控 CICD 自动化

[!quote]- 标准答案
MySQL 高可用架构的核心目标是保证数据库故障时业务能够快速恢复。
中小型系统通常采用主从复制加 Keepalived 或 MHA 的方案，当主库故障时自动切换到从库。
对于更大规模的生产环境，可以采用 MGR、PXC 或云厂商提供的高可用数据库服务，实现自动故障检测和自动主从切换。
除此之外，还需要考虑：数据备份、监控告警、读写分离、主从延迟控制以及灾难恢复等能力。
真正的高可用不仅是主从切换，更重要的是数据安全和业务连续性。

[!tip]- 面试官考察点
考察是否具备数据库架构设计能力，以及高可用体系建设思维。

25. MHA、Keepalived、MGR 分别是什么？

#db
🔗 中间件 操作系统 K8S 监控 CICD

[!quote]- 标准答案
MHA（Master High Availability）是一套 MySQL 高可用管理工具，能够自动检测主库故障并完成主从切换。
Keepalived 本身并不管理数据库，它主要通过 VIP 漂移实现访问入口切换，常用于配合主从架构实现高可用。
MGR（MySQL Group Replication）是 MySQL 官方提供的高可用方案，支持多节点复制和自动故障切换，也是MySQL InnoDB Cluster 的核心组件。
简单理解：Keepalived 解决访问入口问题，MHA 解决主从切运换问题，MGR 则是官方提供的一体化高可用方案。
目前新项目更倾向于使用 MGR 或云数据库生高可用方案。

[!tip]- 面试官考察点
考察是否了解主流 MySQL 高可用技术，以及不同方案的定位和应用场景。
生产故障排查

26. MySQL CPU 飙高如何排查？

#db
🔗 中间件 操作系统 K8S

[!quote]- 标准答案
当 MySQL CPU 持续升高时，首先要确认是数据库本身的问题，还是业务流量突然增加导致的。
通常会先查看 MySQL 当前运行状态，重点关注活跃连接数、执行中的 SQL 以及慢查询情况。
如果发现某条 SQL 长时间运行或扫描大量数据，则很可能是慢 SQL 导致 CPU 消耗过高。
生产环境中常见原因包括索引缺失、全表扫描、大量排序操作、复杂关联查询以及高并发访问。
排查思路一般是：先看资源使用情况，再找慢 SQL，最后分析执行计划和索引设计。

[!tip]- 面试官考察点
考察是否具备数据库性能问题分析能力，以及慢 SQL 排查经验。

27. MySQL 连接数满了怎么办？

#db
🔗 中间件 操作系统

[!quote]- 标准答案
当 MySQL 连接数达到上限时，新连接将无法建立，应用通常会报出 “Too many connections” 错误。
排查时首先查看当前连接数和最大连接数配置，确认是否真的达到上限。
然后分析连接来源，确认是否存在连接泄漏、连接池配置不合理或者业务流量异常增长等问题。
如果是短期流量增长导致，可以临时提高最大连接数；
如果是程序没有及时释放连接，则需要从应用侧进行优化。
生产环境中，大量连接并不一定是好事，盲目增加连接数反而可能导致数据库压力进一步增大。

[!tip]- 面试官考察点
考察是否理解数据库连接管理机制，以及连接数异常的处理思路。

28. 数据库磁盘满了如何处理？

#db
🔗 监控 K8S 操作系统

[!quote]- 标准答案
数据库磁盘满了属于高风险故障，因为数据库可能无法继续写入数据，甚至导致服务异常。
首先需要确认是数据文件、日志文件、Binlog、归档日志还是备份文件占满磁盘。
然后根据实际情况清理无用文件，例如过期 Binlog、历史备份或者临时文件。
如果磁盘空间确实不足，还需要及时扩容存储。
生产环境中，很多数据库磁盘满并不是因为业务数据增长，而是因为日志长期未清理导致的。
因此除了故障处理，还需要建立容量监控和自动清理机制。

[!tip]- 面试官考察点
考察是否处理过数据库存储故障，以及容量管理意识。

29. 数据库误删数据如何恢复？ 维

#db

[!quote]- 标准答案
误删数据后，首先要停止相关写操作，避免新的数据覆盖恢复所需的信息。
如果存在完整备份，可以通过备份恢复数生据；
如果开启了 Binlog，还可以通过时间点恢复（Point In TimeRecovery）将数据库恢复到误删之前的状态。
生产环境中，恢复方式通常是：先恢复备份，再重放指定时间范围内的 Binlog，从而尽可能减少数据损失。
对于核心业务系统，定期备份和 Binlog 保存策略是数据恢复的基础。

[!tip]- 面试官考察点
考察是否理解数据库备份恢复机制，以及生产环境数据保护意识。

30. 如何设计企业级数据库体系？

#db
🔗 监控 K8S 中间件 操作系统 CICD 自动化

[!quote]- 标准答案
企业级数据库体系的设计目标是保证高可用、高性能、可扩展和数据安全。
通常需要从多个方面考虑，包括主从复制、读写分离、高可用切换、数据备份、监控告警和灾难恢复。
对于业务规模较大的系统，还需要考虑分库分表、缓存加速、连接池管理以及容量规划等问题。
此外，数据库监控、慢 SQL 治理、权限管理和审计日志也是企业级数据库体系的重要组成部分。
真正成熟的数据库体系，不仅要保证数据库能够运行，更要保证发生故障时能够快速恢复业务。

[!tip]- 面试官考察点
考察是否具备数据库架构设计思维，以及对高可用、性能优化和数据安全的整体理解。
