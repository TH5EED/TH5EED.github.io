Harbor 部署流程

本笔记为 Harbor 企业级镜像仓库的 Docker Compose 部署手册，跑在 ci-01 (.231)，是《闭关虚拟机部署规划》Step 2.6 的执行文档。
前置 GitLab 见《GitLab部署》、Jenkins 见《Jenkins部署》；后续 ArgoCD 见《ArgoCD部署》；Docker 环境见《Docker+Docker Compose部署》。
本笔记只写步骤，不代执行：命令列出来，SSH 上去照做，跑完把结果回填到「验证清单」。

一、Harbor 在 CI/CD 流水线中的角色

Harbor 是链路中段 ==企业级容器镜像仓库==：它不托管代码（GitLab）、不跑构建（Jenkins）、不直接管 K8s 部署（ArgoCD），它干的事是 ==把”构建产物”集中托管成”运行负载”唯一可信的镜像源==。

与上下游的数据流

三种角色对照表

角色 作用 上游 下游
镜像集中存储 所有构建产物统一托管，K8s 拉取唯一可信源 Jenkins push / 开发者手动 push ArgoCD → K8s kubelet（pull）
镜像安全门禁 内置 Trivy，push 时自动漏洞扫描，可设阻断策略 镜像 push 事件 扫描结果挂镜像元数据，供 ArgoCD/Jenkins 校验
权限与治理 项目级 RBAC、机器人账号、保留策略、镜像复制（replication） - ArgoCD/Jenkins 用 robot 账号按项目授权

关键定位：==Harbor 是”代码变镜像”与”镜像变运行”两半之间的解耦点==——Jenkins 只管往里推，ArgoCD/K8s 只管从里拉，二者互不直接耦合。相比裸 Docker Registry，多了漏洞扫描、签名、RBAC、审计、复制，生产可用。

二、部署方案

目标机器：ci-01 192.168.31.231（4C16G，Docker 29.7.2 + Compose v5.4.0，data-root /data/docker）

端口规划（与 GitLab/Jenkins 错开）：

服务 HTTP 备注
GitLab 8929 已部署（SSH 2222）
Jenkins 8080 已部署（Agent 50000）
Harbor 80 本次；HTTP 模式，80 在 ci-01 上空闲

数据目录：/data/harbor/（80G 数据盘，系统/数据分离原则）

  • offline installer 解压目录：/data/harbor/harbor/
  • 持久化数据卷：data_volume: /data/harbor/data（PG / Redis / registry 全部落这）

安装方式：官方 offline installer（自带镜像 tar 包，避免在线拉取不稳）

镜像版本：harbor-offline-installer-v2.11.2.tgz（pin 固定版本，避免某天跳大版本踩兼容性坑，呼应 GitLab 的 grafana 教训）

部署形态关键点：

  • HTTP 模式（80 端口）：学习环境最快；K8s 节点拉取需配 containerd insecure_registries（见步骤 8）
  • 内置 Trivy 漏洞扫描 ==默认开启，无需任何开关==：Harbor v2.4+ 已将 Trivy 设为默认扫描器，harbor.yml 的 trivy: 段只有 ignore_unfixed / skip_update / skip_java_db_update / offline_scan / security_check / insecure / timeout / github_token，没有 enabled 字段（老教程写 trivy.enabled: true 已过时，加上反而报错）。保持 trivy 段默认即可；skip_update: false 时首次扫描会从 GitHub 拉 Trivy DB（ci-01 需能访问 GitHub，内网不通就改 skip_update: true 离线挂 db，见坑位 6）
  • admin 密码：首次设强密码（别用默认 Harbor12345，内网也别偷懒）
  • 可选增强（本期不启用）：Notary 镜像签名、ChartMuseum Helm 仓、镜像保留策略、复制容灾
  • 持久化：PG / Redis / registry 全在 /data/harbor/data，重装不丢数据

七、常见坑位（部署时留意，预判）

以下为 Harbor 官方部署与内网 HTTP 模式的常见坑，部署时对照排查。

1. https 段未注释 → 启动卡住/失败

harbor.yml.tmpl 默认带 https: 段但无证书路径。若只改 hostname 不注释 https，prepare/install 会因找不到证书或一直 pending。==必须注释整个 https 段走 HTTP==（步骤 3 的 sed 已处理）。

2. 80 端口被占

ci-01 上 GitLab 用 8929、Jenkins 用 8080，80 应空闲；若被占（如 nginx 已监听 80），install.sh 起 nginx 会失败。步骤 0 已让你先查 80，被占就释放或改 http.port（同时 K8s insecure endpoint 端口要同步）。

3. K8s 节点没配 insecure registry → 拉镜像报 x509 / HTTP response

ArgoCD/kubelet 拉 http://192.168.31.231/... 时，containerd 默认要求 TLS，会报 server gave HTTP response to HTTPS client 或 x509: certificate signed by unknown authority。==步骤 8 必须做，且三节点都做==。

4. admin 密码用默认 Harbor12345

内网也别偷懒，首次登录立即改强密码；若忘了，可进 harbor-db 容器重置（属进阶操作，本期不展开）。

5. 重装 / 改配置

改 harbor.yml 后必须重新 ./prepare && ./install.sh 才生效；彻底停掉用 docker compose down -v（数据在 data_volume 不受影响）。升级前先备份 /data/harbor/data。

6. trivy 段没有 enabled 开关（新版已改）

Harbor v2.4+ 起 Trivy 已是默认内置扫描器，harbor.yml 的 trivy: 段只有 ignore_unfixed / skip_update / skip_java_db_update / offline_scan / security_check / insecure / timeout / github_token，没有 enabled 字段。网上很多老教程让你加 trivy.enabled: true 已过时，加上反而让 YAML 解析/校验报错。==保持 trivy 段默认即可==。

  • skip_update: false（默认）：每次扫描首次会联网从 GitHub 拉 Trivy DB（匿名限流 60 次/小时，学习环境够用）。ci-01 必须能访问 GitHub，否则首次扫描会失败/超时。
  • 内网确实不通 GitHub：改 skip_update: true，并手动下载 trivy-offline.tar.gz、解压出 trivy.db + metadata.json 挂到 trivy-adapter 的 /home/scanner/.cache/trivy/db（进阶，本期一般不用）。

7. install 阶段仍是 Pulled 而非 Loaded（离线包没用上）

offline installer 本意是解压后自带 harbor.v2.11.2.tar.gz（所有组件镜像），install.sh 应 docker load 后直接起，不再联网。但若 ./prepare 拉 goharbor/prepare、./install.sh 的 [Step 4] 里 9 个镜像都显示 Pulled（不是 Loaded），说明离线镜像没被 load，实际走了在线拉取。排查：ls -lh /data/harbor/harbor/harbor.v2.11.2.tar.gz 是否存在且约 500MB+；若不存在/损坏，就是下成了 online 版或包不完整。==功能不受影响==（能联网就 pull 成功），只是没起到”离线加速/断网部署”的作用。

经验教训（与 GitLab/Jenkins 串起来）

  • 版本 pin：offline installer 固定 v2.11.2，不裸用 latest，避免跳版本踩配置坑（同 GitLab grafana 教训）。
  • HTTP 内网模式要配套改 consumer：服务端用 HTTP 简单，但所有消费方（K8s containerd、docker 客户端、ArgoCD）都要声明 insecure，否则”服务端起来了、客户端拉不动”——这是内网 registry 最常被忽略的一环。
  • 数据盘隔离：data_volume 指到 /data/harbor/data，和 GitLab/Jenkins 的 /data/gitlab、/data/jenkins 各自独立，重装互不污染。
