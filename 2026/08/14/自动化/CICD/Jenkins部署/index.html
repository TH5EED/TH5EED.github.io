Jenkins 部署流程

本笔记为 Jenkins LTS 的 Docker Compose 部署手册，跑在 ci-01 (.231)，是《闭关虚拟机部署规划》Step 2.5 的执行文档。
原理与 Pipeline 设计见《jenkins（完善版）》；前置 GitLab 见《GitLab部署》；后续 Harbor 见《Harbor部署》。
本笔记只写步骤，不代执行：命令列出来，SSH 上去照做，跑完把结果回填到「验证清单」。

一、Jenkins 在 CI/CD 流水线中的角色

Jenkins 是整条链路的 ==CI 执行引擎==：它不托管代码（那是 GitLab），也不存镜像（那是 Harbor），更不直接管 K8s 部署（那是 ArgoCD）。它干的事是 ==把”代码变成可部署的变更”这一步自动化==。

与上下游的数据流

三种角色对照表

角色 作用 上游 下游
CI 执行引擎 按 Jenkinsfile 跑构建/测试/扫描 GitLab Webhook Harbor（镜像）、清单仓库（tag）
Pipeline as Code 载体 Jenkinsfile 跟随业务代码版本管理 开发者提交的 Jenkinsfile 自身各 stage
构建环境提供者 通过挂载宿主机 docker.sock 复用 host Docker 构建镜像 ci-01 宿主 Docker Harbor

关键决策：本项目 Jenkins ==以独立 Docker Compose 服务跑在 ci-01==，而不是像《jenkins（完善版）》里讲的”K8s 里动态起 Agent Pod”。原因：ci-01 是独立 Docker 主机（不是 K8s 节点），最简单的做法是 ==Docker-outside-of-Docker（DooD）==——把宿主机 /var/run/docker.sock 挂进 Jenkins 容器，让流水线直接用宿主 Docker 守护进程构建/推送镜像。K8s 动态 Agent 模式是生产级进阶（适合 Jenkins 本身就跑在 K8s 里），留作后续增强，不影响当前链路打通。

二、部署方案

目标机器：ci-01 192.168.31.231（4C16G，Docker 29.7.2 + Compose v5.4.0，data-root /data/docker）

端口规划（与 GitLab/Harbor 错开）：

服务 HTTP Agent(JNLP) 备注
GitLab 8929 2222(SSH) 已部署
Jenkins 8080 50000 本次
Harbor 80 - 后续 Step 2.6

数据目录：/data/jenkins/jenkins_home（80G 数据盘，系统/数据分离）

镜像版本：jenkins/jenkins:2.568.2-lts（2026-08-13 查官方 LTS 为 2.568.2；pin 固定版本，避免某天跳大版本踩配置/插件兼容坑，呼应 GitLab 的 grafana 教训）

部署形态关键点：

  • 持久化：/var/jenkins_home → /data/jenkins/jenkins_home（配置/插件/凭据/构建历史全在这）
  • DooD：挂 /var/run/docker.sock + 宿主机 /usr/bin/docker，流水线直接调宿主 Docker 构建推送
  • 权限①（docker.sock）：jenkins 容器默认以 uid 1000 运行，访问 docker.sock 需加入宿主机 docker 组 GID → 用 compose group_add: ${DOCKER_GID} + .env 传入（precheck 取真实 GID，本机实测 991）
  • 权限②（JENKINS_HOME）：bind 目录必须 chown 成 1000:1000，否则容器入口写不进（见踩坑实录）。这是最容易翻车的一步
  • JVM 内存：JAVA_OPTS -Xmx2048m（ci-01 共 16G，GitLab 已占 ~3-4G，Jenkins 给 2G 上限稳妥）
  • admin 初始化：不预设密码，首次启动生成 /var/jenkins_home/secrets/initialAdminPassword（同 GitLab 风格，登录后立即改）

七、踩坑实录（2026-08-14 实测）

现象

docker compose up -d 后 docker logs -f jenkins 反复刷：

ss | grep 8080 什么都没有（其实 ss 不带 -l 本就看不了监听端口；真排查用 ss -ltn）。容器状态虽显示 Started，但 Jenkins 入口在写 JENKINS_HOME 阶段就失败，根本没起 Web。

根因

  • 步骤 1 用 root 跑 mkdir -p /data/jenkins/jenkins_home，目录属主是 root:root、权限 755。
  • jenkins/jenkins 镜像的入口以容器内 uid 1000（用户 jenkins） 运行，对 root 属主、others 只有 r-x 的目录没有写权限 → 入口写不了 copy_reference_file.log 直接失败。
  • 这跟 group_add: DOCKER_GID（991）无关——那个是给 /var/run/docker.sock 用的，是另一处权限；JENKINS_HOME 自己是 bind 目录属主问题。

修复

因为失败发生在”写不进”阶段、没生成任何文件，无需删目录；chown 后重启即可。

经验教训

  • bind mount 给非 root 容器用，必须先把宿主机目录 chown 成容器运行 uid：jenkins/jenkins 跑 uid 1000，固定 chown 1000:1000。这是 Docker 数据卷最常见的坑之一，和 GitLab 的”坏 gitlab.rb 残留死循环”一样，属于”bind mount 权限/状态残留”大类。
  • 验证监听端口用 ss -ltn | grep 8080 或 curl -I，别用裸 ss（默认只看已建立连接）。
  • group_add: ${DOCKER_GID} 解决的是 docker.sock 访问，JENKINS_HOME 属主是独立问题，两者别混。
  • 想彻底规避：可把 /var/jenkins_home 换成 Docker 命名卷（named volume）——命名卷首次挂载会被镜像内目录的属主（1000）初始化，自动规避此坑；本项目为方便检视目录内容选了 bind mount，故需手动 chown。
