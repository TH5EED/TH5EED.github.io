Docker Compose 与 Kubernetes 编排对比（含 Helm）

文档定位
承接 Docker+Docker Compose部署 的”怎么用 Compose 起服务”，本文聚焦后半段——Compose 与 K8s 编排的本质区别，以及 Helm 在其中扮演的角色。背景来自我们的 CI/CD 学习架构：ci-01（.231）用 Docker Compose 跑 GitLab / Jenkins / Harbor 这套 CI 控制面，而 ArgoCD 必须跑在真 K8s 集群（.221/.222/.223）里做 CD。本文把”单节点 Compose”和”多节点 K8s + Helm”摆在一起讲清，并给出可落地的迁移路径与面试话术。

一、一句话定位（先懂角色，再懂区别）

工具 本质角色 一句话理解
Docker Compose 单机多容器编排器 “在一台机器上，按一份 YAML 把多个互联容器一起拉起来”
Kubernetes 集群级容器编排平台 “跨多台机器调度容器，负责自愈、伸缩、服务发现”
Helm K8s 的包管理器 “把一堆 K8s YAML 变成可复用、可参数化、可版本化的应用安装包”

==核心关系==：Docker Compose 的 docker-compose.yml ≈ Kubernetes 的”多份 YAML 声明” ≈ Helm 的一个 Chart（参数化模板）。三者是同一层的不同实现与抽象级别，不是替代关系，而是递进关系。

二、Docker Compose：能做什么 / 不能做什么

角色：在单台宿主机上，根据 docker-compose.yml 声明式地拉起多个互联容器，并统一管理网络、存储卷、启动顺序。

强项（为什么学习/本地开发几乎都用它）

  • ==隔离==：环境不污染宿主机，docker compose down 一把火全清；
  • ==可复现==：一份文件 = 一套确定环境，换机器照起；
  • ==极简依赖管理==：depends_on 控制启动顺序，networks/volumes 开箱即用；
  • 在我们的架构里，它负责把 GitLab / Jenkins / Harbor 这三个重组件快速、完整地跑在 ci-01 上（见 Docker+Docker Compose部署）。

边界（这是它和 K8s 的根本分水岭）

  • 单机：没有调度器，容器只能落在这台机器上，机器宕机 = 全停；
  • 无自愈：容器挂了不会自动重建（除非 --restart 策略，但那是 Docker 引擎层，不是编排层）；
  • 无弹性伸缩 / 无多副本 HA：想扩到 3 副本跨节点？Compose 做不到；
  • 发布语义弱：没有滚动更新、就绪探针、健康检查这些”生产级”概念；
  • 不适合生产多副本承载真实流量。

学习边界
Compose 是”编排器的最小形态”。用它学 CI/CD 工具链的交互、网络、卷完全够；但一旦涉及多副本、跨节点、自愈、灰度发布，就超出它的设计目标了——这正是 K8s 的领地。

三、Kubernetes：集群级编排平台

角色：把”容器跑在哪台机器上、挂了怎么办、怎么被访问、怎么扩缩”这些事全部接管。

核心抽象（和 Compose 概念一一对应）

  • Pod（最小调度单位，里面是 container）/ Deployment（无状态多副本）/ StatefulSet（有状态）；
  • Service / Ingress（服务发现与暴露，等价于 Compose 的 network + ports）；
  • PersistentVolumeClaim（存储，等价于 Compose 的 volume）；
  • ConfigMap / Secret（配置与密钥，等价于 Compose 的 environment）；
  • 探针（liveness/readiness）、initContainer 等，承担了 Compose depends_on 的”启动顺序 + 健康”职责，且更强。

在我们的环境里，3 节点集群（.221 master + .222/.223 worker，containerd + Calico，详见 K8s家庭集群学习交接文档）承载 ArgoCD + 业务负载，是真正的”生产形态”编排场。

四、Helm：为什么 K8s 需要”包管理器”

痛点：一个真实应用上 K8s，往往要写 N 份 YAML——Deployment、Service、Ingress、PVC、ConfigMap、Secret……重复且难维护。换环境（dev/test/prod）要改一堆文件，升级回滚更是手动活。

==Helm 用三个概念解决它==：

  • Chart：一个应用的模板包（含 Chart.yaml + values.yaml + templates/）；
  • Values：参数文件，用同一份 Chart + 不同 Values 出不同环境；
  • Release：Chart 被部署出来的”一个实例”（带版本、可回滚）。

helm install 时把 Values 渲染进模板，生成最终的 K8s YAML 并提交 apiserver。

能力对照 Compose：

  • helm install / upgrade / rollback / history ≈ Compose 的”启动 + 版本化 + 回退”，但 Helm 原生带版本历史与一键回滚；
  • Chart 可发布到仓库（如 Harbor 的 Helm 仓库），团队复用，≈ Compose 文件但参数化 + 可分发；
  • 类比：Compose 文件像”写死的脚本”，Helm Chart 像”带了变量的安装包”。

在我们的学习路径里，练习④就是”用 Helm 打包一个带 PVC 的有状态应用”（见 K8s解剖练习与CI-CD进阶路线），正好是本篇的实操落点。

Docker Compose Kubernetes Helm 的体现

七、我们的学习路径：从 Compose 平滑迁移到 Helm / ArgoCD

现状：ci-01 用 Compose 跑 GitLab/Jenkins/Harbor（CI 控制面，单节点够用）；K8s 集群跑 ArgoCD + 业务负载（CD 与运行态）。

迁移思路（不是推翻重来，而是”同一批镜像，换个编排器”）

  1. 先把 Compose 里每个 service 对应成 K8s 的 Deployment + Service（用第五节映射表）；
  2. 把 environment/volume/ports 抽成 ConfigMap/PVC/Service；
  3. 用 Helm 把上述 YAML 包成 Chart，用 values.yaml 管理环境差异；
  4. 最后让 ArgoCD（本就跑在 K8s 里）监听 Git 仓库里的 Helm Chart，自动同步部署——这就是 GitOps 闭环。

关键认知
你并不是”只用了 Compose 没碰 K8s”。你的架构是教科书级 GitOps 分层：构建/仓库在外（Compose），部署控制器贴着集群（ArgoCD in K8s）。所谓”单节点 Compose”只是 CI 控制面的合理简化，CD 与负载已经在真 K8s 上了。等 GitLab/Jenkins/Harbor 通了，入场 ArgoCD 时，这篇的映射表会直接变成你执行的 Helm 操作。

八、何时用 Compose，何时上 K8s + Helm

用 Docker Compose 就够的场景

  • 本地开发、单机实验、学习工具链交互；
  • 单节点跑 CI 控制面这类”不需要多副本 HA”的辅助系统；
  • 快速验证一个想法，用完即焚。

上 Kubernetes + Helm 的信号

  • 需要多副本、跨节点、自愈、弹性伸缩；
  • 多环境（dev/test/prod）复用同一套应用定义；
  • 需要滚动更新、金丝雀/蓝绿、配置与密钥统一管理；
  • 团队协作、应用要”可分发、可版本化、可回滚”——这正是 Helm 的强项。

九、面试话术（秋招向）

Q：Docker Compose 和 Kubernetes 有什么区别？

Compose 是单机多容器编排器，解决”在一台机器上把多个互联容器一起拉起来”，没有调度、自愈、多副本 HA，适合开发和单机辅助系统。K8s 是集群级编排平台，跨节点调度、自愈、服务发现、弹性伸缩，面向生产多副本。二者是同一层概念的不同实现——Compose 的 service 对应 K8s 的 Deployment，volume 对应 PVC，network/ports 对应 Service/Ingress。我们家环境就是分层用的：ci-01 用 Compose 跑 GitLab/Jenkins/Harbor，K8s 集群跑 ArgoCD 和业务负载。

Q：Helm 解决什么问题？

K8s 一个应用要写一堆 YAML，换环境重复改、升级回滚麻烦。Helm 是 K8s 的包管理器，用 Chart（模板）+ Values（参数）+ Release（实例）把应用定义参数化、可分发、可版本化，helm upgrade/rollback 原生带历史与一键回退。相当于把”写死的 YAML”变成”带变量的安装包”。

Q：为什么 ArgoCD 必须跑在 K8s 里，而不能像其他组件一样用 Compose 起？

因为 ArgoCD 是 K8s 原生控制器，它本身就是通过 watch K8s API、操作集群资源来实现 GitOps 同步的，离不开 apiserver。用 Compose 在外部起不了它——这也正好体现了”CD 控制器必须贴着目标集群”的 GitOps 设计。
