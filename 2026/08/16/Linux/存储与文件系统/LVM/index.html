各概念介绍

LVM Linux对应
磁盘disk /dev/sda
分区part /dev/sda1,/dev/sda2
物理卷PV /dev/sda2被初始化成了物理卷PV，LVM的基本单位
卷组VG 将一个或多个PV结合成VG，形成大存储池；centos为卷组名
逻辑卷LV 从VG这个存储池中拿出一部分空间作为LV；此时LV相当于传统分区，可格式化，创建文件系统；centos卷组分了两个==灵活隔间==root,home
文件系统 LV作用相当于传统分区：有块组，INode，block；被挂载；ext4文件系统被挂载到了/和/home中

先有卷组作为大仓库，然后在其中划分可改变大小的格子作为逻辑卷，挂载到合适的目录
==扩容性==：如果大仓库不够了，可以再加一块磁盘通过命令进行扩容

实战，如何将多余200GB给到/或者直接给到/opt/qfusion
注意过程中理解物理卷，物理卷组等，以及各通用命令

2026-08-12 补：这个问题被下面的 ci-01 实战完整解答了——给 / 用 growpart 链（场景二）；给 /opt/qfusion 则是把空间 lvextend 给独立 LV 再挂载（对应实习的”数据目录挂盘”）。

场景二：单盘变大的扩容链（ci-01 实战 2026-08-12，==已全部执行==）

上面”新增磁盘 → vgextend”是扩容的路径之一；这次是另一条路径：==现有 PV 所在的虚拟盘变大了==（PVE 把 thin 盘上限从 32G resize 到 100G），guest 里要把新空间一层层传导到文件系统。

两条扩容路径对比

路径 触发场景 关键命令 典型用法
加新盘进 VG 多挂了一块盘 pvcreate → vgextend → lvextend 物理机加盘、数据目录独立盘
单盘变大 虚拟盘上限被调大 ==growpart → pvresize → lvextend → xfs_growfs== VM 磁盘扩容（本次 ci-01）

两条路最终汇合在最后两步：==把 VG 的空闲空间划给 LV，再让文件系统知道==。

实测环境布局（ci-01，Rocky 9 Anaconda 默认分区）

两个实测长出的知识点：

  1. ==VG 名不是教科书里的 rl==：Anaconda 自动分区默认拿装机时的主机名当 VG 名，模板装机时主机名是路由器 DHCP 自动分配的（小米路由器风格命名），所以 VG 名又长又怪。用 vgs 看实际名，==任何脚本都不要硬编码 VG 名==，动态取：findmnt -no SOURCE /
  2. lsblk 与 /dev/mapper 的名字有==转义==：- 是 VG 与 LV 的分隔符，所以真实名字里的 - 显示为 --（rl_miwifi-rd03v2-srv → rl_miwifi--rd03v2--srv-root）。认名字一律以 vgs/lvs 输出为准

扩容命令链（每步对应一层，跳步即断链）

传导路径：磁盘（已 100G）→ 分区 sda2 → PV → VG → LV root → xfs

lvextend -r（-r = –resizefs）可把第 3、4 步合成一步，自动识别文件系统类型调对应扩容。此处拆成两步是为了把原理看清楚。

==2026-08-12 ci-01 全链路执行==：growpart → pvresize → lvextend → xfs_growfs 一次通过，/ 从 31G 扩到 99G，无坑。

“扩了怎么没变大”排查表（每层有自己的验证命令，断在哪层看哪层）：

现象 断点 验证命令
growpart 后 pvs 大小没变 忘了 pvresize pvs / vgs
lvextend 后 df 大小没变 忘了 xfs_growfs df -h /
growpart 报 NOCHANGE 分区号写错 / 盘没变大 lsblk（看整盘 SIZE）

红线与坑

  • ==xfs 只能扩不能缩==（上文”扩缩容”节已记）；thin 盘 + LVM 都遵循”宁小勿大、按需扩”
  • growpart 分区号：Rocky 9 默认布局扩的是 2（sda1 是 /boot），写错轻则报错重则动 boot
  • PVE Resize Disk 对话框填的是==增量==不是目标值（+68 → 100G，填 100 得 132G）
  • 盘符会漂移（总线类型 vd/sd、加盘顺序都影响）：fstab 写 ==UUID==，脚本取路径用 findmnt/blkid

两层”超卖”的关系（PVE thin 池 × guest LVM）

同一个 100G，在宿主和 guest 里是两套互相独立的机制：

宿主侧（PVE LVM-Thin） guest 侧（LVM）
管什么 虚拟磁盘文件的”上限”，按实际写入增长 guest 内部的容量分配
风险点 thin 池写满 → ==所有 VM 一起写挂== VG 空间划错 → 只影响单台
监控 PVE 概要页 nvme 用量，超 70% 警觉 df / vgs

本次扩容动的是 guest 侧链路；宿主侧 thin 上限在关机 resize 时就改好了。两层互不感知——==guest 不知道自己住在 thin 盘上==。
