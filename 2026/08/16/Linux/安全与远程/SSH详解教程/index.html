第一章 · SSH 是什么

SSH（Secure Shell） 是一种加密的网络协议，用于在不安全的网络上安全地远程登录到另一台计算机并执行命令。

它解决的核心问题：明文协议的窃听与篡改。

协议 传输内容 风险
Telnet / rlogin / rsh 明文（含密码） 同网段任何人可抓包拿到密码、篡改命令
SSH 全程加密 即使被抓包，看到的是密文

典型用途：

  • 远程登录shell（ssh user@host）
  • 远程执行单条命令（ssh host "uptime"）
  • 安全文件传输（scp / sftp）
  • 端口转发 / 内网穿透（见第八章）
  • 跳板机（ProxyJump，见第八章）

版本：

  • SSH-1：早期版本，已被证明有设计缺陷，已废弃，不要用。
  • SSH-2：现行标准，本文所有内容均基于 SSH-2。

小知识：你Windows上的 ssh 命令来自 OpenSSH（Win10 1809+ 自带，可在”可选功能”里安装”OpenSSH 客户端”）。

第二章 · 底层原理：如何建立安全通道

一次 SSH 连接大致分三步：TCP 握手 → 密钥与算法协商 → 用户认证。

2.1 两种加密，各管一段

SSH 同时用了非对称加密和对称加密，分工明确：

  • 非对称加密（公钥/私钥）：
    • 用于协商阶段和身份认证。
    • 计算慢，不适合大量数据传输。
    • 典型算法：RSA、Ed25519、ECDSA、Diffie-Hellman（DH）。
  • 对称加密（同一个密钥）：
    • 握手完成后，双方用协商出的**会话密钥（session key）**对后续所有数据加密。
    • 计算快，适合持续通信。
    • 典型算法：AES、ChaCha20。

2.2 会话密钥怎么来的（DH 密钥交换）

双方通过 Diffie-Hellman 算法，在不安全的信道上各自独立算出一个只有彼此相同的会话密钥，而该密钥从未在网络上明文传输。即使攻击者全程抓包，也还原不出会话密钥。

2.3 防中间人攻击（MITM）

设想攻击者在你和服务器之间插一脚，假装自己是服务器。SSH 怎么防？

  • 服务器持有主机密钥（host key）（详见第五章）。
  • 客户端首次连接时，会把服务器主机密钥的指纹记到本地 known_hosts。
  • 以后再连，会比对指纹：不一致就报警 REMOTE HOST IDENTIFICATION HAS CHANGED，提示你可能被中间人劫持。

记住一句话：密码/公钥解决”你能不能进门”，主机密钥解决”这门是不是真的”。

第三章 · 认证方式总览

SSH 支持多种认证（服务端 sshd_config 里配置允许哪些）：

方式 说明 安全性
password 输用户名密码 方便，但易被暴力破解、钓鱼
publickey 用公私钥对，免密登录的核心 推荐，最安全
keyboard-interactive 交互式问答（常配合 PAM/双因素） 可控
GSSAPI 企业域环境（Kerberos） 企业
SSH 证书（CA） 用证书签名代替逐台分发公钥 多机/企业级

本文重点讲 publickey（公钥认证），它是免密登录的基础。

第四章 · 公私钥体系（关键词全覆盖）

这是整篇的核心。先把一组容易混的词理清。

4.1 私钥（private key）与公钥（public key）

  • 私钥：你独自保管的”钥匙”，绝不可泄露、不离开本机。一旦泄露，别人就能冒充你登录。
  • 公钥：由私钥推算出来的”锁孔”，可以放心公开，放到你想登录的服务器上。
  • 数学关系：公钥加密的东西只能用对应私钥解开；私钥签名的东西只能用对应公钥验证。但无法从公钥反推私钥。

4.2 密钥算法类型

ssh-keygen -t <类型> 选择算法：

算法 推荐度 说明
ed25519 ⭐ 首选 椭圆曲线，密钥短、性能好、安全性高
rsa ✅ 兼容好 用 -b 4096 指定长度；老设备兼容首选
ecdsa ⚠️ 一般 椭圆曲线，但实现曾有过随机数问题
dsa ❌ 废弃 已不安全，新版本默认不支持

结论：新机器一律 ed25519；要兼容老设备用 rsa -b 4096。

4.3 密钥指纹（fingerprint）

公钥很长，不好比对。SSH 对公钥做哈希，得到一串短指纹，用于核对身份：

  • 现代格式：SHA256:AbCdEf...（默认）
  • 老格式：MD5:xx:xx:xx:...（用 ssh-keygen -l -E md5 查看）

首次连服务器时屏幕会问你确认主机指纹，就是在做这件事。

4.4 密码短语（passphrase）

私钥本身可以再设一道口令（passphrase）：

  • 不设：谁拿到私钥文件就能直接用（方便但风险高）。
  • 设了：即使私钥文件泄露，对方还要知道口令才能用（安全）。
  • 代价：每次用私钥都要输一次口令 —— 用 ssh-agent 可化解（见第六章）。

4.5 ssh-keygen（生成密钥对）

  • -C 只是给密钥加个注释（方便辨认是谁的），不影响功能。
  • 默认生成在 ~/.ssh/id_ed25519（私钥）和 ~/.ssh/id_ed25519.pub（公钥）。
  • 过程中会提示 Enter passphrase：直接回车=不设口令（纯免密）；输入口令=带锁。

4.7 ssh-agent / ssh-add（私钥管家）

ssh-agent 是一个运行在内存里的”私钥保管箱”：

  • 你只输一次 passphrase，agent 记住解密后的私钥。
  • 之后所有 ssh 都向 agent 借钥匙，不再反复要口令。

适合”私钥带 passphrase 又想免重复输入”的场景。

4.8 用户密钥 vs 主机密钥（先看一眼，第五章详解）

  • 用户密钥（第四章主角）：决定”你能不能登录这台服务器”，放在服务端 ~/.ssh/authorized_keys。
  • 主机密钥（第五章主角）：证明”这台服务器是谁“，放在服务端 /etc/ssh/ssh_host_*。
  • 两者完全独立，互不影响。

★ 第五章 · 主机密钥（Host Key）专题 —— 服务器的”身份证”

这一段专门拆解你提到的命令：
rm -f /etc/ssh/ssh_host_* && ssh-keygen -A
原话要点：主机密钥=服务器身份证，每台唯一；与 authorized_keys 用户密钥是两套东西，不影响免密。

5.1 什么是主机密钥

主机密钥是 SSH 服务端（sshd）的身份凭证，用来向客户端证明”我就是我，不是冒充者”。

  • 文件位置：/etc/ssh/ssh_host_*：
    • ssh_host_rsa_key / ssh_host_rsa_key.pub
    • ssh_host_ed25519_key / ssh_host_ed25519_key.pub
    • ssh_host_ecdsa_key / ssh_host_ecdsa_key.pub
    • （每种算法一对，含私钥+公钥）
  • 生成时机：sshd 首次安装/启动时自动生成；每台机器应当不同。

5.2 主机密钥 ≠ 用户密钥（核心区分）

这是最容易混淆的点，务必分清：

维度 主机密钥（host key） 用户密钥（user key）
回答的问题 “这台服务器是谁？“ “登录的人是谁？“
防什么 中间人冒充服务器（MITM） 未授权用户进门
存放位置 服务端 /etc/ssh/ssh_host_* 服务端 ~/./.ssh/authorized_keys + 客户端私钥
影响免密？ 不影响（重生成它，你照样能免密登录） 决定能否免密

所以你那句结论成立：重生成主机密钥，只是换了服务器的”身份证”，你放在 authorized_keys 里的公钥纹丝未动，免密登录完全不受影响。

5.3 命令逐词拆解

  • rm -f：rm 删除；-f = force，无确认提示直接删（危险，生产环境慎用）。
  • /etc/ssh/ssh_host_*：通配符，匹配所有主机密钥文件，全部删光。
  • &&：逻辑”与”——只有前面删除成功，才执行后面；前面失败则后面不跑。
  • ssh-keygen -A：A = all，为所有支持的算法重新生成”当前缺失的”主机密钥（即把刚删掉的补齐）。
  • 整体语义：把服务器的身份证全部销毁 → 重新签发一整套全新的。

5.4 何时需要这么做

  • 主机密钥被误删，导致 sshd 启动报错/无法提供主机密钥。
  • 怀疑主机私钥曾泄露，想主动”换身份”。
  • 系统初始化脚本里用 ssh-keygen -A 确保主机密钥存在（很多发行版首次启动就是这么干的）。

5.5 ⚠️ 安全大坑：克隆 / 模板镜像共用同一套主机密钥

这是家庭虚拟化（你的 PVE！）最常见的坑：

现象：你从同一个 PVE 模板批量克隆出多台 VM。如果模板里已经带了一套 ssh_host_*，那么所有克隆出来的虚拟机主机密钥完全一致——它们共用同一把”身份证”。

后果：

  1. 客户端 known_hosts 里同一个指纹对应多台不同机器 → 连接时告警混乱。
  2. 更严重：同一把主机私钥分布在多台机器 → 任一台被攻破，攻击者可冒充其它兄弟机器做中间人。

正确做法：

  • 做模板时清掉主机密钥，让每台 VM 首次启动自动生成自己的：
    • 手动：模板里执行 rm -f /etc/ssh/ssh_host_* 后再关机封存。
    • 自动化：用 cloud-init 的 ssh_deletekeys: true + ssh_genkeytypes，首次启动自动重生。

第八章 · 进阶关键词

8.1 端口转发（SSH 的隐藏大招）

把”本地/远端端口”通过加密隧道打通：

  • 本地转发 -L：把远端服务映射到本机端口。
  • 远程转发 -R：把本机/内网服务暴露到远端。
  • 动态转发 -D：建一个 SOCKS 代理，浏览器挂上即可安全翻越。

第九章 · 安全最佳实践

  1. 禁密码登录：免密稳定后 PasswordAuthentication no。
  2. 改默认端口：Port 2222 之类，减少自动化扫描骚扰（不是真安全，但降噪）。
  3. 限制用户/IP：AllowUsers、Match Address 按需收紧。
  4. fail2ban：自动封禁暴力破解 IP。
  5. 私钥妥善保管：设 passphrase、权限 600、备份到安全处；丢了立即从 authorized_keys 撤掉对应公钥。
  6. 多机规范：用 config 别名 + ssh-agent；克隆 VM 务必重置主机密钥（见 5.5）。
  7. 不共享主机密钥：每台机器主机密钥唯一，杜绝克隆镜像共用。

第十章 · 排错速查

现象 可能原因 处理
Permission denied (publickey) 服务端无你的公钥 / 权限不对 检查 authorized_keys 是否写入、~/.ssh 权限 700、私钥 600
Permissions ... are too open 私钥/目录权限过宽 chmod 700 ~/.ssh && chmod 600 ~/.ssh/id_*
REMOTE HOST IDENTIFICATION HAS CHANGED 服务端主机密钥变了 确认无误后 ssh-keygen -R 主机 再连（见 5.6）
连不上 / 超时 IP、端口、防火墙、sshd 未起 ping/TCP 探测；systemctl status sshd；查防火墙
算法不兼容 老客户端 vs 新服务端 服务端加回兼容算法，或升级客户端
仍要密码（想免密却没免） 公钥没上传成功 / 用了错私钥 重跑 ssh-copy-id；ssh -v 看用的是哪个 key

加载模块命令12345# 立即加载 overlay 模块modprobe overlay # 立即加载 br_netfilter 模块modprobe br_netfilter overlay 作用：提供 OverlayFS 联合文件系统支持 在 K8s 中的意义：containerd 使用 OverlayFS 来构建容器的文件系统层级。容器的镜像是分层存储的，OverlayFS 能把多个只读层叠加，再在上面加一个可写层，实现”写时复制”。没有这个模块，containerd 无法正常创建容器的根文件系统，Pod 会启动失败。 br_netfilter 作用：让 Linux 网桥上的流量能被 iptables 规则过滤 在 K8s 中的意义：K8s 的 Pod 网络和 Service 转发大量依赖 iptables。Pod 之间通信数据会经过网桥（如 cni0），如果不加载此模块，这些流量会绕过 iptables，导致 Service 的 ClusterIP 无法访问、Pod 网络策略失效。
