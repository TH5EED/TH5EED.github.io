容器→镜像

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:

commit

底层原理

  • 基于容器当前的文件系统变更，在原有镜像层之上新增一层（即“提交层”）

  • 保留原镜像的所有配置信息（如 ENV、CMD、ENTRYPOINT、EXPOSE、WORKDIR 等）

  • 这些元数据会被复制到新镜像中，可以通过 --change 选项修改它们

    • -a, --author：作者信息

    • -c, --change：应用 Dockerfile 指令到提交的镜像（如 --change='CMD ["app"]'）

    • -m, --message：提交信息

示例

特点

  • ✅ 镜像可以直接 docker run，行为与原镜像基本一致（默认启动命令不变）

  • ✅ 保留多层结构，可追溯历史

  • ❌ 不可复现，别人无法知道容器内做了什么改动

  • ❌ 每次 commit 增加一层，镜像体积会膨胀（即使删除文件，文件仍在历史层中占用空间）

适用场景

  • 临时保存调试现场，后续再整理成 Dockerfile

  • 在 CI 中动态修改镜像并推送（不推荐生产使用）

export+import

export

导出容器的文件系统（即当前所有文件的当前状态） 成一个tar归档，不包含任何镜像元数据

import

  • 将tar归档导入为一个新的镜像，只有文件系统，没有元数据

  • 导入时可以通过--change选项添加一些元数据

特点

  • ✅ 导出文件系统可用于非 Docker 场景（如 chroot、备份）

  • ✅ 导入的镜像是单层，没有历史记录，体积可能变小（但实际大小取决于文件内容）

  • ❌ 丢失所有原有配置（环境变量、端口、工作目录、默认命令等）

  • ❌ 必须手动通过 -c 指定 CMD 等，否则 docker run 会报错（因为没有入口点）

  • ❌ 不保留分层缓存，每次导入都是全新单层

适用场景

  • 提取容器内的文件（如数据卷备份）

  • 制作“静态”镜像，不需要复杂元数据，只要文件系统

  • 迁移容器文件系统到另一个 Docker 环境（但会丢失配置）
