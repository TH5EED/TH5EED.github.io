Pod创建全流程

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:
1. 用户请求

  • 用户通过kubectl命令行工具或者api接口向api-server发送一个REST API请求

  • 提交一个pod的定义，通常是yaml文件或json配置文件来描述pod的详细信息，包括容器镜像，环境变量，资源需求，卷挂载等

2. api server接收请求
  • 用户请求到达apiserver，后者对前者进行认证、鉴权和准入控制——3A检查
3. 持久化存储到etcd

  • 一旦apiserver验证了请求的有效性，会将pod的定义信息写入etcd（分布式键值存储），以确保集群内所有组件都能获取最新的集群状态

  • 此时pod状态为“Pending”

Ｑ：什么是持久化？是否和“以确保集群内所有组件都能获取最新集群状态”有关？难道是持续更新状态？

持久化是指确保数据不丢失（写入磁盘中），状态同步是指确保所有组件看到相同数据（通过Watch机制）

  • 多个etcd节点之间同步复制（通过Raft一致性算法）
  • 保证强一致性（所有节点看到相同的数据）
  • etcd有变化时，api server会通过watch机制收到通知，并转化为API事件
  • 组件不需要知道 etcd的存在，只通过api server获取信息
Q：什么是Watch机制

Watch = 长连接 + 事件推送（替代轮询）

传统轮询 Kubernetes Watch
客户端每秒问”有变化吗？” 客户端建立长连接，等待推送
浪费资源、延迟高 实时、高效
❌ 不适合大规模集群 ✅ 适合海量资源监控
Q：apiserver watch etcd？所以确保组件看到相同数据的主语是api server？所以这也解释了虽然数据存在了etcd中，但调度器，kubelet监听api server获得最新信息？

是的

🔗 链路一（后端数据链路）：APIServer (客户端) vs etcd (服务端)

  • 角色：APIServer 内部有一个叫做 Reflector（反射器） 的组件，它充当 etcd 的专属客户端。

  • 动作：APIServer 启动时，会向 etcd 发起 唯一的 List-Watch 请求。

  • 目的：APIServer 通过这条链路，将etcd硬盘里的数据同步进APIServer自己的内存缓存（WatchCache）中。

  • 运维意义：这条链路只有1条。它确保了即使有几千个节点组件连接过来，etcd 也只承受这1个Watch连接的压力，极大地保护了磁盘IO敏感的etcd。

🔗 链路二（前端业务链路）：kube-proxy (客户端) vs APIServer (服务端)

  • 角色：kube-proxy 内部的 client-go 库（同样是Reflector）充当 APIServer 的客户端。

  • 动作：每个节点上的 kube-proxy 都会向 APIServer 发起独立的 List-Watch 请求（带上过滤参数，只关注 Service 和 Endpoint）。

  • 目的：kube-proxy 通过这条链路，从APIServer的内存缓存（WatchCache）中拿到最新的业务数据，然后去修改本机的 iptables/IPVS 规则。

  • 运维意义：这条链路有N条（取决于节点数量）。APIServer 负责管理这成千上万条长连接，并在内存中将数据分发给各个节点。

4. 调度决策
  • 当pod被创建并保存到etcd后，调度器通过Watch机制监听api server，发现未调度的pod（spec.nodeName为空），触发调度决策
  • 调度器根据集群节点的资源状况，亲和性和反亲和行规则以及其他约束条件，选择最适合该pod的节点，并更新pod状态为“Scheduled”
  • 将调度结果写回api server，再持久化写入etcd，所有组件通过Watch获取最新状态（即kubectl得知本节点被绑定）
Q：什么时候pod被创建了？什么叫api server触发调度器？不是调度器监听api server吗？pod的定义信息被写入etcd，调度器监听api server干什么？

此时pod为逻辑创建，即etcd中由pod的定义信息；调度器主动监听api server，发现未被调度的pod后执行调度

5. 绑定pod到节点
  • 调度器将调度决定通知给api server，由后者将pod与节点进行绑定
6. kubelet执行
  • 相应节点上的kubelet进程通过监听api server事件，得知自己所在的节点需要创建新的pod
  • kubelet从etcd中获取该pod的详细信息，然后开始执行创建pod的具体工作
    • 下载容器镜像（CRI：pull image）
    • 创建网络名字空间和网络策略（CNI流程开始）
    • 设置pod的卷
    • 启动各容器（CRI：create/start container）
7. CNI网络配置流程
  1. kubelet调用CRI创建pod sandbox（pause容器）
    • 创建pause容器+网络名字空间（proc,pid,ns,net）
    • 此时并无IP，路由（网络未配置）
  2. CRI调用libcni库
    • CRI会借助libcni库生成一个json文件描述网络插件如何配置和使用
  3. libcni执行CNI插件（add命令）
    • 构造stdin输入（json格式，包含容器id，netns路径等）
  4. CNI插件实际工作
    • 分配IP
    • 创建veth pair
    • 配置路由
    • 建立跨节点隧道（vxlan，bgp）
    • stdout输出json（含IP，gateway，routes）
  5. libcni接收插件输出，返回给CRI
    • CRI将IP注册到pod状态（status.podIP）
    • kubelet上报给api server，再 持久化写入etcd
8. 启动业务容器（共享网络名字空间）
  • CRI启动容器，复用pause容器的网络名字空间
  • CRI监控容器的生命周期事件，如健康检查，重启策略等
Q：这是不是容器中钩子的工作？

钩子是容器启停的自定义逻辑，CRI管理容器的生命周期。二者不同

9. pod就绪和运行
  • 当所有容器均启动成功并通过了就绪探针检测，kubelet会将pod的状态报告给api server，标记pod为“running”状态
  • 此时的pod可以接收来自service的流量
10. 持续监控与管理
  • 在pod的整个生命周期内，kubelet和api server将持续监听pod的状态，并根据pod的定义和系统策略进行相应的管理和维护操作
  • api server通过watch同步状态变化
  • 若容器异常退出，根据重启策略重新创建
  • 若用户删除pod
    1. kubelet触发生命周期钩子
    2. 调用CRI停止容器
    3. 调用libcni执行CNI插件DEL命令清理网络
