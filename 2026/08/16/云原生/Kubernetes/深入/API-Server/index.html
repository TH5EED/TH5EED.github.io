为什么组件监听API-Server而不是etcd

1. 安全性与权限隔离（审计和RBAC）

  • 运维痛点：etcd 本身是一个没有细粒度权限控制的纯KV存储（只有用户名密码认证，没有“命名空间”或“资源类型”概念）。

  • 如果直连etcd：kubelet 一旦拿到etcd的证书，就能看到整个集群所有Namespace的所有Pod、Secret（密钥），这严重违反了最小权限原则。

  • 为什么监听APIServer：APIServer 是唯一的“安检口”。它会对kubelet的请求做RBAC鉴权（比如只允许kubelet看自己节点上的Pod），并且所有的操作都会记录在**审计日志（Audit Log）**里。出了问题，运维能查日志追责；直连etcd，运维根本不知道是谁干了什么。

2. 数据格式与准入校验（防止脏数据写爆集群）

  • 运维痛点：etcd 只是个“笨仓库”，它不认识 Pod、Service 是什么，它只认二进制或字符串。

  • 如果直连etcd：如果 kubelet 或 kube-proxy 有BUG，或者网络传输出现乱码，直接把一堆乱码写进 etcd，或者直接删掉一个关键key，APIServer 读出来无法反序列化，会导致整个控制平面脑裂或崩溃。

  • 为什么监听APIServer：APIServer 暴露的接口有严格的Swagger/OpenAPI校验。数据必须先经过 APIServer 的准入控制（Admission Webhook）（比如设置默认CPU请求值、校验镜像地址合法性），校验通过、格式正确才会存进去。APIServer 保护了 etcd 数据的一致性。

3. 过滤与性能优化（避免“惊群效应”）

  • 运维痛点：一个生产集群有几千个节点，etcd 里存着几十万条资源对象。

  • 如果直连etcd：etcd 的 Watch 机制是前缀匹配（Prefix），它无法做复杂的过滤。意味着集群里每一个 kubelet 都要从 etcd Watch 全量的所有资源，网络带宽瞬间打满，etcd 的连接数会爆炸（单机撑死几千连接），直接导致集群不可用。

  • 为什么监听APIServer：APIServer 内部有强大的 过滤器（Filter）。kubelet 监听时带上了参数 fieldSelector=spec.nodeName=my-node。APIServer 只把“属于该节点的Pod”推送给这个kubelet。APIServer 是高效的“智能分发器”，极大地减轻了 etcd 和网络的负担。

4. 解耦与容错（APIServer 是“防爆墙”）

  • 运维痛点：etcd 是分布式KV存储，对网络延迟极其敏感（尤其写操作）。kubelet 是节点上的常驻进程，如果节点高负载导致 kubelet 卡顿，或者频繁重连，这种**“笨重客户端”**直接去拖拽 etcd，极易引发 etcd 的 Leader 选举超时。

  • 为什么监听APIServer：APIServer 有自己的 Watch Cache（本地缓存）。当客户端（kubelet）因网络短暂断开后重连，如果发过来的 resourceVersion 太旧（etcd里已不存在），APIServer 不会去查etcd，而是直接返回 410 Gone 让 kubelet 重新 List 全量，并**从本地缓存（Watch Cache）**提供数据。APIServer 用缓存隔离了底层 etcd 的压力，即使 etcd 慢一拍，APIServer 依然可以响应客户端的重连请求。

总结

第一，安全合规。 etcd 没有 RBAC 能力，如果 kubelet 直连 etcd，任何一个被攻破的节点都能拿到全集群的 Secret 数据。APIServer 提供了细粒度的权限控制，并且是唯一能记录审计日志的地方，出了安全事件我们方便溯源。

第二，数据保鲜。 APIServer 有准入控制，能拦截非法格式的写入，保护 etcd 里的数据不被脏数据污染。直连 etcd 等于绕过了安检，后患无穷。

第三，网络减负。 APIServer 能根据 nodeName 做精确过滤，只把本机的 Pod 推送给对应的 kubelet。如果直连 etcd，每个节点都要拉取全集群数据，集群网络会被瞬间打爆。

第四，隔离故障。 如果 etcd 因为磁盘 IO 高出现抖动，APIServer 内部还有 Watch Cache 可以做缓冲降级，尽可能不影响节点上的业务。所以，APIServer 不仅仅是 etcd 的代理，更是 etcd 的‘智能防火墙’和‘流量调度器’。”

审计日志 Audit Log

是什么

  • apiserver在处理每个请求的不同阶段生成审计事件，根据配置的策略进行处理和记录

  • 默认不开启，开启后位于/var/log/下，可通过/etc/kubernetes/manifests/静态资源路径下查看对应yaml文件

  • 生产环境必须开启，并且要配置好--audit-policy-file，避免把apiserver撑爆

作用

审计日志是运维的“眼睛”和“武器”，主要有以下三大用途：

  1. 安全审计与合规：这是最核心的用途。它可以回答“谁在什么时候做了什么”这类关键安全问题。对于需要满足 CIS（Center for Internet Security）Kubernetes Benchmark 等安全标准的集群，审计日志是必须开启的功能。

  2. 故障排查与根因分析：当集群出现异常时，审计日志是定位问题的第一手资料。例如：

    • RBAC权限问题：当出现 Forbidden 错误时，可以快速定位是哪个用户或ServiceAccount因权限不足被拒绝。

    • 资源变更追踪：可以查看谁在何时修改或删除了关键资源（如Deployment、ConfigMap）。

    • 安全事件调查：当怀疑集群被入侵或存在异常操作时，审计日志是调查取证的核心依据。

  3. 集群监控与告警：通过将审计日志接入到监控系统（如ELK、Splunk），可以设置告警规则。例如，当检测到某类敏感操作（如删除Namespace、创建高危特权容器）时，系统可以自动发出告警。

策略

审计日志不是什么都记，而是通过审计策略（Audit Policy） 来精细控制记录的内容。策略文件（通常是 audit-policy.yaml）通过 --audit-policy-file 参数传递给 kube-apiserver。

策略的核心是规则（Rules） 和级别（Level）。处理事件时，会按顺序匹配规则，第一个匹配的规则将决定该事件的审计级别（Audit Level）：

级别 (Level) 记录内容 适用场景
None 不记录任何信息。 对于一些高频、无安全风险的请求（如kube-proxy的定期健康检查），可以配置此级别以减少日志量和降低APIServer内存消耗。
Metadata 只记录请求的元数据：用户、时间戳、资源、操作动词（verb）等，不包含请求体和响应体。 这是最常用的级别，平衡了信息量和性能开销。适合绝大多数常规审计需求。
Request 记录元数据和请求体，但不记录响应体。 当需要知道请求的详细内容（如创建Pod时的完整YAML）时使用，但会消耗更多资源。
RequestResponse 记录元数据、请求体和响应体。 信息最全，但开销最大。只建议在需要详细排查特定问题时，对特定资源（如pods）开启。

运维提示：审计日志会增加APIServer的内存消耗。因此，在生产环境中，务必要精心设计审计策略，避免记录过多不必要的信息，防止对APIServer性能造成影响。

启用和查看

  1. 创建审计策略文件：在Master节点上创建 /etc/kubernetes/audit-policy.yaml 文件，并根据需求编写规则。

  2. 配置kube-apiserver：修改 kube-apiserver.yaml 文件，添加以下几个关键启动参数：

    • --audit-policy-file=/etc/kubernetes/audit-policy.yaml：指定策略文件路径。

    • --audit-log-path=/var/log/kubernetes/audit.log：指定日志文件路径。

    • --audit-log-maxage=30：日志文件保留天数。

    • --audit-log-maxbackup=10：保留的旧日志文件最大数量。

    • --audit-log-maxsize=100：日志文件在轮转前的最大大小（MB）。

    • --audit-log-format=json：指定日志格式为JSON。

  3. 重启kube-apiserver：保存配置后，kube-apiserver通常作为静态Pod运行，会自动重启并加载新配置。

查看日志：配置生效后，审计日志会写入你在 --audit-log-path 指定的文件中。你可以直接在Master节点上使用 tail、grep 等命令查看，或者将日志接入到EFK、ELK等集中式日志系统，以便于检索和分析。
