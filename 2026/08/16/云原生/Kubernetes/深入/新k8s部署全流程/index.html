K8s 组件版本推荐

组件 推荐版本 说明
Kubernetes 1.32.x 2026 年 8 月稳定版，文档丰富
containerd 2.3.3 已安装，不用降级；K8s 1.30+ 起官方支持
kubeadm/kubelet/kubectl 1.32.x 三者版本必须严格一致
Calico 3.29.x 或更新 按 Calico 官方对照表选对应 K8s 1.32 的版本

版本选择原则（面试可讲）：

  • kubeadm/kubelet/kubectl 小版本必须一致（如 1.32.x），大版本差 1 以内可容忍
  • containerd 2.x 已 GA，兼容 K8s 1.30+；学习集群直接保留已安装的 2.3.3
  • CNI（calico）版本与 K8s 版本对照表看官方文档

每台节点安装步骤（面试核心技能）

这是你简历上”手动部署 K8s”的实操部分，每一步都要能讲清为什么。

第一步：加载内核模块 + 设置 sysctl（所有节点）

面试话术：

  • br_netfilter：让网桥流量经过 iptables 处理，K8s 的 Service/NetworkPolicy 依赖这个
  • overlay：containerd 默认使用的存储驱动
  • ip_forward=1：允许 IP 转发，Pod 跨节点通信必需

第二步：安装 containerd（所有节点）

当前已安装版本为 containerd.io-2.3.3，无需卸载，保持三台一致即可。

==铁律：改过 /etc/containerd/config.toml 必须 systemctl restart containerd==

面试话术：

  • containerd 是容器运行时，kubeadm 1.24+ 不再内置 dockershim，必须用 containerd 或 CRI-O
  • SystemdCgroup = true：让 containerd 使用 systemd 作为 cgroup 驱动，与 kubelet 保持一致（kubelet 默认用 systemd）
  • cgroup 驱动不一致会导致 kubelet 启动失败

第三步：安装 kubeadm/kubelet/kubectl（所有节点）

如果 v1.32 仓库还不可用，把上面 URL 中的 v1.32 换成 v1.31，containerd 2.3.3 同样兼容。

面试话术：

  • kubeadm：集群引导工具，负责生成证书、启动控制平面、生成 join 命令
  • kubelet：节点代理，每个节点必跑，负责管理 Pod 生命周期
  • kubectl：命令行客户端，只在 master 或管理节点用
  • kubelet 必须开机自启，因为它是 systemd 管理的，控制平面组件（apiserver 等）是 kubelet 拉的 static Pod

第四步：验证安装（所有节点）

3. 加速与验证

验证集群

业务镜像加速（docker.io，所有节点，2026-08-10 实测可用）

业务镜像大多来自 docker.io，逐个手动拉不现实。containerd 的 certs.d 加速机制对 docker.io 实测有效（master 上 busybox、nginx:alpine 约 6 秒拉完；对照：直连 docker.io 纯超时）。

为什么 docker.io 行、registry.k8s.io 不行（同机制不同结果，面试可讲）：

  • containerd 加速探测会带 ?ns=<原始仓库> 参数。达欧云本职就是 docker.io 代理，?ns=docker.io 是它的原生业务，全程支持
  • 阿里的 google_containers 只是 registry.k8s.io 的另一个仓库布局，不认 ?ns=registry.k8s.io 的跨命名空间探测，回 404 → 回退原始源超时
  • 解析链路：image: nginx:alpine → 补全 docker.io/library/nginx:alpine → 查 certs.d/docker.io/hosts.toml → 先试达欧云，失败才回退原始源

公共加速源不保证永久可用，兜底方案：可达源全名拉 + ctr -n k8s.io images tag 打标准名。CI/CD 阶段业务镜像主要来源是自己的 Harbor（内网直拉，无需加速），docker.io 加速主要服务开源基础镜像。

实测附带结论：systemctl restart containerd 不会杀正在运行的容器（shim 进程独立存活），重启期间 13 个 Pod 全部保持 Running。

踩坑实录（2026-08-10 实战，全部已验证修复）

  1. init 卡 wait-control-plane（4 分钟后 API server unhealthy）
    • 首查：==改 containerd 配置后没重启==。stat -c %y /etc/containerd/config.toml 对比 systemctl show -p ActiveEnterTimestamp containerd
    • 实锤证据在 journalctl -u kubelet：RunPodSandbox failed ... failed to pull image "registry.k8s.io/pause:3.10": not found——四个 static Pod 全死在创建 sandbox 这一步
    • preflight 阶段出现 sandbox image "" 警告就是 pause 不可用的信号
  2. pause 不在 kubeadm config images pull 的 7 个镜像里：组件镜像由 kubeadm 带阿里仓库名直拉；pause 由 CRI 按 registry.k8s.io/pause:3.10 现拉，要单独绕（阿里全名拉 + ctr images tag 打标准名）
  3. certs.d 镜像加速对 registry.k8s.io → 阿里云组合无效：阿里云对带 ?ns=registry.k8s.io 的 HEAD 探测回 404，containerd 按协议回退原始源（谷歌）超时。统一绕法：可达源全名拉 + 本地打标签，CRI 本地命中就不远程拉
  4. calico Init:ImagePullBackOff：docker.io 同样被墙。达欧云（docker.m.daocloud.io）实测可用约 6MB/s；镜像源选型探测法：curl -m 8 https://源/v2/ 返回 401/200 = 可达，000 = 不可达
  5. 多行命令反斜杠截断：kubeadm init \ 某行漏反斜杠（或反斜杠后带空格），bash 静默只执行前半段，参数悄悄丢失
  6. 重新 init 前先 kubeadm reset -f：否则 preflight 报 manifest “already exists”、10250 端口占用；reset 会删 /etc/crictl.yaml，正常现象，init 自动重建
  7. worker 不做准备就 join = 重演 master 故障：pause 版本修正 + 打标签 + kube-proxy 预拉，三件套缺一不可

三个组件解剖练习（集群就绪后）

  1. Static Pods：ls /etc/kubernetes/manifests/，看 apiserver/etcd/scheduler/controller-manager 的 YAML，理解 kubelet 如何拉起控制平面
  2. etcd 备份恢复：etcdctl snapshot save /tmp/etcd.db，停 etcd 观察集群状态，恢复
  3. TLS Bootstrap：kubeadm token create，在 worker 上 join 时观察 CSR 批准流程

集群状态（2026-08-10 建成）：三节点全部 Ready，kube-system 13 个 Pod 全 Running（控制面 4 static Pod + etcd 含内、kube-proxy ×3、calico-node ×3、calico-kube-controllers、coredns ×2）。下一步：三个组件解剖练习 → CI/CD 平台（见《闭关虚拟机部署规划》Step 2）。
