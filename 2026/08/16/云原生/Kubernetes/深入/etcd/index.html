etcd

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:

详看exp-etcd

原理

etcd 是 K8s 的唯一数据存储（single source of truth）。

集群的一切状态——Pod/Service/ConfigMap/Secret/Node/RBAC——全存在 etcd 里。

kube-apiserver 是 etcd 的唯一客户端，其余组件（scheduler/controller-manager/kubelet）都通过 apiserver 间接读写。

这意味着：

  • etcd 挂 = 集群”脑死亡”：apiserver 无法读写 → kubectl 超时、无法调度新 Pod、controller-manager 无法 reconcile
  • 但已运行 Pod 不会立即消失：kubelet 在本地缓存了 Pod 声明，etcd 挂了 kubelet 仍按缓存继续管理已运行容器 → 数据面（running pods）幸存于控制面故障

为什么 K8s 敢这么设计？
这是 K8s “声明式 + 最终一致”架构的核心取舍：控制面和数据面解耦。etcd 挂了只是”无法变更意图”，已部署的工作负载继续服务。面试时讲清这一点 = SRE 视角的可用性理解。

==TLS 双向认证：etcd 只接受带客户端证书的连接；证书在 /etc/kubernetes/pki/etcd/==

备份

操作 时机 机制 是否在线
snapshot save etcd 运行中 通过 etcd API 获取一致性快照（复制 boltdb 数据文件 + metadata） 在线，不中断服务
snapshot restore etcd 必须停止 从快照文件重建数据目录（新 boltdb + 新 WAL 初始化） 离线，运行时 restore 会损坏数据

snapshot save 做了什么：调用 etcd 的 Maintenance/Snapshot API → etcd 在内部对 boltdb 做一次一致性的数据文件拷贝 → 返回给 etcdctl 写入文件。这是逻辑快照（通过 API 获取），不是文件级 cp。

snapshot restore 做了什么：读取快照文件中的 boltdb 数据 → 在指定 --data-dir 下创建全新数据目录结构（member/snap/db + member/wal/ 初始化 WAL）→ 新 etcd 启动时从这个点开始。

Raft选举机制

场景 Raft 行为 你的集群
单 etcd 退化为单节点，无选举、无脑裂 你现在就是这个
3 etcd quorum=2，容忍 1 个挂 实习时 QFusion 生产环境
5 etcd quorum=3，容忍 2 个挂 大规模生产

Raft 保证：写操作必须经 quorum（n/2+1） 成员同意才提交。单 etcd 没有这个问题（自己就是 leader），但也意味着 SPOF——挂了就是挂了，没有容错。
