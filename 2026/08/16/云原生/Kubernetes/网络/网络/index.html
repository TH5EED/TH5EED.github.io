网络

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:

核心网络设计原则

  • 所有Pod无需NAT即可直接通信（IP可达）
  • Pod与Node之间也可直接通信
  • 每个Pod拥有独立的IP，且此IP在整个集群全局唯一，可路由

这就被称为扁平网络，即所有Pod像在同一台交换机上

GCE（理想）

在Google Compute Engine里，默认支持该原则，无需额外配置网络插件即可满足扁平网络要求

私有云和自建机房（现实）

问题所在

  • 各节点处于不同子网或隔离 VLAN
  • 节点间默认不能直接路由 Pod IP
  • Docker 默认用 docker0 网桥（仅本机 Pod 互通，跨节点不通，违反了第一条扁平原则）

解决方案

  1. 部署 CNI 插件（如 Calico/Cilium/Flannel）→ 实现跨节点 Pod 通信

    • Flannel：用 VXLAN 或 Host-GW 封装 Pod 流量
    • Calico：用 BGP 或 IPIP 实现三层路由
    • Cilium：基于 eBPF 实现高性能网络策略与路由

  2. 确保网络连通性前置

    • 在启动 kubelet 之前，必须确保
      • 所有节点能互相访问（Node ↔ Node）
      • Pod IP 能在节点间路由（通过 CNI 插件配置路由表或隧道

CNI

插件机制

k8s自身不实现网络功能，而是定义接口规范（即 CNI）
通过插件化方式集成多个网络插件，实现扁平网络

CNI 标准中定义的核心接口操作：

  • add，将容器添加到网络
  • del，从网络中删除一个容器
  • check，检查容器的网络是否符合预期

网络模型

非封装网络underlay network

  • 本质：物理网络层L2、L3，真实存在的网络设备与链路
  • 实现方式：使用交换机，路由器
  • 可达性保证：保证任意两点可达——依赖物理拓扑和路由协议BGP
  • 典型技术：VLAN，BGP-based routing（Calico的BGP模式），IPvlan

封装网络overlay network

  • 本质：逻辑网络层，物理网络之上虚拟化构建的网络，屏蔽掉了用户不需要知道的信息
  • 实现方式：隧道技术（VXLAN，GRE等）在IP包中封装原始数据包
  • 可达性保证：逻辑上全连通，不依赖底层拓扑
  • 典型技术：VXLAN（Flannel，Calico的VXLAN模式），GRE

注意

非封装≠不用IP，而是指不额外加封装头，直接在物理网络上传输容器流量

路由转发

一种外部网关协议，用于在互联网上交换路由和可达性信息

BCP可以帮助进行跨集群pod之间的网络，此功能对于未封装的CNI网络插件是必须的，并且通常由BCP完成。如果你想构建跨网段拆分的集群，路由分发是一个很好的功能

网络策略

Kubemetes提供了强制执行规则的功能，这些规则决定了哪些service可以使用网络策略进行相互通信。这是从Kubemetes1.7起稳定的功能，可以与某些网络插件一起使用

网格

允许在不同的Kubernetes集群间进行 service之间的网络通信

外部数据存储

具有此功能的CNI网络插件需要一个外部数据存储来存储数据

要么使用api接口即通过api server连接etcd，要么外部创建一个etcd
更多使用后者，但前者不能没有

加密

允许加密和安全的网络控制和数据平面

Ingress/Egress 策略

允许你管理Kubernetes 和非 Kubemetes 通信的路由控制

Calico

本质

  • 纯三层的虚拟网络，不使用二层广播、ARP、网桥转发，而是通过IP路由实现pod间通信
  • 没有复用docker的docker0网桥，而是自己实现
  • 不需要NAT和端口映射

三种模式

模式 封装 网桥 路由方式 适用场景
BGP (Underlay) ❌ 无 ❌ 可无 BGP + 内核路由 物理机集群、裸金属、高性能要求
VXLAN (Overlay) ✅ VXLAN ✅ cni0 VTEP 封装 云环境（AWS/GCP）、网络隔离强需求
IPIP (Overlay) ✅ IP-in-IP ✅ cni0 IPIP 隧道 兼容老内核、简单部署

非封装网络的CPU开销最低，网络带宽无损耗，但是最复杂，需要物理网络管理（三层交换机或路由器）
如果是公有云环境，用户无法接触底层物理网络设备，所以选择VXLAN或ip-in-ip更稳妥
