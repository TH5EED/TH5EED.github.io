k8s 网络模型完全指南

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:

从 Pod 通信到 Service 负载均衡

K8s 集群里几百个 Pod 是怎么互相通信的？Service 背后的负载均衡到底怎么实现？为什么 Pod 重启后 IP 就变了？本文把 K8s 网络的核心机制一次讲透，配图 + 命令 + YAML，看完就能上手。

一、K8s 网络的四条铁律

K8s 网络看似复杂，但底层只有四条规则，所有网络插件都必须遵守：

规则 描述 一句话理解
所有 Pod 直接通信 不需要 NAT 同事之间直接喊名字
所有 Node 直接通信 不需要 NAT 两个办公室之间走廊畅通
Pod IP = 真实 IP 无地址转换 你的手机号就是别人拨你的号
跨 Node Pod 直通 网络对 Pod 透明 不同楼层的人感觉在同一层

一句话总结：K8s 要的是一个”扁平网络”——所有 Pod 像在同一台交换机上。

Docker 默认的 bridge 网络用 NAT 做端口映射，违反了第一条规则。所以 K8s 不用 Docker 网络方案，改用 CNI 插件。

二、Pod 是怎么通信的？

同节点：veth pair + 网桥

每个节点上有一个网桥（如 cbr0），每个 Pod 通过 veth pair（虚拟网线）连上去：

┌─────────────── Node A ──────────────┐
│ ┌──────┐ veth ┌──────┐ veth ┌──┐ │
│ │Pod-1 │─────│ cbr0 │─────│P2│ │
│ │.1.2 │ │ │ │.3│ │
│ └──────┘ └───┬───┘ └──┘ │
│ │ eth0 │
└──────────────────┼─────────────────┘
│
物理网络（路由/VXLAN）
│
┌──────────────────┼─────────────────┐
│ │ eth0 │
│ ┌──────┐ veth ┌──┴───┐ │
│ │Pod-3 │─────│ cbr0 │ │
│ │.2.2 │ │ │ │
│ └──────┘ └───────┘ │
└────────────────────────────────────┘

Pod-1 发包给 Pod-2 → 通过 veth 到网桥 → 按 MAC 转发 → Pod-2 收到。零开销，就跟同一台机器上一样。

跨节点：三种方案

方案 插件 原理 推荐场景
路由模式 Calico 节点间路由表，直连转发 ⭐ 生产首选
Overlay Flannel VXLAN 物理网络套虚拟网络 学习/测试
eBPF Cilium 内核层面处理，绕过 iptables 追求高性能

💡 生产环境推荐 Calico 或 Cilium。Flannel 适合学习和测试，但功能有限。

三、Service：Pod IP 总是变的怎么办？

Pod 的 IP 不固定（重建就变）、副本数动态变化、故障会迁移到其他节点。如果直接连 Pod IP，每次变化都要改配置——这不现实。

Service 就是解决方案：一个稳定的虚拟 IP + DNS 名称，自动负载均衡到后端 Pod。

Client ──→ Service (ClusterIP: 10.96.0.100)

　　　　 + DNS: my-app.default.svc.cluster.local

　　　　├──→ Pod-1 (10.244.1.2)

　　　　├──→ Pod-2 (10.244.2.3)

　　　　└──→ Pod-3 (10.244.2.5)

五种 Service 类型

类型 用途 典型场景
ClusterIP（默认） 集群内部访问 微服务互相调用
NodePort 每个节点开端口 开发测试
LoadBalancer 云厂商负载均衡 云上对外暴露
ExternalName DNS 别名 引用集群外服务
Headless 不分配 VIP StatefulSet

最常用的是 ClusterIP，一个 YAML 就搞定：

apiVersion: v1
kind: Service
metadata:
name: my-backend
spec:
selector:
app: my-backend # 通过标签匹配后端 Pod
ports:

  • port: 80 # Service 端口
    targetPort: 8080 # Pod 端口

⚠️ NodePort 端口范围固定 30000-32767，生产环境别用它暴露服务。

四、kube-proxy：Service 背后的流量转发

Service 的 ClusterIP 怎么变成真实的 Pod IP 转发？答案是 kube-proxy。它运行在每个节点上，监听变化并动态配置网络规则。

三种代理模式

模式 原理 性能 推荐度
iptables 随机概率规则 O(n)，规则多时慢 默认，小集群够用
IPVS 哈希表查找 O(1)，多种调度算法 ⭐ 推荐
nftables 新一代防火墙 优于 iptables K8s 1.29+

IPVS 支持轮询（rr）、最少连接（lc）、源地址哈希（sh）等算法，比 iptables 的随机概率更灵活。

💡 建议：新集群直接用 IPVS 模式，后续扩展不用担心性能瓶颈。

Endpoints：Service 的”地址簿”

kube-proxy 转发到的 Pod IP 来自 EndpointSlice（新版）。Pod 增减时自动更新，kube-proxy 感知后刷新规则。

五、DNS：为什么 Service 名能直接用？

K8s 内置 CoreDNS，自动为每个 Service 生成 DNS 记录。

命名规则：<service>.<namespace>.svc.cluster.local

完整域名

my-backend.default.svc.cluster.local

同命名空间可省略

my-backend

Pod 的 /etc/resolv.conf 自动注入 DNS 配置，关键参数 ndots:5 决定了查询顺序——查 my-backend 时会自动拼 search 域，所以同命名空间内直接用 Service 名就行。

Headless Service（ClusterIP: None）不分配 VIP，DNS 直接返回所有 Pod IP 列表——StatefulSet 必须搭配 Headless Service，每个 Pod 有稳定 DNS：mysql-0.mysql-headless.default.svc.cluster.local

六、Ingress：一个域名搞定多个服务

多个 HTTP 服务要暴露到外网，每个开一个 NodePort？太乱了。Ingress 在七层做路由，按 Host + Path 分发：

api.example.com/v1 → api-service

www.example.com/  → frontend-service

⚠️ Ingress 资源只是规则定义，真正干活的是 Ingress Controller（如 NGINX Ingress），需要额外部署。

七、NetworkPolicy：谁能跟谁说话？

K8s 默认网络全通——所有 Pod 可以互相访问。生产环境不够安全。

八、网络排查速查表

Pod 网络问题？
├── DNS 解析失败 → 检查 CoreDNS + resolv.conf + ndots
├── Service 不通 → 检查 Endpoints + selector 是否匹配
├── 同节点 Pod 不通 → 检查 CNI 网桥 + veth
├── 跨节点 Pod 不通 → 检查路由 + CNI + ip_forward
├── Pod 访问外网不通 → 检查 SNAT + iptables
└── 外部访问不通 → 检查 NodePort/LoadBalancer/Ingress

九、核心要点

组件 解决什么问题 推荐方案
CNI Pod 网络连通 Calico / Cilium
Service 稳定 VIP + DNS ClusterIP + Ingress
kube-proxy Service → Pod 转发 IPVS 模式
CoreDNS DNS 解析 默认安装
Ingress HTTP 七层路由 NGINX Ingress
NetworkPolicy 网络隔离 按需配置

请求路径全景：

**外部：**Client → Ingress → Service → kube-proxy → Pod

**内部：**Pod A → CoreDNS → Service → kube-proxy → Pod B
