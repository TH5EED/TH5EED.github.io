控制器

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:

详看kube-controller-manager
用来不断地确保集群当前状态与期望状态（spec）保持一致

  • 当一个pod损坏（可能所处节点损坏）时，控制器会重建一个pod来尽量满足期望

  • 当一个pod的容器损坏（进程被杀死）时，只要pod的重载策略是always，pod就会重建一个新容器并重启，RESTARTS字段+1

任务模型分类

  • 守护进程/长期运行型：deploy，ds，sts
    场景：数据库sts，web服务器deploy，监控代理ds
    无状态服务：web服务器→deploy
    有状态服务：数据库→sts

    • 无状态服务的每个实例都是完全相同且可相互替换的。它本身不保存任何需要持久化的数据，每次处理请求都是独立的。它的“状态”通常保存在外部的数据库或缓存中

    • 有状态服务需要持久化存储来保存数据，Pod重启或迁移后数据不能丢失。同时，它的每个实例通常需要一个稳定、唯一的网络标识，以便其他服务能准确找到它

  • 批处理型：job，cronjob
    场景：数据迁移，备份

二者区别在于对于pod的重启策略restartPolicy不同

  • Always：容器退出会被视为异常，必须重启

  • OnFailure：成功退出（返回码为0），结束；失败才会重启

  • Never：顾名思义，无论成功退出失败退出

默认

  • Deployment / ReplicaSet / DaemonSet / StatefulSet：默认 Always

  • Job：默认 OnFailure（或显式设置为 Never）

  • CronJob：继承 Job 的模板设置

Pod名称特征 上一级资源类型 实例

  • operator：In, NotIn, Exists, DoesNotExist

滚动更新

deploy的默认更新策略，能够实现零停机更新
它通过逐步替换pod来完成更新，始终保持一定数量的pod在运行，从而确保服务在整个更新过程中都可用

推荐通过修改清单文件然后apply，即方法二

更新过程中，可以超出期望副本数的最大百分比（maxSurge）和不可用副本的最大百分比（maxUnavailable），默认都是 25%

[!金丝雀部署（deploy不完全支持）]
用极少的数量测试当前版本的稳定性
deploy的做法最好是两个deploy共享一个svc，调整副本数比例

回滚更新

清理策略

方法一
旧rs在etcd中，作为记录，想要回滚依赖etcd中的旧rs，可以利用rollout命令回滚

方法二
设置spec.revisionHistoryLimit=0→etcd中不再存放旧rs
每次更新，用不同yaml文件，文件名记录更新时间，人物，内容
保存在磁盘中作为更新记录，想要回滚使用apply命令

避免了多次回滚并行的现象

DS

特性

  • 会忽略节点上的unschedulable状态，即node.kubernetes.io/unschedulable 污点，但会尊重其他污点

  • 确保集群上全部（或一些）节点上运行一个pod副本，动态匹配

  • 支持滚动更新

使用场景

  • 节点级别的监控代理（如 Prometheus Node Exporter）

  • 日志收集器（如 Fluentd、Filebeat）

  • 网络插件（如 Calico、Flannel 的节点代理）

  • 存储插件（如 Ceph 客户端）

示例（Fluentd日志收集）

STS

特性

有状态服务，为有状态应用设计的控制器

  • 有序创建，逆序删除

  • 稳定的持久化存储（每个pod绑定独立的PVC，重建后仍挂载同一卷）

  • 稳定的网络访问方式（pod的名称固定，重启后不变）
    域名：<pod-name>.<headless-svc-name>.<namespace>.svc.cluster.local

使用场景

  • 数据库（MySQL、PostgreSQL、MongoDB）

  • 消息队列（Kafka、RabbitMQ）

  • 分布式存储（Elasticsearch、HDFS）

Job

特性

Job 负责运行一个一次性任务，直到任务成功完成（容器退出码为 0）才结束
如果失败，Job 会根据重启策略和重试限制自动重试

关键字段

spec.completions需要成功退出的pod数，默认1
spec.parallelism最大并行pod数，默认1
spec.backoffLimit失败重试次数，默认6
spec.activeDeadlineSeconds失败pod的重试最大时间，超过则不会继续重试，无限制
ttlSecondsAfterFinished任务结束后多久自动清理pod，默认一直保留，即completed

使用场景

  • 数据库迁移

  • 批量数据导入/导出

  • 运行计算任务（如 Pi 值计算）

  • 定期备份（结合 CronJob）

CronJob

特性

CronJob 是一个定时创建 Job 的控制器，类似于 Linux 的 crontab
在每个设定的时间点，CronJob 会创建一个 Job 对象，由 Job 去启动 Pod

使用场景

  • 每天凌晨备份数据库

  • 每小时清理临时文件

  • 每周生成报表

关键字段

spec.schedulecron表达式，指定任务运行周期，必填
spec.jobTemplate job模板
spec.successfulJobHistoryLimit和spec.failedJobHistoryLimit 历史限制，指定etcd可保留多少完成和失败的pod，默认3和1（批处理类型没有版本一说，不必考虑回滚）

题目

  1. deployment 属于 k8s 的什么资源？
    控制器，pod上一层的资源

  2. k8s 有哪些探测手段？
    就绪，存活，启动

  3. k8s 中设置污点的命令是？
    kubectl taint nodes <node-name> key=value:effect

  4. 污点有哪些排斥等级？
    NoSchedule 不能被调度
    PreferNoSchedule 尽量不被调度
    NoExecute 新pod不被调度，旧pod不容忍被驱逐

  5. pod 有哪些状态？
    pending 创建未被调度
    running 至少一个容器在运行
    succeed 所有容器成功退出
    failed 至少一个容器失败退出
    unknown 失联

  6. 如何通过 rs 实现 pod 的副本数变成 5？
    kubectk scale replicaest <rs-name> --replicas=5

  7. 使用什么命令能够直接修改某个资源的属性，不使用 yaml 文件？
    kubectl scale 可以修改副本数
    kubectl set 可以修改镜像
    如果说任意属性需要kubectl edit <resourse> <name>
    打补丁用patch

  8. 如何驱逐某个节点上的 pod？
    kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data
