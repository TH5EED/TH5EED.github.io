集群安全机制

发表于2026-08-16|更新于2026-08-16|云原生
|浏览量:

安全机制说明

  • 围绕api-server设计，因为它是集群内部各组件通信的中介，也是外部控制的入口

  • Authentication：认证

  • Authorization：鉴权

  • AdmissionControl：准入控制

（附件缺失：../assets/集群安全机制/Pasted%20image%2020260707141912.png）

认证

认证模式

  • HTTP Token：一串长字符串token作为表达用户的方式，存储在apiserver能访问的文件中，当客户端发起api请求，需要在HTTP Header中放入token供服务端验证

  • HTTP Base：基于用户的认证。用户+密码通过base64编码后，用户将其放入HTTP Request的认证域中发送给服务端，服务端解码验证

  • HTTPS：基于CA根证书的客户端身份认证方式

前两个是单向认证，第三个HTTPS双向认证mTLS（HTTPS也有单向：客户端验证服务端）

（附件缺失：../assets/集群安全机制/Pasted%20image%2020260707151240.png）

服务端和客户端都会用ca.crt去验证对方发来的crt证书

  • API Server (kube-apiserver)：集群的访问入口，必须配置TLS双向认证。它通过以下启动参数指定证书:

    • --tls-cert-file：指定其服务端证书。

    • --tls-private-key-file：指定其服务端私钥。

    • --client-ca-file：指定用于验证客户端证书的根CA证书。

  • 客户端：所有与API Server交互的组件和工具（kubectl, kubelet, kube-scheduler, kube-controller-manager, kube-proxy等）都需要配置自己的客户端证书，以便在发起请求时出示

需要认证的

  • 组件（如果有些以pod运行，但集群默认组件依旧按组件算）：封装成kubeconfig文件

    • 无需加密：
      基于kubeadm部署的与apiserver处同一节点的controller manager，scheduler
      通过127.0.0.1非安全地址访问即可

    • 需要加密：

      • 证书手动颁发
        kube-proxy、kubectl

      • 自动颁发
        kubelet

  • pod（dns,calico）：
    ServiceAccount：sa.crt，token，namespace

ServiceAccount

pod的创建，销毁是动态的，为它手动生成证书不可行，所以使用ServiceAccout解决访问apiserver的认证问题
