为什么需要 Volume（存储卷）

  1. 容器重启丢失数据：容器重建后，会恢复镜像最初状态，日志或生成文件全丢

  2. Pod 内多容器文件隔离：一个 Pod 里的多个容器（如主容器+日志采集Sidecar）默认无法互通文件

  3. 节点漂移：Pod 被调度到其他节点后，原来的本地文件就找不到了

核心定律：Volume 是 Pod 级别的资源（先定义 spec.volumes，再在 spec.containers.volumeMounts 里挂载），一个 Pod 可同时挂载多个 Volume

临时/本地存储（无持久化或半持久化）

emptyDir

  • 用于pod内部多容器文件共享，
    ==如为了减小镜像体积，可以将一些启动文件让初始化容器wget下载，再保存到emptyDir中，主容器挂载同一个volume读取==

  • 生命周期与pod一致

  • 存储位置为节点临时目录（kubelet管理），最初为空

  • 性能模式：加上medium: "Memory"，会挂载宿主机内存文件系统，读写极快，但会消耗pod的内存限额

hostPath

  • 让节点读写宿主机上的特定目录，如监控采集/var/log

  • pod删除或重建，数据依然存在

  • 用来存重启后仍然希望保留的数据，如日志、临时包等，和PV、PVC一样用来存持久化数据

  • 缺点：不能跨pod共享，除非另一个pod也被调度到同一节点且挂载同一路径

  • 风险：不要挂载宿主机根目录，存在安全提权风险

PV与PVC

解耦思想

  • 直接挂载NFS：如果yaml清单中写死了NFS的IP地址或者云硬盘ID，开发与运维严重耦合，比如开发要知道NFS的细节，换个环境就要开发重写一套yaml

  • 正常用hostPath：pod漂移就会丢失数据，而且无法（很难）跨节点，毕竟只是半持久存储

  • 用emptyDir：生命周期与pod关联，不能持久存储

PV用法：

这里作为PV的一种存储资源选择，反而有时候是一种最佳选择

  • 本地开发测试，单节点计算，边缘计算等不值得搭建NFS服务，云服务等场景

  • 虽说会有pod漂移风险，但可以借助nodeSelector将pod锁死到固定节点，实现高性能读写，远快于云硬盘，详见存储实验

工作原理

  • PV：集群里的存储资源（好比“硬盘”），由运维提前准备好

  • PVC：用户对存储的“申请单”（好比“我要 10G 空间”），由开发者定义

  • 绑定流程：Pod 绑定 PVC → PVC 根据条件匹配合适的 PV → PV 背后对接真实的 NFS、Ceph 或云硬盘

关联条件

  • 容量：PV值不小于PVC要求

  • 读写策略：

    • 单节点读写RWO：适合本地锁EXT4，XFS

    • 多节点只读ROX

    • 多节点读写RWX：适合网络锁GFS

  • 存储类：类必须一致，不存在包容降级关系

生命周期

  1. Available（可用）：空闲状态，等待 PVC 来绑定

  2. Bound（已绑定）：已被某个 PVC 关联，正在被 Pod 使用

  3. Released（已释放）：【重点踩坑】Pod 删了，PVC 也删了，PV 从 Bound 变成 Released。此时的 PV 虽然数据还在，但不能被新 PVC 直接使用！ 管理员必须手动清理数据（或删除 YAML 中的 claimRef 字段），才能让它回到 Available

  4. Failed（失败）：PV 底层存储出现故障，无法自动恢复

回收策略

pod删除后，pvc还存在，那么pv就还在；只有将pvc删除后，pv会有几种回收策略

  • Retain（保留）：默认策略。PV 变成 Released 后，保留数据，等待管理员手动备份和清理

  • Delete（删除）：PV 被释放时，自动删除关联的存储资产（仅支持 AWS EBS、GCE PD、Azure Disk 等云存储）

  • 【重要废弃信息】：Recycle（回收，简单擦除）已在 Kubernetes v1.15+ 废弃，官方不再推荐使用。不要在 YAML 里写 Recycle 了

用法

STS

volumeClaimTemplates

  • volumeClaimTemplates 不是新存储类型，而是 StatefulSet 专属的“自动批量生成 PVC 的模具”。

  • 工作原理：它里面的 spec 字段（如 accessModes、storageClassName）100% 完全等同于普通 PVC 的写法。

  • 特殊之处：当 StatefulSet 创建 mysql-0 时，系统自动创建一个 pvc-data-mysql-0；创建 mysql-1 时，再自动创建一个 pvc-data-mysql-1。每个 Pod 拥有独立的、互不干扰的专属硬盘。

详见双向链接

串联终极连线：
volumeClaimTemplates 自动生成 PVC → PVC 匹配 StorageClass → StorageClass 开启 WaitForFirstConsumer → Pod 调度到具体节点后才触发创建云硬盘 → 数据隔离，永不丢失。

StorageClass

为什么需要

如果每次申请存储，都要运维提前手动创建好 PV（静态供给），在大规模集群下太累了。
StorageClass 让运维只需定义一套“硬盘模板”，当 PVC 提交时，系统自动根据模板调用云厂商 API 创建 PV，实现“按需分配，量身打造，用完即删”

volumeBindingMode

这是生产环境必看、且 StatefulSet 必须注意的参数：

模式 行为 风险 / 适用场景
Immediate（立即绑定） 创建 PVC 的一瞬间，云厂商的硬盘就被创建出来了。 风险：如果 Pod 还没调度，PVC 可能在一个可用区（如 上海A）创建了硬盘，结果 Pod 被调度到 上海B 区，导致 Pod 挂载失败（云硬盘无法跨可用区挂载）。
WaitForFirstConsumer（延迟绑定） 创建 PVC 时不创建硬盘，直到有一个 Pod 真正调度到某个节点上时，才在该节点所在的可用区创建硬盘。 必须使用：这是所有 StatefulSet（有状态服务，如数据库）存储类的标准配置，确保硬盘和 Pod 在同一个可用区。
