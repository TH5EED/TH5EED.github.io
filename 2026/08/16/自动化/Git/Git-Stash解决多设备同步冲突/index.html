Git-Stash解决多设备同步冲突

发表于2026-08-16|更新于2026-08-16|作战室
|浏览量:

前提

  • 同一个 Obsidian 笔记仓库（mix-note）在==两台设备==间通过 GitHub 远程仓库同步
  • 公司设备已提交并推送了最新改动（整理目录结构、删除部分插件追踪）
  • 家里设备有==未提交的本地修改==（Obsidian 自动生成的插件配置文件变动）
  • 家里设备执行 git pull --rebase 时被 Git 拒绝

场景

多设备协作中非常典型的情况：A 机器改了并推上去了，B 机器也有本地改动但还没 commit，此时 B 想拉取 A 的最新版本。

类比：你在公司把作业写完交了（push），回家发现桌上还摊着另一份没写完的草稿（unstaged changes），这时你想把公司交的那份打印出来对照——但桌子太乱，打印机不让你放纸上去。

问题描述

Git 的顾虑：rebase 需要把你的本地提交”摘下来”再”重新接”到远程最新节点后面。如果工作区有未提交的改动，rebase 过程中可能==覆盖或丢失==这些改动，所以 Git 直接拒绝执行。

操作步骤

第一步：暂存本地改动（stash）

把当前工作区所有未提交的改动==临时存到一个栈里==，工作区恢复干净。

输出：

类比：把桌上没写完的草稿先塞进抽屉，桌面清空。

第二步：拉取远程最新版本

此时工作区干净，rebase 正常执行。本次是 ==Fast-forward==（本地没有独立提交，远程领先），直接快进到最新 commit。

输出（关键部分）：

第三步：恢复本地改动（stash pop）

把抽屉里的草稿拿回桌上。但这次遇到了==冲突==：

第四步：解决冲突

本次冲突类型是 ==modify/delete==（一边改了，另一边删了）：

来源 对该文件的操作 原因
远程（公司） 删除 取消了插件文件的 Git 追踪
本地 stash 修改 Obsidian 自动更新了插件配置

决策：以公司版本为准，接受删除。

第五步：清理 stash 记录

stash pop 遇到冲突时==不会自动删除== stash 条目（留着以防万一），需要手动清理。

涉及命令速查

命令 作用 要点
git stash 暂存未提交改动，工作区变干净 存进栈结构，可多次 stash
git pull --rebase 拉取远程并变基 要求工作区干净
git stash pop 弹出最近一次 stash 并应用 冲突时 stash 条目保留
git rm <file> 标记文件删除（解决 modify/delete 冲突） 同时从工作区和暂存区移除
git stash drop 删除栈顶 stash 条目 pop 冲突后必须手动执行
git status 确认最终状态是否干净 收尾验证

补充：为什么之后不会再冲突

公司那边做了两件事（已随 commit 推送到远程）：

  1. .gitignore 添加了 .obsidian/plugins/ 忽略规则
  2. git rm --cached 将插件文件从版本控制中移除（本地文件保留）

git pull 是 Fast-forward，家里这边==完整继承了同一个 commit==，.gitignore 规则已生效。之后两台机器上插件文件的任何变动都不会被 Git 感知，自然不会再产生冲突。

经验总结

  • git pull --rebase 前习惯性先 git status 看一眼，有脏文件就先 stash
  • stash 是==临时手段==，不是替代 commit 的长期方案
  • modify/delete 冲突只需要做一个决定：留还是删，用 git add 或 git rm 表态
  • 多设备同步时，.gitignore 是避免无意义冲突的第一道防线
