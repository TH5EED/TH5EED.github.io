Jenkins Pipeline（完善版）

原笔记纠错补充 + 回答 pod-template 问题 + 简历版对照

大白话先说

Jenkins 在这套 CICD 里就是个”自动执行器”。你把构建和部署的步骤写成脚本（Pipeline），Jenkins 收到 Webhook 通知后自动按脚本一步步执行。

Jenkins 在 K8s 里跑有个特殊点：==每次构建都会起一个临时 Pod 当构建环境==，构建完就销毁。这样每次都是干净的环境，不会互相污染。

Jenkins 在 K8s 中的部署

持久化存储

在 K8s 中起 Jenkins 服务，需要创建一个 ==PVC（持久化卷声明）==，底层一般用 ==NFS==（网络文件系统）。

大白话：Jenkins 自己有一堆配置数据、构建历史、插件、凭据，这些不能丢。Pod 重启就没了，所以需要挂一块”外部硬盘”——PVC 就是声明”我要一块存储”，NFS 就是底层真正存数据的地方。

为什么要 NFS：多节点的 K8s 集群中，Jenkins Pod 可能调度到任何节点。用本地存储的话换节点就读不到了，NFS 是网络共享存储，所有节点都能访问。

Pod Template 与 Jenkins Agent（回答你的问题）

原笔记问题：==”为什么？说是在 k8s 中创建流水线会以 jenkins-slave 形式，不管什么程序，Python，go，Java 都要预置好环境，搞不懂”==

核心原理

Jenkins 有两种角色：

  • ==Master==：管理节点，负责调度任务、管理配置、提供 Web 界面。你自己跑的那个 Jenkins Pod 就是 Master。
  • ==Agent（Slave）==：执行节点，真正跑构建任务的工作者。

在 K8s 中的特殊机制

传统 Jenkins：Agent 是固定的物理机/虚拟机，一直开着等任务。

K8s 中的 Jenkins：==Agent 是临时的 Pod==。每次有构建任务时，Jenkins Master 调用 K8s API 创建一个新 Pod 当 Agent，构建完了就销毁。

Pod Template 是什么

==Pod Template== 就是一个”Agent Pod 的模子”。你提前定义好：

  • 用什么镜像（比如 maven:3.8 + docker + kubectl）
  • 需要什么资源
  • 挂载什么卷

不同语言的项目需要不同的构建环境：

  • Java 项目：Pod 里要有 Maven、JDK
  • Go 项目：Pod 里要有 Go 编译器
  • Python 项目：Pod 里要有 Python 解释器

所以需要不同的 ==pod-template== 模板，每个模板预置对应语言的环境。

为什么这样设计

优点 说明
干净 每次构建全新环境，不存在上次构建的残留
弹性 构建多时自动扩 Pod，空闲时自动回收
隔离 不同项目用不同环境，互不干扰
资源利用 不用一直开着空闲的 Agent 机器

Pipeline 各阶段

视频版（Helm 部署）

（附件缺失：assets/jenkins/Pasted%20image%2020260805150550.png）

阶段 做什么 说明
1. 指定执行节点 选择 pod-template 根据 Java/Go/Python 选对应模板
2. 定义参数 服务名、环境、镜像 Tag 参数化，不写死
3. 环境变量 设置 PATH、 registry 地址等 构建环境配置
4. 拉取业务代码 git clone 业务代码仓库 拉到 Agent Pod 里
5. 拉取 CI 模板 git clone CI/CD 模板仓库 拉取 build.sh、deploy.sh 等
6. 执行构建脚本 先 mvn clean 出 jar，再 docker build 出镜像 两个制品依次产生
7. 执行部署脚本 helm upgrade 部署到 K8s 用 Helm chart 部署
8. 状态检查 kubectl get deploy 确认部署成功

简历版（ArgoCD GitOps 部署）

阶段 做什么 与视频版区别
1. 指定执行节点 选择 pod-template ==相同==
2. 定义参数 服务名、环境、镜像 Tag ==相同==
3. 拉取业务代码 git clone 业务代码仓库 ==相同==
4. 拉取 CI 模板 通过 ==Shared Library== 加载构建逻辑 换成共享库方式
5. 单元测试 跑测试用例 新增
6. ==BuildKit== 构建镜像 DOCKER_BUILDKIT=1 docker build 替代标准 docker build
7. 推送 Harbor 镜像推到 Harbor + ==Trivy 扫描== 新增安全扫描
8. ==更新 Git 清单 Tag== 修改 K8s 清单仓库中镜像 Tag ==替代 helm deploy==
9. ArgoCD 自动同步 ArgoCD 检测 Git 变更，自动部署 ==Jenkins 不直接部署==
10. Prometheus 监控 统计成功率/时间，告警通知 新增

==核心区别==：视频版第 7-8 步是 Jenkins 主动用 Helm 部署到 K8s；简历版第 8-9 步是 Jenkins 只更新 Git 仓库里的 Tag，==部署交给 ArgoCD 自动完成==。

Shared Library

这是什么

大白话：Shared Library 就是把多个项目重复用到的 Pipeline 逻辑（构建、测试、推送、部署）封装成==共享函数==，存在单独的 Git 仓库里，各个项目调用就行，不用每个项目写一遍。

你笔记里的对应关系

原笔记写的 ci-template/java-pipeline.groovy（会在仓库的vars目录下） ==其实就是 Shared Library 的全局函数==。只是当时记笔记时没点出”Shared Library”这个概念名。

==纠错==：原笔记写”因为用的是声明式语法”——vars 目录下放全局函数和用声明式还是脚本式 Pipeline 没有直接关系。声明式 (Declarative) Pipeline 也可以调用 vars 里的函数。

Shared Library 在简历中的体现

简历写的是”通过 ==Shared Library== 封装构建逻辑”——就是把你笔记里看到的 build.sh、deploy.sh 的逻辑封装成 Groovy 函数，让多个微服务共用。

横向知识

Pipeline as Code

大白话：把流水线定义写成代码（Jenkinsfile），提交到 Git 仓库管理，而不是在 Jenkins 界面上手动点。

对比 传统方式 Pipeline as Code
定义方式 在 Jenkins Web 界面手动配置 写 Jenkinsfile 提交到 Git
版本管理 无法追溯变更 ==Git 就是变更历史==
可复用 每个项目重新配 Shared Library 共用
可审查 看不到谁改了什么 PR/MR 审查流水线变更

Jenkins Master-Agent 架构

Master 不干活，只调度。Agent 才是实际跑构建的。在 K8s 里 Agent 是临时 Pod，==动态创建、用完即删==。

Jenkinsfile 语法风格

声明式 (Declarative) 脚本式 (Scripted)
语法 结构化，pipeline { stage {} } 纯 Groovy 代码
易读性 好，像配置文件 差，像编程
灵活性 受限 高
推荐场景 简单流水线 复杂逻辑

现在主流用声明式，复杂逻辑通过调用 Shared Library 里的函数来补充。
