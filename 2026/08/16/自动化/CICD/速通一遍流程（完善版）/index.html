CICD 速通一遍流程（完善版）

原笔记纠错补充 + 简历版 ArgoCD 流程 + 发布策略 + 大白话

大白话先说

CICD 就是一套自动化流程：开发 push 代码 → 系统自动编译、测试、打包镜像、推仓库、部署到 K8s。全程不需要人手动操作，最多最后点一下”发布”按钮。

==CI 解决”怎么把代码变成可部署的镜像”==，==CD 解决”怎么把镜像部署到环境里”==。

环境需求

基础环境

组件 说明 几台机器
K8s 集群 一主两从 3 台
Harbor 镜像仓库 1 台
GitLab 代码仓库 + CI/CD 模板仓库 1 台
==共 5 台==

可选组件

组件 作用
==Nexus== 制品仓库（存 jar 包），如果只存镜像可以不要
代码检测工具 如 SonarQube，代码质量检查
==ArgoCD== GitOps 部署工具，简历版需要

==纠错==：原笔记写 “naxus” → 应为 ==Nexus==。

不引 Jenkins 行不行？

原笔记思路是对的：只用 GitLab CI（.gitlab-ci.yml）也能完成 CI，但不灵活。Jenkins 优势：

  • ==插件生态丰富==（400+ 插件）
  • ==Shared Library== 可复用构建逻辑
  • ==复杂流水线==编排能力强
  • 开源免费

GitLab CI 更轻量，适合简单场景。复杂企业级流水线一般用 Jenkins。

CI 与 CD

CI（持续集成）

开发者频繁将代码提交到主分支，自动完成：

  • 代码拉取
  • 编译构建
  • 单元测试
  • 代码检查（CI 最后一步，CD 前一步）

==目标：尽早发现问题==。代码一提交就编译就测，不要等到部署时才发现编译不过。

CD（持续交付/部署）

将构建好的制品自动发布到环境：

  • 测试环境
  • 预发布环境
  • 生产环境

==目标：让软件随时可发布==。

持续交付 vs 持续部署

持续交付 (Continuous Delivery) 持续部署 (Continuous Deployment)
区别 到生产环境前==手动确认== ==全自动==部署到生产
适用 大多数公司 成熟企业 / 非核心服务
你笔记说的 “发布一般还是手动发布” “除非大型企业接入 OA”

原笔记这句话是对的：==”提交代码后自动触发后续所有流程，但发布一般还是手动发布”==——这是持续交付，不是持续部署。大多数公司都是 CD（交付），最后上生产需要人审批。

自动化流程

视频版（Helm 部署）

步骤 动作 说明
1 开发者 git push 提交代码到 GitLab
2 触发 ==Webhook== GitLab 通知 Jenkins
3 拉取代码 Jenkins Agent Pod git clone 业务代码
4 编译构建 build Java: mvn clean 出 jar 包
5 单元测试 test 跑测试用例
6 代码质量检查 SonarQube 等（可选）
7 打包制品 artifact jar + Dockerfile → Docker 镜像
8 推送制品仓库 jar → ==Nexus==，镜像 → ==Harbor==
9 自动部署 ==Helm== helm upgrade 部署到 K8s
10 发布完成 灰度 / 金丝雀 / 蓝绿发布

简历版（ArgoCD GitOps 部署）

步骤 动作 与视频版区别
1 开发者 git push ==相同==
2 触发 ==Webhook== ==相同==
3 拉取代码 + ==CI 模板== 通过 ==Shared Library== 加载构建逻辑
4 单元测试 提前到构建前
5 ==BuildKit== 构建镜像 替代标准 docker build，快 40%
6 推送 ==Harbor== + ==Trivy 扫描== 不推 Nexus，新增安全扫描
7 ==更新 Git 清单仓库 Tag== Jenkins 不直接部署，只改镜像 Tag
8 ==ArgoCD 自动同步== ArgoCD 检测 Git 变更，自动部署到 K8s
9 滚动回滚 <1 分钟 ArgoCD 版本回退
10 ==Prometheus 监控 + 告警== 新增监控统计

==核心区别==：视频版 8-9 步是 Jenkins → Nexus/Harbor → Helm 主动部署；简历版 6-8 步是 Jenkins → Harbor → 更新 Git Tag → ==ArgoCD 被动拉取部署==。

横向知识

GitOps（简历核心概念）

大白话：GitOps 就是 ==Git 仓库是唯一真实源==。K8s 集群里跑什么，由 Git 仓库里的清单说了算。

对比 传统 CD GitOps
部署模式 Push（Jenkins 主动推到 K8s） ==Pull==（ArgoCD 主动从 Git 拉取）
集群凭证 Jenkins 需要 K8s kubeconfig ==不需要==，ArgoCD 在集群内部
部署历史 看 Jenkins 日志 ==Git log== 就是部署历史
回滚方式 helm rollback ==git revert==
审计 难 Git 提交记录就是审计

为什么更安全：传统方式 Jenkins 要拿 K8s 的 kubeconfig（集群管理员凭证），一旦 Jenkins 被入侵集群就暴露了。GitOps 模式下 Jenkins ==根本不接触集群==，只改 Git 文件，ArgoCD 在集群内部自己拉取。

Helm（视频版部署工具）

大白话：Helm 就是 K8s 的”包管理器”，类似 Linux 的 apt/yum。

  • ==Chart==：Helm 的包，包含一组 K8s 资源模板（Deployment、Service、Ingress）
  • ==values.yaml==：变量文件，不同环境用不同值
  • helm install / helm upgrade：安装或升级

多环境管理：

发布策略

笔记最后提到”灰度发布，金丝雀，蓝绿发布”，补充解释：

策略 大白话 风险
==滚动更新== (Rolling) 旧 Pod 逐个替换为新 Pod 期间新旧版本并存
==蓝绿发布== (Blue-Green) 旧环境(蓝)和新环境(绿)同时存在，切换流量 切换瞬间生效，回滚=切回去
==金丝雀== (Canary) 先放一小部分流量到新版本，观察没问题再全量 最安全，但需要流量控制
灰度发布 类似金丝雀，逐步扩大新版本流量比例 同金丝雀

K8s 默认用滚动更新。ArgoCD 配合 Argo Rollouts 可以做金丝雀发布。

制品仓库为什么要两个

仓库 存什么 为什么
==Nexus== jar 包 有些场景需要直接用 jar（如给其他项目引用、本地调试）
==Harbor== Docker 镜像 K8s 部署的制品就是镜像

简历版只要 Harbor：因为最终部署到 K8s 的就是镜像，jar 包只是构建中间产物，不需要单独存。
