CICD 基础架构（完善版）

原笔记纠错补充 + 简历项目对照 + 大白话

大白话先说

CICD 就是一条自动流水线：开发写完代码 push 上去，后面的事自动完成——编译、打包、构建镜像、推到仓库、部署到 K8s。开发只管 push，剩下的交给流水线。

核心思路是 ==两个仓库分离==：

  • ==业务代码仓库== 放业务代码（src、pom.xml、Dockerfile）
  • ==CI/CD 模板仓库== 放流水线脚本（构建逻辑、部署脚本）

为什么要分开？因为流水线逻辑是通用的，多个微服务共用一套构建模板，不应该和某个业务的代码耦合在一起。这就是你笔记里说的”多环境多服务的统一模板，参数化，不要写死”。

核心概念补充

微服务

大白话：原来一个应用把所有功能塞在一起（单体架构），现在拆成多个小服务各管各的（用户服务管用户、订单服务管订单），每个微服务独立部署、独立升级。

CICD 和微服务的关系：微服务越多，手动部署越不现实，CICD 的价值越大。每个微服务可以有自己的流水线，但共用一套模板。

制品 (Artifact)

大白话：编译构建后产出的”成品”。两种制品：

  • ==jar 包==：mvn 编译 Java 代码后的产物，是应用本身
  • ==Docker 镜像==：jar 包 + Dockerfile 打包后的产物，是可部署的服务镜像

制品推到仓库（Nexus 存 jar，Harbor 存镜像），后续部署时从仓库拉取。

Webhook

大白话：Webhook 就是”事件通知”。代码 push 到 GitLab 时，GitLab 主动发一个 HTTP 请求告诉 Jenkins”代码变了，快来干活”。不用 Jenkins 自己去轮询检查。

完整流程

视频版（Helm 部署）

这是你看视频记的版本，用 ==Helm== 做部署

（附件缺失：assets/基础架构/Pasted%20image%2020260805143706.png）

  1. 开发者推送业务代码到 GitLab 的 ==业务代码仓库==（user-service/src、pom.xml、Dockerfile）

  2. 推送后触发 ==Webhook==，通知 Jenkins 中该服务对应的流水线

  3. Jenkins 先从 GitLab 拉取 ==CI/CD 模板仓库== 的代码（不是业务代码，是构建和部署脚本）

    • 模板仓库结构：ci-template/java-pipeline.groovy（流水线定义，在 vars 目录下）、build.sh、deploy.sh
    • ==纠错==：原笔记写 ci-templarte，应为 ci-template

  4. ==mvn clean== 编译 Java 代码，产出第一个制品（jar 包），jar 包 + Dockerfile 产出第二个制品（Docker 镜像）

  5. 推送前可能有 ==代码质量检测==（SonarQube 等），检测通过才继续

  6. jar 包推到 ==Nexus==，Docker 镜像推到 ==Harbor==

  7. ==Helm== 拉取该服务的 Chart 模板，给变量赋值（values-dev/test/prod 对应不同环境），执行 helm upgrade 部署到 K8s

  8. Pipeline 还在运行，做==部署后状态检查==（kubectl 获取 Deployment 状态）

简历版（ArgoCD GitOps 部署）

这是你简历上写的版本，用 ==ArgoCD== 做部署，视频没涉及

（附件缺失：assets/基础架构/Pasted%20image%2020260805143706.png）

  1. 开发者推送业务代码到 GitLab ==业务代码仓库==

  2. 推送后触发 ==Webhook==，通知 Jenkins 流水线

  3. Jenkins 拉取 ==CI/CD 模板仓库==（Shared Library 封装构建逻辑）

  4. ==BuildKit== 构建 Docker 镜像（比传统 docker build 快 40%，缓存复用更好）

  5. 单元测试通过后，镜像推送到 ==Harbor==（不推 Nexus，因为简历版没有 jar 包仓库）

  6. ==关键区别==：Jenkins 构建成功后，不直接部署到 K8s，而是==自动更新另一个 Git 仓库中的 K8s 清单文件==（Deployment/Service/Ingress）中的镜像 Tag

  7. ==ArgoCD== 监听这个 Git 仓库，发现镜像 Tag 变了，自动同步到 K8s 集群完成部署

  8. ==Trivy== 在推送 Harbor 时做镜像安全漏洞扫描

  9. ==Prometheus== 监控部署成功率和构建时间，通过 Webhook 发钉钉/企业微信告警

两版对比

环节 视频版 (Helm) 简历版 (ArgoCD GitOps)
构建工具 标准 docker build ==BuildKit==（缓存更好，快 40%）
制品仓库 Nexus（jar）+ Harbor（镜像） ==只 Harbor==（镜像）
部署方式 Helm chart + helm upgrade ==ArgoCD== 监听 Git 变更自动同步
部署触发者 Jenkins 调 deploy.sh 主动 push ==ArgoCD== 主动 pull Git
安全 代码质量检测 ==Trivy== 镜像漏洞扫描
监控 无 ==Prometheus== + Webhook 告警
回滚 helm rollback ==git revert== + ArgoCD 自动同步
集群凭证 Jenkins 需要 K8s kubeconfig ==不需要==，ArgoCD 在集群内部

==核心区别==：视频版是 Jenkins 主动推到 K8s（push 模式），简历版是 ArgoCD 主动从 Git 拉取（pull 模式 / GitOps）。GitOps 更安全——不需要把集群凭证给 Jenkins。

横向知识

Nexus vs Harbor

两个都是”仓库”，但存的东西不同：

Nexus Harbor
存什么 jar 包、npm 包等各种制品 ==Docker 镜像==
类比 编译后的程序包仓库 镜像仓库
你的场景 存 mvn 编译后的 jar 存 docker build 后的镜像

简历版没用 Nexus，因为镜像就是最终部署的制品，jar 包只是中间产物，不需要单独存。视频版用 Nexus 是因为有些场景需要直接管理 jar 包。

BuildKit

大白话：BuildKit 是 Docker 的新一代构建引擎，替代传统的 docker build。

为什么快 40%：

  • ==更好的层缓存复用==：没变的层直接用缓存，不重新构建
  • ==并行构建==：多阶段构建中无依赖的阶段同时跑
  • 垃圾回收更高效

用法：DOCKER_BUILDKIT=1 docker build 或 Jenkins Pipeline 中直接配置 BuildKit。

Trivy

大白话：Trivy 是一个镜像安全扫描工具，扫描 Docker 镜像里的 ==CVE 漏洞==（公开已知的安全漏洞）。

集成方式：推送到 Harbor 时自动触发 Trivy 扫描，发现高危漏洞可以阻止部署。

Prometheus 监控

大白话：Prometheus 是一个时序数据库 + 拉取式监控系统。在 CICD 场景中监控：

  • 构建成功率（部署成功 vs 失败次数）
  • 平均构建时间
  • 资源使用率

告警方式：配置 ==Webhook==，部署失败时自动发钉钉/企业微信通知。
