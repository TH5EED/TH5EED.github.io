类别 检查项 特殊条件

关键复杂度来源：

  • 操作系统分支：CentOS 7 / RedHat 7 / 麒麟 V10 / 统信 / 欧拉 → 不同 OS 不同行为

  • 部署形态：物理机 vs 虚拟机（IO 调度、磁盘调度整个跳过）
  • 安装方式：Docker 容器化 vs Ansible 原生（ansible 检查可跳过）
  • 客户定制忽略：某些项客户明确说不用管

精装版

这个问题问得很好，说明你在认真想而不是盲目堆工作量。我帮你从面试视角和实际可控性两个维度分析一下。

先说结论：做个「精装版」，不要阉割版

你的顾虑我理解——完整版 14 个 check + fix + 多节点 SSH 并发 + INI 配置解析，纯手工写确实工作量大。但阉割成单文件一堆 if-else 反而更危险，因为面试官一追问就露馅。

正确做法：架构完整 + 检查项精选（6-8 个代表性项）

总代码量约 400-500 行，你自己能完全读懂每一行，面试时也能讲清楚。

面试官到底关心什么？能问到什么深度？

我按真实面试场景模拟一下：

第一层：你做了什么？（30 秒）

“写了一个 QFusion 数据库安装前环境检查脚本，用 Bash 实现，支持检查模式和自动修复模式，通过配置文件控制各检查项的行为，能在多节点并发执行。”

✅ 这句话不管 6 项还是 14 项都能说

第二层：怎么设计的？（2-3 分钟）← 这是核心得分点

面试官会看你的架构思维：

“一开始我也想过写成一个大的 shell 脚本里面一堆 if-else，但后来发现每个检查项都要获取数据、判断、输出结果、可能还要修复，逻辑混在一起很难维护。所以分了四层：

  • 数据层 get_xxx() 只负责拿原始值
  • 检查层 check_xxx() 调数据层做判断
  • 修复层 fix_xxx() 只在 –apply 时执行
  • 基础层 _ok/_fail 统一日志格式和计数

这样加新检查项只需要写三个函数，主逻辑不用动。”

💡 这段话就是 bullet 的价值——体现你有工程化思维，不是只会写脚本

第三层：追问（这才是你要准备好的）

追问 你需要掌握的程度 难度
“不同操作系统怎么区分处理的？” 知道 get_os_type() 怎么读 /etc/os-release，switch 分支 ⭐
“虚拟机和物理机怎么判断？” 知道 dmidecode 或 /sys/class/dmi/id/product_name 含 virtual 关键字 ⭐⭐
“配置文件怎么解析的？” INI 格式 grep/sed 或 source 的原理 ⭐
“–apply 修复怎么保证幂等？” 知道先检查再操作的概念（SELinux 已经 disabled 就不改） ⭐⭐
“多节点怎么并发的？” 知道 ssh 后台执行 + wait 收集结果 ⭐⭐
“如果 ssh 连不上怎么办？” 知道设 timeout + 错误码捕获 ⭐⭐

这些问题的共同特点：都是概念性的，不需要你背代码，但要理解为什么这么设计。

第四层：不会问的

  • 不会让你现场手写完整的 IO 调度算法检测
  • 不会纠结麒麟系统和 CentOS 的具体命令差异细节
  • 不会问你 systemd mount 的 config.json 结构

推荐方案：6-8 个代表性检查项

选这些是因为它们覆盖了你文档里所有设计模式：

# 检查项 覆盖的设计模式 复杂度
1 操作系统版本 get → check 基本流程 ⭐
2 内核版本 版本号比较逻辑 ⭐
3 SELinux 有状态检查 + fix（改配置+需重启提示） ⭐⭐
4 swap 服务关闭类 + fstab 持久化检查 ⭐⭐
5 firewalld systemctl 状态检查 ⭐
6 主机名规则 正则校验（无大写、唯一性） ⭐⭐
7 IO 调度算法 物理机/虚拟机分支 + OS 分支 + fix ⭐⭐⭐
8 k8s 依赖包 多包批量检查 + 缺失时给出安装命令 ⭐⭐

这 8 个已经足够展示：

  • ✅ 三层架构（get/check/fix）
  • ✅ 条件分支（OS 类型、物理机/虚拟机）
  • ✅ 配置驱动（跳过某项 / 只警告不修）
  • ✅ 两种模式（check / –apply）
  • ✅ 统一日志格式 + 计数汇总

剩下的 NetworkManager、auditd、ansible、docker 卸载、磁盘挂载等，架构一样只是具体命令不同。面试时一句话带过：”其他检查项遵循同样的模式扩展即可”。

关于”没 AI 做不出来”这件事

说实话：

  1. 架构设计是你自己的判断力——你知道要分层、要知道交互不能靠问答、要配置驱动。这部分 AI 只是帮你想得更周全，核心思路是你的。
  2. 具体代码实现——是的，AI 写得快。但你拿到代码后，逐行读懂、能讲清楚每一步为什么这么做，这就够了。
  3. 面试的本质不是考你能不能徒手写出 500 行脚本，而是看你有没有这种意识和能不能讲清楚思路。

我的建议是：让我把精装版写出来，然后你花时间彻底吃透它。能做到以下程度就非常稳了：

  • 能画出架构图（四层结构）
  • 能说出每个文件的作用
  • 能解释为什么要分 get/check/fix 而不写一起
  • 能讲清楚配置文件怎么控制行为
  • 能说出至少一个”踩过的坑”和解决方案

你觉得这个方向 OK 吗？确认后我就开始写这个精装版。
