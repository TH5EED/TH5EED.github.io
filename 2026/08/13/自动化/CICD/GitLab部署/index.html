GitLab 部署流程

本笔记为 ==GitLab CE 的 Docker Compose 部署手册==，跑在 ci-01 (.231)，是《闭关虚拟机部署规划》Step 2.4 的执行文档。
学习路线总纲见《CI-CD系统学习路线》；前置 Docker 环境见《Docker+Docker Compose部署》。

==本笔记只写步骤，不代执行==：命令列出来，自己 SSH 上去照做，跑完把结果回填到「验证清单」。

一、GitLab 在 CI/CD 流水线中的角色

GitLab 在整条链路中承担 ==三重角色==：

角色 作用 上游 下游
代码仓库 (SCM) 托管应用源码，支持分支/MR/Code Review Developer git push Jenkins（通过 Webhook 拉取）
Webhook 触发器 push 事件主动通知 Jenkins，免轮询 Git 内部 hook Jenkins Webhook receiver
K8s 清单仓库 (GitOps Source) 存放 Deployment/YAML，ArgoCD 持续监听 Jenkins 更新 image tag ArgoCD diff → sync

数据流：Developer push → GitLab 收到 push event → 触发 Webhook → Jenkins 拉代码、跑单测、docker build → push 镜像到 Harbor → Jenkins 改清单仓库的 image tag → ArgoCD 检测到 diff → sync 到 K8s → Pod 滚动更新。

==GitLab 是整条链路的起点和 GitOps 闭环点==——代码进去，变更出来，ArgoCD 再把它拉回集群。

二、部署方案

目标机器：ci-01 192.168.31.231（4C16G，Docker 29.7.2 + Compose v5.4.0）

端口规划（避免后续 Jenkins/Harbor 冲突）：

服务 HTTP SSH 备注
GitLab 8929 2222 2222=容器SSH映射，避开宿主已占的22（宿主SSH）；80留给后续Harbor
Jenkins（后续） 8080 - -
Harbor（后续） 80 - -

数据目录：全部放 /data/gitlab/（80G 数据盘，系统/数据分离原则）

资源优化（4C16G 还要跑 Jenkins+Harbor）：

  • Puma worker = 2（默认按 CPU 核数，会占 4 个）
  • Sidekiq 并发 = 5（默认 10-20）
  • 内置 Grafana 已移除；内置 Prometheus 在 19.x 默认仍运行（实测约 370M，影响小，暂不关，后续由集群级 Prometheus 统一纳管）
  • PostgreSQL max_connections = 100（默认 200）

镜像版本：gitlab/gitlab-ce:19.2.2-ce.0（2026-08-13 实测 :latest 即指向此；已 pin 固定版本避免再次跳大版本）

七、踩坑实录（2026-08-13 实测）

现象

docker compose up -d 后 docker logs -f gitlab 反复刷同样的 FATAL，容器一直起不来：

日志里同一段错误重复约 10 次（每次间隔 8-10 秒），gitlab Reconfigured! 从未出现。

根因

  • 拉到的版本是 gitlab-ce=19.2.2-ce.0（:latest 当前指向）。
  • GitLab 16.0 移除了内置 Grafana、17.0 移除了内置 Prometheus，19.x 的 Omnibus 配置里已经没有 grafana['enable'] / prometheus_monitoring['enable'] 这两个 key。
  • 原笔记（步骤 2）里写的”关闭内置监控”两行，在 19.x 上触发 UnknownConfigOptionError，reconfigure 在解析配置阶段就挂了，服务一个都没起来。

为什么删容器没用（死循环原理）

GitLab 容器首次启动时，entrypoint 把 GITLAB_OMNIBUS_CONFIG 写进 /data/gitlab/config/gitlab.rb，然后跑 gitlab-ctl reconfigure。reconfigure 失败后，gitlab.rb 里已经固化了那行坏配置。之后容器每次重启发现 gitlab.rb 已存在，就不会再从环境变量重建它，于是每次 reconfigure 都撞同一行坏配置 → 无限重启。

修复（已在步骤 2 的 compose 里改好）

  1. cd /data/gitlab && docker compose down
  2. rm -f /data/gitlab/config/gitlab.rb ← 关键：必须删掉含坏配置的 gitlab.rb，否则重建无效
  3. 用去掉 grafana['enable'] / prometheus_monitoring['enable'] 的 compose 覆盖 /data/gitlab/docker-compose.yml（见步骤 2 当前内容）
  4. docker compose up -d → 这次 gitlab.rb 从干净环境变量重建 → reconfigure 通过

经验教训

  • 版本敏感配置必须 pin 版本：compose 里固定 gitlab/gitlab-ce:19.2.2-ce.0，不要裸用 :latest，避免某天跳 20.x 又踩未知配置。
  • “关监控”配置项在 19.x 已移除：Grafana 16.0 移除、旧 Prometheus 配置项（prometheus_monitoring['enable']）也已不支持，写了触发 UnknownConfigOptionError 崩。但 Prometheus 进程本身在 19.x 默认仍运行（实测约 370M，并非”默认关闭”），只是不能用旧 key 去控制它。
  • 排障先看日志里的 FATAL + 第一条 UnknownConfigOptionError，基本就是配置项版本不兼容。
  • 容器反复重启时，优先怀疑 bind mount 里残留的旧 gitlab.rb / gitlab-secrets.json，而不是容器本身。
